# 大目录索引容量放大修复与复验（2026-10-30—31）

## 结论与范围

本轮修复浏览器本地索引的存储放大：全文检索词的索引使用短数字主键，不再为每条词关联重复保存包含长路径的片段主键。文件范围、源码正文、完整词表、符号、导入引用、切块规则和模型上下文预算均保留。未修改后端文档上传、提示词增强、Plan、账号和模型设置，没有真实模型调用。

本轮已完成真实整目录建立与正文抽查，存储中断未再出现；高层上下文选取的整库检查因验收脚本断言错误而无效，已修正脚本并完成三个真实文件的定向补验，未重跑整库选取，不将整份报告写成全部通过。

## 根因与最终实现

旧版 `chunks.searchTerms` 多值索引为每个词重复保存原字符串主键（项目编号、长路径、片段序号）。真实 Chromium 固定样本表明，小批次写入不能降低这一容量放大。

数据库升到版本 4：

- `chunks` 保留原 ID、正文及其他元数据，外部片段契约不变。
- `chunkSearch` 按片段存储一份完整词表，使用自增数字主键建立原生 multiEntry 索引；原片段 ID 通过唯一索引绑定。没有截短词表或做近似词匹配。
- `chunkSearchKeys` 每块保存最多 256 个数字键与原片段 ID 的对应关系。词查询只读命中的数字键及映射块，再按原字符串主键选取原有候选限额；不把写入先后当作原检索顺序。
- 正文与完整词表在同一个只读事务中还原。覆盖、增量删除、项目删除和清空同时维护关联与映射，其他文件和项目保留。
- 旧词表在版本升级事务内逐批迁移，失败整体回滚；迁移和日常写入不加载全项目正文。

候选词查询增加了数字键到原 ID 的映射步骤。其耗时需要和空间收益分别记录，不能承诺所有查询均比旧版更快。

## 保留的失败与方案取舍

最初尝试按词保存关联列表。共享词样本从约 263 MB 降至 25.5 MB，但不同词样本从约 100 MB 上升到 282 MB，写入耗时明显增加，因此未采用。该候选的真实目录测试在 10,749 / 21,536（49.9%）时主动停止；当时未出现存储错误，但绝不计为整目录通过。首次失败和停止记录继续留档。

随后采用短数字键，并将完整词表独立保存一次，避免在正文记录和检索记录中重复保存。没有为了提高结果而排除 `docs/testing`、减少源码、削减词表或提高产品容量上限。

另作了容量边界探针，但没有把它算为通过：普通 Chrome 的 CDP 接口报告已覆盖 70 MiB／12 MiB 配额，旧版仍允许超额写入，没有触发 `QuotaExceededError`；`navigator.storage.estimate()` 的数值也不能单独证明强制限额生效。普通磁盘配置的压缩占用与临时浏览器不同；同轮两组 200 片段在普通配置中分别约 28—30 MB 和 7.7—7.9 MB，只说明该样本存储差异，不能代替真正容量耗尽后的恢复测试。探针和结果全部保留。

数据库有 **21,300** 条文件记录，文件元数据合计 **39,552** 个片段、**259,425,318** 个字符，与摘要一致。**23 / 23** 份分布抽样的实际源文件、索引正文拼接及尾部全部一致；未在提交完成前显示 100%。最终浏览器报告占用 **1,041,697,483** 字节。

### 验收脚本问题与补验边界

整库高层检索脚本错误地断言 `返回路径 === 原文件路径`。实际接口返回的是 `原文件路径#chunk-编号`（`projectIndexer.ts` 中的既有契约），因此三项都被判成 false，整份原始 `report.json` 的 `passed=false` **原样保留**。原运行没有保存这三项实际返回的路径，不能事后把它们改写为通过。

修正后的脚本保留实际返回路径，并检查片段后缀。随后使用同三个真实文件定向补验：3 / 3 条文件选择与复制路径通过，完整索引 16 个片段、92,769 字符。这个补验验证了断言修正及相关检索路径，不替代全库其他文件干扰下的选取验证。原整库查询耗时约 0.96—3.09 秒，仍需纳入后续检索性能观察。

最终核对包括：范围计数相等、数据库文件与片段数量、摘要字符数、代表性源文件逐字符/哈希和尾部对比、路径检索以及不提前显示 100%。这里的正文哈希是分布抽查，不能写成逐文件核验全部源码。

片段与字符合计来自数据库文件元数据，并与最终摘要核对；正文完整性另以实际读取的片段拼接进行分布抽查，没有宣称逐一读取全部数据库片段验证。

## 尚未覆盖

浏览器配额受设备与站点其他占用影响，容量压缩不能保证任意目录永不失败；2 GiB 仍是估算索引预算。空异常说明、容量耗尽后的恢复体验、接近配额的大旧库升级、16 万文件及跨设备压力测试继续待办。本轮没有修改这些策略，也不据此宣布整个文件上传功能全部验收。
