## 2. 按批准顺序实施

### 2.1 安全诊断与成功率

- Provider 的既有修复循环在发布每次失败事实前采集代码定义的校验原因与字段。`ModelCallLogger`、`ModelCallObservation`、`ModelCallAuditService` 复用现有 journal／幂等落库；日志、持久记录和管理员明细新增 `validationReason`、`validationField`。
- 原因仅接收当前枚举，位置仅接收固定协议位置。未知值和旧记录保持 null；成功或非响应校验失败不携带上一轮诊断。数据库读取端再次过滤，损坏或伪造的历史 JSON 不能借新增列回显任意正文。
- 管理员模型明细增加请求结果统计。原始尝试、失败用量、明细分页、管理员权限及租户范围继续沿用既有路径；未新增表或字段，既有审计 JSON 采用可选键扩展，schemaVersion 仍为1。

统计以同租户、requestId、operation 归并，只用于 `prompt.optimize` 和 `plan.generate`。并行的文档摘要和向量化不套用这套顺序修复模型。Mock、明确未发送的尝试排除；缺关联号单列。只有从第1轮开始、序号连续且唯一、前序失败明确会重试、末轮已终止的链路进入成功率分母。跨日截断、漏记录、重复序号或仍在修复的链路标为不完整，不计作最终失败。

| 指标 | 判据／分母 |
| --- | --- |
| 首次成功率 | 首轮成功请求 ÷ 已结束完整请求 |
| 修复成功率 | 第二轮或以后成功请求 ÷ 实际进入重试且已结束的完整请求 |
| 最终失败率 | 末轮失败且不再重试的请求 ÷ 已结束完整请求 |

Plan 提问与最终增强是不同操作，各计一个请求；这些指标只说明响应通过当前校验，不代表作品质量验收。

### 2.2 修复已证实的误拒绝

发现 `OptimizationResultAssembler.resolveAmbiguities` 先对原始模型提醒执行 assessment 一致性检查，后过滤五种已有固定泛化提醒。模型仅返回这些本就不会展示的提醒时，过滤前会提前抛出冲突。新增用例在修复前稳定失败：[首次失败记录](./evidence/response-reliability-2026-10-16/red-result.json)。

修复顺序：先完成原始数组数量、类型、长度和凭据检查，再对模型提醒执行**原有五句的精确过滤**，随后校验剩余模型问题，最后独立合并服务端资料冲突与未决条件。词表未扩大，也不使用关键词批量删除问题。

正反例覆盖：固定提醒可正常过滤；夹带真实授权问题且 assessment 不一致仍拒绝；专业事项不能被改成用户必选；有效 USER_DECISION 保留；敏感内容先拒绝；服务端资料冲突不被模型声明删除；requests 代码任务可把网址作为输入参数并保留可运行代码交付。

**归因：这是一条已由本地失败用例证实的平台校验顺序缺陷。** 因缺少本次用户响应原件，不能认定原 502 必然由该路径引起，也不能声称所有普通参数／专业建议的语义分类问题已解决。

未采用全局系统提示词扩写或研究指导改写：当前缺少支持其质量收益及正常变体风险的真实证据。保留模型声明校验和重要提问，不清空问题、不伪造 USER_DECISION、不将代码任务降级为问卷或空模板。

### 2.3 保持有限修复预算

首次加两次修复仍最多三次；同一模型和路由不变。复用候选七178／180原件通过正式 Provider 离线回放，无效类型和真实专业／用户决定冲突仍在三次后失败，同时逐次保存具体原因与字段。未增加外层重试、在线评审或隐藏模型切换。

### 2.4 按错误类型处理超时

没有修改连接／读取超时、温度或输出预算。本症状为响应到达后的校验失败，延长超时不能修复字段矛盾。网络故障退避、429或请求总截止时间需要独立证据和预算评估，本节点不引入未经验证的策略。

### 2.5 真实、可恢复的错误

`RESULT_INVALID`、HTTP 502及安全诊断详情保持兼容。assessment 冲突改为明确说明“补全判断与待确认事项不一致，本次增强未完成”；其他响应拒绝说明结构、内容或安全校验未通过。

前端沿用后端安全信息及 requestId。直接／Plan 两条失败测试均确认原始输入、背景说明、已有优化结果和未保存编辑草稿保留，加载状态结束，不自动重放请求。没有用 Mock、未校验正文或空架子冒充成功。
