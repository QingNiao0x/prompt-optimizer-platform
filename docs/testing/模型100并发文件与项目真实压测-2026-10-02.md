# 模型 100 并发：文件与项目上下文真实压测（2026-10-02）

## 1. 结论与配置

**全局默认上限已从 50 改为 100，单账号仍为 3。实际达到 100 个同时进行的 DeepSeek 上游调用；本机短时容量验证成立，但综合业务验收未全部通过。**

100 个独立账号同时直接增强时，Flash 返回 99/100 个成功响应，Pro 返回 100/100 个成功响应。Flash 有一次 HTTP 502 / `RESULT_INVALID`；Pro 有一条成功响应未通过规则代号的严格文本检查。100 人 Plan 首轮成功 90 人，失败全部来自 Flash。针对失败账号再提交一次后，共 98 人取得计划；这 98 人同时确认增强全部成功。因此不能把本轮结果表述为“100 人所有流程稳定成功”或“正式上线验收通过”。

本轮没有观察到上游 HTTP 429、网络超时或超过前端 70 秒的业务响应。观察到的问题集中在结果校验及内容检查；它们不能被归为并发名额不足，也不能因并发计数正常就忽略。

配置与实现：

- `.env.example`：`MODEL_CONCURRENCY_GLOBAL_LIMIT=100`，账号上限仍为 `MODEL_CONCURRENCY_USER_LIMIT=3`。
- `services/api/src/main/resources/application.yml`：全局环境变量默认值为 100。
- `ModelConcurrencyProperties.globalLimit` 默认值为 100；已有 Redis 共享名额、租约、续租和释放机制继续使用。
- 超出全局上限立即返回 503 / `MODEL_CONCURRENCY_LIMIT`；同账号第 4 个业务请求返回 429 / `USER_MODEL_CONCURRENCY_LIMIT`。

源码配置需重新启动后端才能生效；部署环境若显式设置为 50，需要同步改成 100。多实例需要共享 Redis、键前缀和一致的限制。本轮使用当前源码启动随机端口的独立测试实例，没有重启已有 9000 服务或执行生产发布；测试后已有服务健康检查仍为 200。

## 2. 工作负载与真实链路

用户明确授权真实 DeepSeek 付费压测。模型接口实际访问 `api.deepseek.com`，调用 ID 为 `deepseek:deepseek-flash` 和 `deepseek:deepseek-v4-pro`；所有成功业务响应均为 `provider.mock=false`。平台显示名来自当前模型目录，不能据此独立证明上游内部版本。

每个 100 人波次使用 **100 个独立账号、100 个真实登录 Session**，同时从起跑门发出请求，包含：

| 资料类型 | 账号数量 | 输入方式 |
| --- | ---: | --- |
| DOCX 活动手册 | 25 | 创建上传任务 → PUT 二进制分片 → complete → 轮询解析到 READY → 通过 documentId 引用 |
| Markdown 活动手册 | 25 | 同样通过真实上传与解析接口，增强请求不内嵌文档正文 |
| Vue / Java 预约项目 | 50 | 调用生产前端 `projectIndexer.ts` 的索引与检索算法，再提交真实代码上下文 |

原始提示词实际为 **778–828 字符**，是本轮“中长度”的明确定义，不代表所有中等项目规模。文档正文为 2280 字符。合成项目含 32 个文件，索引 31 个、过滤一个受保护的 `.env` 文件；本次召回 31 个文件、5574 字符，含 Vue 页面、TypeScript 请求、Java 服务与仓库接口、SQL、测试及需求文档。资料均为测试生成，不读取开发者项目源码或真实用户资料。

项目索引调用的算法为产品实际实现，存储适配器使用测试内存仓库，不是浏览器 IndexedDB 性能测试。API 压测不经过 Vite、浏览器渲染、公网反向代理或 TLS 入口，也没有模拟 100 个浏览器窗口。

真实链路：

```text
独立账号 → CSRF / 图形验证码 / 密码登录
→ 文件分片上传、异步解析或前端项目索引
→ 上下文准备与账号所有权校验
→ 直接增强 / Plan / 带真实 planId 的确认增强
→ 账号限制 → 业务编排 → Redis 全局计数 → 官方 DeepSeek
→ Provider 校验及已有修复重试 → 结果组装 → PostgreSQL 历史提交
→ HTTP 响应及按账号核对历史数量
```

测试仅读取本轮生成的验证码答案来完成正常登录，不跳过密码、验证码或 CSRF 校验。仅禁用测试实例的开发账号初始化器；模型供应商、编排、上下文、连接池及历史保存均使用真实实现。Plan 回答使用合成场景的保守答案，未知日期、数值和业务选择保持待确认。

## 4. 失败证据与改进方向

### 4.1 Flash 直接增强的应用层校验失败

- 场景 46，Markdown 文件，HTTP 502 / `RESULT_INVALID`，8.697 秒。
- requestId：`ff8a65a7-f1b0-45f5-a556-af3ce299a536`。
- 日志显示 `model.call.completed` 后，`DefaultEnhancementOrchestrator` 记录 `optimization.failed / INVALID_RESPONSE`。这证明该请求已经得到上游响应，随后在平台业务流程中失败。

Provider 的 `retryWhenResponseIsInvalid` 只包围其请求和解析逻辑；后续 `OptimizationResultAssembler.assemble` 的校验位于该重试范围外。因此“已有结构修复重试”不保证所有应用层结果校验失败都能恢复。现有脱敏日志没有细分失败字段，不能据此断言是某一个字段超长、缺段落或敏感信息检测误判。

改进方向：为应用层校验补充稳定的原因码和阶段指标，在保留现有安全要求的前提下，对适合修复的结果问题设计有界修复；补足固定失败样本回放，再进行相同输入的真实复验。

### 4.2 Flash 的 Plan 稳定性不足

100 人 Plan 波次中，Flash 10 次返回 502 / `RESULT_INVALID`，其余 40 次成功；Pro 50 次均成功。补试后还有两个 Flash 文档场景失败，场景编号为 48、56。

之前一次 4 人基线中也出现过同类 Flash Plan 失败，运行编号 `bf8fdc8cf218496597ca262917d28f4d`。因此已有证据说明该错误在低并发时也能出现，不能把原因简单归结为“100 并发太大”；本次有限样本也不足以证明并发对发生率完全没有影响。

`OptimizationPlanningServiceImpl.requestValidatedPlan` 已对应用层额外校验失败再试一次，Provider 内部还保留格式修复。因此首轮业务请求中的 10 次失败并非“完全没有自动重试”。继续无差别增加重试会放大时延和费用，应先定位具体校验原因，再检查模型输出约束与校验规则是否一致。

改进方向：优先定位 Flash Plan 的无效结果原因及重试耗尽情况，按模型、操作、资料类型统计用户可见错误；使用失败场景做针对性回归和真实复验。当前 Pro Plan 在这组 50 人子样本中通过，不等于单独验证了 100 人 Pro Plan，也不替代既有 Plan 正式业务质量门槛。

### 4.3 Pro 的一条资料代号检查未通过

- 场景 85，项目代码上下文，HTTP 200，25.073 秒，requestId `a1536f59-cd42-4861-b5a4-1c30400d913b`。
- 返回 31 个上下文片段，片段包含 `RESERVATION_WINDOW_8D`，但最终提示词没有通过该代号的原样字符串包含检查。

本次只保存安全元数据，没有归档该条完整生成正文；因此尚未人工区分“内容遗漏”和“Markdown 转义或表达差异”。报告将其保留为未通过的内容检查，既不计作 HTTP 故障，也不宣称已经证实丢失了业务语义。后续需为合成失败样本保存可审阅正文，再核对渲染后的内容与业务事实。
