# 通用文章编辑候选的基线与封存题集

[基线请求](baseline.json)通过本地工作台调用的文章服务实际生成一次，复用数据库中已核实的合成账号，验收事务回滚。探针从能力接口对应的服务读取文章默认模型。实际运行采用 text-polish-v3、DeepSeek Flash、温度 0.2、关闭思考、8000 输出 Token、非流式及 JSON 响应。基线 1 次上游调用，协议修复 0 次。这条人工编写的探针仅用来锁定参数。

开发回归可使用已见的[中文轻度稿](../text-polish-zh-light-fidelity-2026-11-21/holdout/blind-packet.json)、[中英文文体稿](../text-polish-options-2026-11-20/matrix/samples.json)及[大幅重构保真稿](../text-polish-options-2026-11-20/fidelity/samples.json)。这些作品可用于核对已有问题与工程链路。

[封存题集](samples.json)均为新写的合成稿件，轻度和大幅重构各八篇，每档含四篇待改稿及混合文体、陌生题材、自然稿、严格限定稿各一篇。公交场站试点报告和同题随笔用于检查用途适应性，公交与灌区两篇报告用于检查不同阅读问题。生成输入使用各题的 input 及基线实测模型 ID。reviewOnly 供人工评阅，不进入模型请求。题目不会作为候选的示范，也不参与候选改稿。

真实对照计划 32 次正常生成，按两档各 16 次安排。对内固定原文、要求、模型和有效参数，只改变实际发送的 system 指导。按每档独立判断，四篇主要待改稿至少三篇解决主要阅读问题，至少两个用途优于基线，整组胜多于负，重要语义错误为零。自然稿持平可通过。混合文体或陌生题材明显退步要记录并限制采用范围。正式采用另需两位独立盲评者核对。阶段一至三以工程和链路验证为完成条件。

## 候选与工程验证

评测实例可用 `--app.text-polish.strategy-version=text-polish-general-edit-v1` 显式选择候选。一次请求装配通用保真资源、按阅读问题编辑的指导及本次文体和幅度。语言识别仅用于执行记录。真实对照以基线快照为准，逐对核对策略、模型、参数和完整输入。

后端 613 项文章及试用相关回归通过。受控请求覆盖中英文、混合语言、短稿及全部文体和幅度，验证完整输入、协议修复前后的策略冻结、工作台生成接口、保存当前稿后继续润色和 PostgreSQL 历史。桌面和移动端 26 项浏览器回归通过，覆盖执行信息、恢复历史和纯正文复制。

第一至三步实际调用 1 次，用于基线快照。第四步按封存题集完成 32 次真实生成。第五步依据实测暂缓采用，累计实际调用为 33 次。[真实作品对照](holdout/README.md) · [采用决定](adoption.md)
