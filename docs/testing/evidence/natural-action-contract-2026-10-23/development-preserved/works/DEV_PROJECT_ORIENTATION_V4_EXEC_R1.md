- **前端**：Vue3 + TypeScript
- **后端**：Spring Boot 3

### 1.2 集成方式（材料明确部分）

## 2. 新旧模块对应关系与职责

### 2.1 对应关系

| 维度 | 新模块 | 旧模块 | 说明 |
|---|---|---|---|
| 后端 | `care` | `legacycare` | 新模块承载记录读写；旧模块保留旧用户入口 |
| 前端 | `care` | `care-old` | 新模块承载随访表单；旧模块保留旧用户入口 |
| 调用路径 | `/api/care` | 待确认（旧入口的调用路径材料未给出） | 新旧是否共用同一路径前缀需确认 |

### 2.2 职责划分（材料明确部分）
- **前端 `care`**：负责**随访表单**（表单展示与交互）。
- **后端 `care`**：负责**记录读写**（随访记录的读取与写入）。
- **`legacycare`（后端旧）与 `care-old`（前端旧）**：**保留旧用户入口**，即旧用户仍可通过旧模块进入相关功能。

### 2.3 待确认项
- 旧模块（`legacycare` / `care-old`）是否仍承担完整的随访表单与记录读写，还是仅做入口跳转/兼容。
- 新旧模块是否共享同一数据存储（同一库表）还是各自独立存储。
- 旧入口的访问路径、路由与 `/api/care` 的关系（是否也走 `/api/care`，或走独立路径）。
- 新旧模块的权限、菜单、用户可见范围如何区分。

## 3. `/api/care` 调用链路

### 3.1 链路（材料明确部分）
```
前端 care（随访表单）
   → 调用 /api/care
   → 后端 care（记录读写）
```

即：前端新模块的随访表单发起请求，经 `/api/care` 路径到达后端新模块 `care`，由其后端完成随访记录的读取与写入。

- **后端侧**：`/api/care` 对应的 Controller/Service/Mapper 分层、读写分别对应哪些操作、事务与校验逻辑。
- **数据层**：涉及的数据库表、字段、读写 SQL 或 ORM 映射（材料未提供，待确认）。
- **异常与返回**：统一返回体格式、鉴权失败与业务异常的约定。

## 4. 新旧模块在随访功能上的差异与同步要点

### 4.1 差异（材料可支撑的部分）
- **实现位置不同**：新随访表单在前端 `care`，旧入口在 `care-old`；新记录读写在后端 `care`，旧入口在 `legacycare`。
- **定位不同**：新模块是随访功能的主实现；旧模块定位为「保留旧用户入口」，即兼容旧用户访问。
- **调用路径**：新链路明确走 `/api/care`；旧链路的调用路径材料未说明（待确认）。

### 4.2 待确认的差异点
- 新旧随访表单的字段、校验规则、交互流程是否一致。
- 新旧后端读写的业务规则（如状态流转、必填项、权限校验）是否一致。
- 旧模块是否已停止功能演进、仅做入口保留，还是仍需同步业务变更。

### 4.3 同步修改检查要点（后续修改随访功能时使用）

> 以下为检查清单，具体实现细节需在拿到完整代码后逐项确认。

**前端**
1. 随访表单字段、校验规则、默认值在 `care` 与 `care-old` 中是否一致（或旧模块是否明确不再同步）。
2. 表单提交/查询的请求路径、参数结构在新旧前端是否一致；旧前端是否仍指向可用接口。
3. 路由与菜单：旧入口 `care-old` 是否仍可正常进入，跳转目标是否正确。
4. 权限与可见性：新旧入口的用户范围、按钮权限是否需同步调整。
5. 错误提示、加载态、空数据等交互在新旧模块是否表现一致。

**后端**
6. `/api/care` 的接口契约（路径、方法、入参、出参）变更时，旧模块 `legacycare` 是否有对应接口或兼容层。
7. 记录读写的业务规则（校验、状态、事务）在新旧后端是否一致。
8. 数据存储：新旧模块是否共用同一数据源；若共用，字段与语义变更需双向确认。
9. 鉴权与权限校验在新旧接口是否一致，避免旧入口绕过新规则。
10. 异常返回格式与错误码在新旧接口是否统一。

**联调与回归**
11. 新链路（`care` → `/api/care` → `care`）端到端验证。
12. 旧入口（`care-old` → 旧路径 → `legacycare`）端到端验证，确认旧用户不受影响。
13. 新旧入口并存时的数据一致性验证（同一记录经新旧入口读写是否一致）。
14. 变更影响面记录：明确本次修改是否要求旧模块同步，若不同步需记录原因与风险。
