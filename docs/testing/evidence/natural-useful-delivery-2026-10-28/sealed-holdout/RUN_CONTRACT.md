# 统一执行合同

## 解封与材料边界

1. 先由协调者在本目录之外记录候选标识、候选源码/指导哈希、拟采用的下游模型与参数、执行臂、调用上限及授权依据；再明确授权解封。编题期间的封存写入不构成解封。
2. `case-index.json` 指明每题唯一的 `prompt.md`、附件清单和答案卡。原始臂使用该 `prompt.md` 全文；优化臂只替换需求正文，附件逐字节保持相同。增强器也必须收到该题全部指定附件，不能只向某一执行臂补资料。各臂都应收到相同的附件名称和明确的正文/附件边界。
3. 只向增强器/执行器开放当前题输入，不开放答案卡、隐藏检查、其他题、其他臂结果或评审意见。不向执行器加入本合同中的评分指令。本合同属于评测运行约束，题目本身的交付要求以原始需求与其附件为准。
4. 四题全部使用合成材料，不包含真实用户数据。数据中的日期和价格只属于该题虚构情境，不能作为现实市场或运营事实。

## 各臂一致条件

- 同一题的各臂使用同一准确下游模型版本、相同采样参数、最大输出 token 数 2600、相同本地工具能力及新会话。记录实际值；模型未固定前不执行。
- 不联网、不读取项目源码或用户历史。文字题所需信息均在输入中；代码题允许使用同一版本 Node.js 进行本地运行，不安装依赖。
- 原始需求内规定的输出格式对所有执行臂完全相同。不得在某一臂追加例子、答案提示、额外约束或更长输出额度；不得单独修复一个臂的作品再计为首轮结果。
- 每臂每题一次正式下游执行。失败、截断、拒答和工具错误均保留；技术重跑必须对称、事先说明原因并与首轮分列，不能挑选最好一次覆盖原件。
- 任何额外付费评审或重跑仍受协调者已冻结的授权调用上限约束，本合同不授予调用预算。

## 作品与判定

1. 保存传给增强器的实际输入、增强器完整响应、平台组装后及实际复制的提示词、传给下游的实际输入、下游完整响应/代码和工具结果。附件用本清单 SHA256 核对；保存组装前后文本以辨别模型、平台和执行器问题。
2. 将作品匿名化后再按各自答案卡判定。每题 10 个二元检查项，每项只取 0 或 1；每项引用作品中的实际位置或运行结果。不按长度、术语数量、标题数量或“看起来更专业”加分。超出题目字数限制只影响对应格式项，不能用篇幅代替内容检查。
3. 一题的等价写法、合理四舍五入和不同但有用的拟议设计都可通过相应项；不得把答案卡中的示例方案或措辞当成唯一正确答案。新增约束只有原始需求或附件明确要求时才可成为硬门槛。
4. 严重标记另列：改变原交付物、捏造实质事实/已确认决定、核心计算错误导致错误结论、遗漏足以使作品不可用的明确要求、代码无法按约定运行。分数不能抵消严重标记；标记归因须结合完整输入、组装文本和作品，不单凭评审标签。
5. 代码题同时运行分离保存的检查脚本。隐藏检查只依据原始需求，运行失败需区分作品问题和检查器问题；不得把脚本自身异常直接记为代码失败。文字题不要求特定句式。
6. 各题分别报告原始臂/优化臂作品是否可直接使用、10 项结果、严重标记、证据和未定归因。四题总分只作描述，不单独构成候选采用或发布结论；本题集规模小，不证明普遍收益。

## 封存与解释边界

这是一组内部、作者信息隔离的留出题，题型覆盖有限，作者不是外部独立专家。不得据此声称全面覆盖真实用户、所有模型或全部场景。冻结后不得改题、补答案条件、换题或者重写原件来适配某个候选；如发现题目缺陷，保留原件并单列争议。
