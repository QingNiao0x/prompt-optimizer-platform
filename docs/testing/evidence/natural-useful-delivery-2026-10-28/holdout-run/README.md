# 冻结后四题：输入、作品与匿名审阅

`seal-verification.json`记录对正式解封manifest及全部18文件的字节校验。原封存题、答案卡与指导均未修改。所有指定附件都在增强和执行时可见，没有execution-only材料；答案卡和检查器不进入增强或执行载荷。

实际UI捕获位于`captures/H01..H03`与`captures-r2/H04`。H01无附件；H02、H03通过实际文件选择器上传；H04最终显式上传两份指定文件，保留原始字节。H04首次小项目选择只召回源码、遗漏package.json的请求和截图保留在`captures/H04`，未调用模型，不作为合格输入。这是输入方式不满足“指定两附件完整可见”的失败，不以添加执行时材料静默弥补。

`generation-bundle.json`仅使用真实UI构造的DTO，31/47四题各一次增强。`product-gate.json`由协调者依据实际正文逐项审核，只允许进入作品，不代表质量收益或采用。通过后运行：

```text
node holdout-run/build-works-bundle.mjs <增强阶段> <product-gate.json绝对路径>
```

生成的`works-bundle.json`各臂每题一次正式执行，max_tokens=2600。共同system只明确既定任务和工具能力；输出格式仍完全由原始需求决定。原始臂使用封存prompt全文，所有臂都收到同一附件原文和边界。H01若三臂实际提示词等价，作品差异只能记采样波动，不能算增强收益。

## 文本匿名审阅

作品阶段完成后执行：

```text
node holdout-run/materialize-blind-review.mjs <作品阶段>
```

`anonymous/<阶段>/H01..H03.json`只含原题、同附件、隐藏臂身份的实际作品和封存判据。随机标签映射单独写进`coordinator/<阶段>-blind-map.json`，不得交给评审代理。保留所有正式结果、截断和缺失，不挑选较好作品。评审先判断各份作品是否能使用、具体还需补改什么，再比较；不以篇幅或标题数量计收益。此为内部辅助评估，不冒称真人或外部专家。

## H04安全检查

封存检查器的CLI会直接import作品，不能用它在宿主加载模型脚本。使用：

```text
node holdout-run/run-h04-results.mjs <作品阶段>
```

`check-h04.mjs`逐次核验原封存检查器哈希，在新受限子进程内用同realm对象、断言和错误类型执行其原十组行为；不加载宿主模块、不继承密钥环境、不运行包脚本。自测分别证明正确实现通过，原桩、显示名错误、宿主构造器尝试和死循环被识别。静态import不支持时标记工具能力复核，不自动认定为语义错误。

唯一代码可定位时，额外说明仅造成格式项失败，代码仍原样查行为；多份实现不擅自选其中一份。检查输出对照答案卡第1—9项记录行为事实，第10项的无外部操作仍须阅读实际源码，不把VM通过等同所有语义正确。所有输出写新文件，禁止覆盖原判或质量重试。
