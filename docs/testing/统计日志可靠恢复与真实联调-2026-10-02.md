# 统计日志可靠恢复与真实联调（2026-10-02）

## 实现变化

### 服务端持久接收与恢复

- `AuditEventJournal` 先写专用目录的不可变事件文件，刷新文件内容后原子发布；接收成功后由 `AuditEventDelivery` 重放。原始 `.json` 和提交确认 `.ack` 永久保留，没有自动清理。
- `AuditEventDatabaseWriter.write` 使用独立 `REQUIRES_NEW` 事务。事务提交后才追加 ack；数据库提交与 ack 之间中断时重新投递，`audit_event.id` 的 `ON CONFLICT DO NOTHING` 防止重复计数。复用现有主键，本轮没有新增或执行数据库迁移。
- 启动扫描未确认事件；运行中分批投递、指数退避且不按失败次数丢弃。数据库连接故障触发实例级退避，约束失败的单条事件不阻塞其他事件。损坏文件保留并告警，不能伪造恢复成功。
- journal 写入失败时尝试独立数据库提交；两个持久通道均失败时，浏览器接口返回可重试 503。服务端业务事件记录明确错误并放行主业务，不能保证这种双重故障下事件仍不丢失。
- 日志只输出稳定事件代码、阶段、异常类型、requestId 和安全 SQLState/约束名称。不输出凭据、密码哈希、原始请求体、审计 JSON、IP 或底层可能含敏感值的异常消息。

### 浏览器恢复与首页采集

- 每个事件先保存账号隔离的 localStorage 条目，再请求服务端；失败或刷新后使用同一 eventId 重试。每条记录只含事件代码、发生时刻、幂等 UUID、预期账号及无认证能力的登录关联号，不保存邮箱、文件正文、Cookie 或 Token。
- 网络失败、408、429 和 5xx 自动退避重试；401/403/409 暂停当前账号，重新认证后恢复。切换账号中止在途请求；服务端使用当前身份复核 expectedUserId，不能把旧账号事件写给新账号。
- 原始发生时间保留并归一到 UTC。不能确认仍处于原登录上下文时，IP、登录关联和所在地保留 null，不能用补写时的新位置伪造历史事实。首次关联信息尚未取得时也按未知处理。
- localStorage 被禁用、配额不足或 UUID 创建失败会明确输出固定降级代码；内存队列不能保证浏览器退出后的恢复，不把这种场景描述成持久化成功。
- 路由采集集中在 `analyticsRouteCapture`：成功导航与身份恢复共同触发，同一文档内一次导航只采一次。直接打开或刷新首页也会在登录身份恢复后补报。刷新产生新的 PV；每日访问人数继续按账号 ID 去重，因此 UV 不随刷新增加。
- `auth.initialize` 复用正在进行的初始化 Promise，避免共享入口并发恢复身份时发生竞态。页面访问、复制结果等主业务不等待审计网络恢复。

### 查询及界面

- 新增管理员 `GET /api/v1/admin/analytics/delivery`，Security 与数据库当前角色复核共同保护；未登录 401，普通用户或已撤销管理员 403。状态标记 `scope=INSTANCE`，不能当作集群汇总。
- 管理员页面每 10 秒读取轻量状态，展示待补写数量、最老事件年龄和损坏文件。状态读取失败不影响仪表盘查询；补写完成后手动查询刷新统计。
- 性能演练发现旧分页计数将完整明细及 `ORDER BY` 包在 COUNT 子查询中，PostgreSQL 报 `TupleSort main` 内存不足。改为 Page.countId 指向独立 `countOperationLogs`，列表和计数复用同一 WHERE；计数不排序、不投影 details、不关联展示字段。所有条件仍参数绑定，分页响应契约保持不变。
- 首次性能实测未达到 2 秒目标。针对执行计划中的原始事件排序，访问/使用/设备指标改为先按账号聚合；日指标和排行榜先按统计时区的账号/自然日聚合；小时指标先汇总再连接 24 小时骨架。保留账号 ID 去重、零值填充、关键操作口径、筛选与排序契约。优化后的 33 项重点回归通过；性能必须另行复测，不能用 SQL 已修改代替性能验收结果。
- 中间复测发现日志页有较大的尾延迟。将显示名称改为不参与排序的标量输出表达式，避免全候选日志先关联账号，再排序分页；MyBatis-Plus 仍负责分页，计数/筛选继续复用原条件。依据 PostgreSQL 16 的 [SELECT 输出求值规则](https://www.postgresql.org/docs/16/sql-select.html#SQL-SELECT-LIST)，不被 DISTINCT、ORDER BY 或 GROUP BY 引用的这种输出会在排序和 LIMIT 后求值。修改后同组 33 项重点回归再次通过；性能报告额外采集独立 COUNT 和真实 LIMIT 20 分页查询的参数化执行计划，继续验证实际效果。
- 后续日志投影实测消除了日志页瓶颈，但并发仪表盘仍未达标。新增内部 `dashboardMetrics`：只扫描一次主区间事件，物化精简投影并复用账号/自然日归并结果，返回 SUMMARY/DAILY/HOURLY/DEVICE 四种类型行。服务严格检查完整日期/小时骨架、重复或非法结果，再组装原有响应；注册账号和固定近十二月趋势仍独立查询，同一只读快照保持不变。原四种独立查询保留，用复杂 PostgreSQL 场景逐项对照，不引入缓存、数据库参数调整或迁移。设备同分顺序继续由 PostgreSQL collation 决定，Java 不重排历史设备代码；日活均值按 BigDecimal 累加防止 long 溢出。此改动的 95 项重点回归、原目标性能验收和最终真实浏览器复验通过。
- 充值仍返回 `rechargeStatisticsAvailable=false`，不查询尚未接入的数据源，不生成模拟套餐统计。

## 恢复配置与运维流程

以下是代码默认值，不是生产配置或凭据：

| 属性（`app.analytics.delivery` 下） | 默认值 | 用途 |
| --- | --- | --- |
| `journal-directory` | `./data/analytics-journal` | 每实例专属持久目录；部署时必须绑定持久卷 |
| `batch-size` | 100 | 单轮最多投递数量 |
| `retry-initial-ms` | 1000 | 初始退避，毫秒 |
| `retry-max-ms` | 30000 | 最大退避，毫秒；无重试次数过期 |
| `pending-alert-threshold` | 1000 | 待写数量达到阈值时降级告警 |
| `oldest-pending-alert-seconds` | 300 | 最老事件年龄达到阈值时降级告警 |

Micrometer 指标：`analytics.delivery.pending.events`、`analytics.delivery.oldest.pending.seconds`、`analytics.delivery.corrupt.files`、`analytics.delivery.database.failures`、`analytics.delivery.journal.failures`。累计失败计数在进程重启后重置；当前状态表示最近投递结果，不能替代数据库存活探针。没有新增 Redis 审计队列或缓存；既有会话 TTL 规则保持不变。

告警处理步骤：

1. 遇到 `analytics.audit_write_failure` 或 backlogAlert，检查数据库连通性、SQLState 和约束；修复后等待自动补写，不手动重新生成 eventId。
2. 遇到 `analytics.audit_journal_failure`，检查实例持久卷权限与容量；此时数据库回退可能已成功，需分别判断两个通道状态。
3. 遇到 `analytics.audit_journal_corrupt`，保留原文件，按受控修复流程检查；不得直接删除文件或把损坏文件视为已提交。修复后重启实例重新扫描，corruptFiles 是扫描快照，普通重放不会自动清除该计数。
4. 遇到 `analytics.audit_unrecoverable_failure`，立即告警并记录双通道故障范围；不能仅凭业务成功响应断言审计完整。
5. 恢复后检查 pendingEvents 回到 0、损坏数量为 0、出现 `analytics.audit_delivery_recovered`，再重新查询统计核对。

生产部署还需把这些指标或日志接入现有告警系统，并演练实际通知接收。本轮实现了指标、错误日志、管理员告警展示，未向任何外部人员或服务发送告警。

持久目录须有服务账户权限、备份与容量监控，每实例使用独立目录，多个进程不能共享同一个 journal；不可位于临时容器层或公开静态目录。POSIX 限制目录/文件权限并刷新目录项；Windows 依赖服务目录 ACL，Java FileChannel 不能在该平台刷新目录元数据。进程重启恢复测试不等于突然断电或存储硬件故障测试。默认目录已加入 `.gitignore`，不得将审计文件提交到仓库。

## 验证方法与证据边界

### 后端单元与数据库回归

使用真实 PostgreSQL 的既有 schema，关闭 Flyway，替换管理员和密码初始化器，随机创建测试账户/租户/工作区，事务回滚并检查无残留。

旧 `AnalyticsLocalDatabaseAcceptanceTest` 为同线程事务夹具，本轮使用测试专用投递适配器把真实 Mapper 写入该事务，避免独立生产写入事务读取不到未提交测试账户。该组验证业务采集和查询契约；不证明生产投递事务的 commit/ack 顺序。新恢复测试和真实 HTTP 验收分别验证恢复协议与网络链路。

### 真实浏览器与 HTTP

`AnalyticsRealBrowserAcceptanceTest` 启动随机端口 Spring Boot、独立 Vite `/api` 代理与真实 Chrome，使用本地 PostgreSQL/Redis。测试账号和验证码仅通过进程间私有管道传递，不输出认证请求或凭据；Mock Provider 避免外部模型调用。

HTTP 测试使用测试专用数据库连接代理，把多线程 HTTP 写入包在外层回滚事务内，防止污染现有数据库。此代理暂不产生独立物理 commit，因此不能将此项结果描述成真实断电、物理提交或数据库停机演练。数据库失败在审计写入边界注入；浏览器网络失败注入一次真实上报请求，其他业务继续通过真实 HTTP/Redis/MyBatis 运行。

### 性能

`AnalyticsPerformanceAcceptanceTest` 使用真实 PostgreSQL 和测试专用 Mapper；关闭 MyBatis 一级跨语句复用，调用实际仪表盘服务。串行查询可见 10 万事件；4 个并发读线程各有独立回滚事务与 10 万事件，物理共 40 万未提交合成事件，各线程看到自身 10 万及原有基线，不是四线程共享同一批已提交事件。包括不带账号过滤的聚合、排行榜和日志分页，并输出脱敏执行计划结构。

目标为每个并发读线程仪表盘 p95 ≤ 2000ms 且查询错误为零。该结果是本机指定规模验收；不能外推多年永久留存规模、生产硬件或持续高并发写入容量。

# apps/web；独立端口与产物目录，避免干扰现有开发服务。
npm.cmd run test
npm.cmd run typecheck
npm.cmd run build
$env:PROMPT_OPTIMIZER_E2E_PORT='5193'
npm.cmd run test:e2e -- e2e/analytics-layout.spec.ts e2e/analytics-pagination.spec.ts e2e/analytics-recovery.spec.ts e2e/analytics-delivery-status.spec.ts --output=test-results/analytics-acceptance

本机默认 HTTP 启动遇到 JDK 的 Unix domain 回环连接 `Invalid argument: connect`，在沙箱外亦复现。切换 `WindowsSelectorProvider` 无效；实际有效措施是将测试 JVM 的 `jdk.net.unixdomain.tmpdir` 指向工作区 `tmp` 目录。默认 Tomcat NIO 已成功启动，不使用 NIO2 替代，不修改项目运行配置或升级 JDK。此参数仅用于本机测试，其他机器应按实际运行环境确认是否需要。
