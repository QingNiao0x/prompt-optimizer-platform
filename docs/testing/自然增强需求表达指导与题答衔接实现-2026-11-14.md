# 自然增强需求表达指导与题答衔接实现

## 第一步 正文指导

新增`EXPRESSION → core-expression-v1`，从正常服务端配置入口选择。正文优先明确动作、对象、指代、顺序和条件归属，普通设计以任务和上下文为依据保持拟议状态，已有事实与用户确认继续要求真实依据。充分需求允许少改或正确保留。

指导采用新的完整正文原则，消除了旧指导对原任务内部设计的宽泛限制。模型本次交付优化提示词，原始工作由下游执行。v5完整响应协议、来源、正文引用及题答规则继续复用，第一步的范围准备与Plan指导逐字复用现有版本，用于后续对照。

`NaturalExpressionProviderTest`通过正常Provider传输核对实际system、原始输入、范围与正文阶段，并覆盖错误正文引用经一次协议修复后继续拒绝。测试中模型响应为受控夹具，其原文保留结果仅用于验证路由与保护。

定向5套共81项通过，分别为表达Provider5、配置10、Plan上下文19、范围来源修复8、自然服务39。首次沙箱运行在Java动态代理加载后停滞并中止，原日志保留在本机tmp。相同离线检查在本机权限下通过，未改变断言。

服务端可用`NATURAL_ENHANCEMENT_PROFILE=EXPRESSION`选择本路径。当前源码默认为`PROTOCOL_SCOPE_REPAIR → core-repair-v5`。本轮尚无真实模型、作品或工作台采用验证，运行服务未重启，生成质量和日常启用待验证。

## 第二步 材料与Plan衔接

表达路径在范围准备、正文和Plan阶段就近携带相同的服务端来源编号。`context`与`planningContext`分别编号，片段原文、摘要与用途保留，完整原始提示词和全部实际题答继续传入。来源标注仅修改序列化输入副本。

准备、正文和Plan共用资料含义说明，格式参考、事实依据与处理对象各自按用户委托使用。正文融合可读材料中的必要名称、栏目、路径和条件，未解析内容保留实际可见范围。此处复用既有文本上下文与材料用途能力，未新增OCR或图片识别服务。

Plan指导明确上下文可回答、用户决定权及结果影响三个条件。原任务内的检索、阅读和已委托设计由执行者承担。实际回答中的待定、无资料和无权限按各自归属保留，题干及推荐值保持问题背景身份。模型是否始终遵循上述语义仍需后续真实评测。

复用既有`NaturalPromptMetadataRepair`，只对已定位的来源记录或维度错误返回补丁，服务端固定首稿并在补丁后重新校验。来源、实际题答、用户目标归属与正文覆盖继续强制检查。准备阶段无首稿时使用原有有界协议修复。

第二步10套定向检查最终覆盖167项不同用例，重复执行不累计。包括表达Provider13、配置10、Plan上下文19、范围来源8、自然服务39、Balanced及双路径历史回放8、既有元数据Provider9、元数据补丁19、材料用途8、问题过滤34。新增用例覆盖以下情况。

- 当前与Plan时材料的编号、用途和内容在准备、正文和Plan中完整传递。
- 已回答但日期待定、明确无资料、明确无权限三种回答继续传递。
- 相同文字的不同题答仍分别核对，漏一项回答来源继续拒绝。
- 零问题Plan与确有用户决定的大小限制问题通过相同阶段DTO解析。
