# 审计补写刷屏修复（2026-10-02）

## 根因与实测证据

- 日志来源是 `AuditEventDelivery` 的 `analytics-audit-delivery` 线程，以及本地 SQL 调试启用的 P6Spy。启动会恢复 journal，单轮最多补写 100 条；原实现对每条写入失败都输出 ERROR 和 SQL/rollback。
- 本机初次检查有 902 个事件文件、431 个确认文件，剩余 471 条未确认。参数化查询确认这 471 条的租户和账号均不存在、事件均未入库。
- 从其中一条原始事件复现插入，PostgreSQL 返回 `23503 / audit_event_tenant_id_fkey`；复现事务随后回滚，没有创建业务数据或执行迁移。
- 这 471 条事件的租户 ID 均匹配 `services/api/src/test/java/com/promptoptimizer/identity/support/TestActors.java` 的固定测试常量。测试默认属性没有配置独立 journal，使用虚拟身份的 Spring 集成测试因此污染日常服务的持久队列。
- `RealModelConcurrencyAcceptanceTest` 已显式配置独立目录。本次根因不能归咎于该付费模型验收自动运行；普通服务启动也不会自动启动它。

## 修改范围

1. 测试属性设置 `${user.dir}/target/test-analytics-journal/${random.uuid}`，不同上下文独立；真实验收的 `DynamicPropertySource` 仍可覆盖为自己的专用目录。测试默认关闭 P6Spy 装饰。
2. 连接故障继续指数退避；数据约束和 SQL 结构错误改为每五分钟复查。失败事件仍保留，不把外键改成 null，不伪造成功确认；其他事件继续正常投递。
3. 同一异常类型、SQLState、约束在一分钟内只打印首条详细错误，之后输出省略数量汇总。失败指标仍逐条计数；退避期间、正常恢复和关闭时也会输出待报告汇总。
4. 首条错误保留 requestId、eventId、SQLState、约束、固定诊断说明及分行异常类型/项目调用位置。不会访问任意异常消息、SQL 绑定值、原始审计 JSON 或凭据。
5. 控制台仅过滤审计后台线程的 P6Spy INFO/DEBUG 明细。业务 ERROR、P6Spy WARN/ERROR 及其他线程的 SQL 诊断继续保留。正常事件成功时不再每次输出“恢复成功”。

涉及代码：`AuditEventDelivery`、`AuditFailureDiagnostics`、新增 `AuditFailureReporter` 和 `AuditSqlLogFilter`，以及 Logback 配置和测试默认属性。没有修改业务 SQL、数据库结构、身份权限、前端契约或正常业务接口。

## 本机历史测试记录隔离

使用 `scripts/analytics/isolate-test-audit-journal.ps1`，先只读检查匹配数量，再按确认的 471 条执行。工具限定 TestActors 固定测试租户、未确认状态、UUID 文件名及仓库内绝对路径；移动前复核哈希和 ack，并拒绝覆盖已有目标。

原始事件已原样保存在：

`services/api/data/analytics-journal/quarantine/test-fixtures-20261002T120901Z-790047f092ba487492f054e98ec15afa/`

目录中 `manifest.json` 记录文件名和 SHA-256，`completed.json` 记录完成数量。471 份哈希均匹配；隔离后检查时，活动目录未确认数量为 0，已经确认的业务记录继续保留。隔离目录仍随 journal 永久保留和备份，不属于构建产物，也没有自动清理。

这是本次已核实测试污染的运维处理，不是将未来所有失败事件自动移出队列。其他环境只能先 dry-run、核对来源和数据库事实，再明确指定本轮匹配数量；不要复制本机数量直接处理未知事件。遇到中途停止时按 manifest 检查已经转存的文件，原始数据在源或目标目录内保留。

```powershell
# 仓库根目录；默认只输出匹配数量。
./scripts/analytics/isolate-test-audit-journal.ps1
# 来源和数据核对后，再显式指定本轮匹配数量执行。
# ./scripts/analytics/isolate-test-audit-journal.ps1 -Apply -ExpectedCount <已核对数量>
```

## 回归验证

- 修复前新增的三个回归均失败，分别复现测试路径缺少隔离、四条相同错误打印四次、约束错误在连接故障的短间隔后再次尝试。
- 修复后定向回归覆盖文件恢复、幂等确认、磁盘/数据库故障、长退避与分钟汇总边界、安全日志、测试目录隔离、客户端采集和管理员 401/403。
- 本机真实 PostgreSQL 验收、聚合查询、登录及受控 HTTP 并发测试共 32 项通过。数据库夹具事务回滚，测试关闭 Flyway；并发上游为本机受控模拟，不调用付费模型。
- 最终定向回归 7 类 38 项通过，含隔离记录不再被重启扫描重放且原文保留；加上兼容性回归，共 12 类 70 项，失败/错误/跳过均为 0。按完整包名与本轮报告修改时间核对，排除 `target` 内残留旧包报告，不累计红绿阶段重复执行。

最终命令在 `services/api` 执行，测试 JVM 使用受限内存；真实数据库组统一关闭 Flyway：

```powershell

mvn -q "-Dspring.flyway.enabled=false" "-DreuseForks=false" "-Dtest=AnalyticsLocalDatabaseAcceptanceTest,AdminAnalyticsQueryDatabaseTest,AdminAnalyticsAggregationRegressionTest,AuthenticationIntegrationTest,ModelConcurrencyHttpIntegrationTest" test
```

本机执行另加 `MAVEN_OPTS=-Xms32m -Xmx256m -XX:MaxMetaspaceSize=128m -XX:ActiveProcessorCount=2`；定向组 argLine 限制为 256 MB 堆、160 MB 元空间、2 个处理器；兼容性组为 384 MB 堆、192 MB 元空间、4 个处理器，并设置已确认的本机 `jdk.net.unixdomain.tmpdir` 工作区路径。配置只作用本轮测试命令，没有修改运行服务的 JVM 配置。

测试 JVM 首次因本机原生内存不足未启动，改为显式限制堆、元空间和处理器数后执行。定向回归中发现并修正测试断言选中了启动 WARN、路径断言依赖不存在目录两个测试问题；保留失败证据，不算作生产行为通过。

## 生效与验证边界

当前 9000 端口的已有进程没有被本轮停止或替换。磁盘转存不会自动清除旧进程已经加载的内存队列，需重新编译并重启后端使修复和新的启动扫描生效。

重启后查看管理员投递状态：`pendingEvents` 应回落，`corruptFiles` 应为 0；不存在其他故障时应为 `HEALTHY`。已有应用进程的重启后控制台尚未现场复验，不能把本轮自动回归当作该进程已经恢复。归档的历史测试记录不会被计为成功入库的业务事件。
