# 模型并发真实压测（2026-10-02）

## 1. 结论

**当前本机环境下，真实直接增强链路已验证可以承接 50 个同时进行的上游调用，同一账号最多 3 个请求的限制生效。** DeepSeek Flash 和 Pro 分别达到真实在途峰值 50，两组各 50 个增强请求全部成功，且均在前端现有 70 秒等待时间内返回。

这个结论针对本轮短提示词、无文件上传、单 API 实例的短时并发峰值。尚未验证持续数小时保持 50 并发、大型项目上下文、Map-Reduce、Embedding、Plan 全流程并发或目标生产服务器；不能据此宣称所有业务场景已经通过正式上线验收。

本次按用户明确授权执行付费测试，没有修改生产业务实现、既有模型密钥、读取超时、输出预算或 50/3 限制。独立测试实例使用随机端口；现有 9000 服务未重启，测试后健康检查仍返回 200。

## 2. 实际测试链路

测试使用当前源码启动真实 Tomcat，通过 HTTP 执行：

```text
独立测试账号 → CSRF / 图形验证码 / 密码登录 → 平台增强接口
→ 账号并发限制 → 真实业务编排 / 上下文与权限处理
→ Redis 全局并发计数 → api.deepseek.com 真实生成
→ 四要素校验 / 必要的结构修复 → PostgreSQL 提交历史 → HTTP 返回
```

模型供应商、增强编排、数据库连接池和历史保存均未替换成 Mock。测试仅读取本轮图形验证码的生成结果来完成正常登录，不跳过验证码、密码或 CSRF 校验；禁用测试实例中的开发账号初始化器，防止接触既有账号。请求入口是 API HTTP，不经过浏览器或 Vite，因此不属于前端渲染和代理性能验收。

两种实际调用 ID 为 `deepseek:deepseek-flash` 和 `deepseek:deepseek-v4-pro`，平台显示名称分别为 `DeepSeek-V4.1-Flash`、`DeepSeek-V4-Pro-0813`。所有成功响应的 `provider.mock=false`。显示版本名来自平台模型目录，不等同于独立核验了上游内部模型版本。

使用 51 个独立账号；账号上限测试另建同一账号的三个登录会话。测试场景为例会纪要、学习计划、读书会筹备、登录表单测试方案和用户访谈五种合成短提示词，循环提交，不上传真实用户资料和项目源码。

环境：Windows，Java 21.0.12，12 个逻辑处理器，测试 JVM 最大堆 4028 MiB；真实 PostgreSQL 16.14，本机 Redis 3.2.100。数据库连接池沿用 10 个连接，模型连接超时 3 秒、读取超时 60 秒、最大输出预算 10000 Token，未为通过测试放宽参数。测试 JVM 使用工作区临时目录绕过本机 JDK 短路径问题，未改系统 Java 设置。

## 3. 实测结果

以下时延从 HTTP 请求发出到完整业务响应收到，包含认证、模型等待、内部结构修复和历史提交；不包含事先登录及后续历史查询。P95 表示 95% 的请求在该时间内完成。

| 模型 | 同时提交 | Redis 在途峰值 | 最终成功 | P50 | P95 | 最慢 | 结构修复重试 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Flash | 20 | 20 | 20/20 | 6.15 秒 | 13.01 秒 | 14.97 秒 | 3 次 |
| Flash | 50 | 50 | 50/50 | 5.98 秒 | 14.21 秒 | 16.31 秒 | 6 次 |
| Pro | 20 | 20 | 20/20 | 5.53 秒 | 10.25 秒 | 10.62 秒 | 4 次 |
| Pro | 50 | 50 | 50/50 | 5.43 秒 | 11.76 秒 | 12.96 秒 | 12 次 |

- 单账号三个真实登录会话同时增强，三个请求成功；第 4 个会话返回 HTTP 429 / `USER_MODEL_CONCURRENCY_LIMIT`。
- 每种模型达到 50 个在途调用后，从另外一个账号提交第 51 个请求，均返回 HTTP 503 / `MODEL_CONCURRENCY_LIMIT`，没有发送给上游。
- 满载时健康检查分别为 5 ms、3 ms；完成后单请求恢复测试分别为 4.16 秒、4.19 秒，均成功。
- 两组 50 并发共 100 个成功响应均具备非空优化提示词和完整四要素；通过各账号历史列表核对，分别新增 50 条已提交历史记录。
- 50 ms 间隔采样未观察到数据库连接池等待。两组 50 并发的 JVM 堆使用峰值分别约 98 MiB、105 MiB，平均 CPU 使用约 0.30、0.28 个逻辑核心。堆使用不等于进程总内存，CPU 包含同一 JVM 内 HTTP 驱动的开销；这些采样值不用于推导生产服务器最低规格。

主负载运行约 104 秒（含账号准备等步骤），每个并发等级是一次同时起跑的请求波次，不是持续固定并发的长期稳定性测试。两次 Maven 执行均退出 0，真实验收测试各 1 项通过，无失败、错误或跳过。

## 4. 重试与费用观察

合计提交 **152 次增强业务请求**：149 次完成真实模型增强，3 次按预期被平台并发控制拒绝。149 次最终成功不表示 149 次均首轮生成成功。

主负载中有 **26 次 `INVALID_RESPONSE`** 触发已有的结构修复机制，全部在第 2 次模型调用成功；预检没有重试。推算实际发送的模型 HTTP 调用为 **175 次**（149 次成功调用 + 26 次格式无效调用）。满载拒绝还产生两条 Provider 日志中的 `UNEXPECTED`，它们对应本地 `MODEL_CONCURRENCY_LIMIT`，不是 DeepSeek 调用失败。

没有观察到上游 429、网络超时、最终结构校验失败或非预期的用户可见失败。结构修复仍然增加时延和费用，尤其本轮 Pro 50 并发有 12/50 个请求发生修复，应持续观察该比例。

成功响应已报告输入 **262714 Token**、输出 **122004 Token**。当前日志未保存 26 次格式无效响应的用量，因此这些数字不包括全部计费用量，不能据此给出准确总费用。没有读取账户余额或将 API Key 写入证据。

## 6. 复现

此测试默认跳过；只有明确授权付费调用后才能启用。凭据由现有服务端环境注入，禁止写到命令行、报告或仓库。它只允许本机 PostgreSQL 地址，并使用独立随机 schema。

在 `services/api` 下执行：

```powershell
# smoke 每个模型一个基线请求；load 增加账号限制与每个模型 20/50 并发。
mvn -q -s ../../.mvn/settings.xml `
  '-Dtest=RealModelConcurrencyAcceptanceTest' `
  '-DrealModelConcurrency.enabled=true' `
  '-DrealModelConcurrency.stage=load' `
  '-DargLine=-Djdk.net.unixdomain.tmpdir=E:/MyProject/prompt-optimizer-platform/services/api/target -Dfile.encoding=UTF-8' `
  '-Dmaven.test.redirectTestOutputToFile=true' test
```

测试为了保留迟到响应的证据，HTTP 驱动总截止时间为 240 秒，但通过条件仍要求每个业务请求低于前端的 70 秒。服务端的 60 秒读取超时没有调整。其他 Windows 环境应替换临时目录路径。

当前 50/3 配置可以作为本轮已验证的短时峰值边界继续使用。目标部署环境上线前，需用相同方法复验实际机器，并补充长上下文、Plan 和持续负载；本报告不替代这些尚未执行的验收。
