# Plan 决策范围修复与下游执行复验（2026-10-04）

## 1. 当前结论与证据边界

本轮已实施跨对象误去重、错误冲突关联、部分重复提醒、常规问题分流、取消规则误拦、任务模板污染及安全阶段计时的修复。最后候选还补修了选项元信息中的新条件误删、原文明确未决项被空数组隐藏、地区状态错误候选、直接增强补回重复及脱离问题的旧待定状态。

**代码回归通过不等于全部业务验收通过。** 实际下游作品仍有篇幅违约、算式错误、伪代码时序遗漏和阅读负担，不能宣称增强在所有任务、所有模型、四个维度上都显著优于原文。正式专业评审、完整目录流程和全量跨行业门禁继续保持 PENDING。

可携带材料见 [本轮证据目录](./evidence/plan-decision-remediation-2026-10-04/README.md)。仅包含合成需求、主动提供的合成材料、真实接口输出、下游作品、公开调用元数据与 AI 辅助评分；不包含认证 Cookie、CSRF、登录 Session、模型密钥或服务端端点。首轮失败及中间候选均保留，不用后续成功覆盖。

## 3. 接口与复制契约

增强请求、Plan 确认和四要素段落契约保留。唯一新增的业务展示字段是 `OptimizationResult.evidenceCards`：

| 字段 | 默认与取值 | 用途 |
| --- | --- | --- |
| `evidenceCards` | 缺失或 null 规范化为 `[]`；前端字段可选，兼容旧响应 | 已过滤且与任务相关的来源证据，供结果面板展开核对 |
| 元素 `id` | 已有卡片标识或文档补充标识 | 用于展示关联，不是授权凭据 |
| `category` / `origin` | 沿用 `PlanningFactCategory` / `PlanningFactOrigin` | 区分事实类型与材料用途；测试例不能据此变成业务实现 |
| `sourcePath` | 安全相对路径，最多 256 字符 | 能定位主动提供的合格资料；不按此路径读取本机保护文件 |
| `evidence` | 非空、最多 220 字符的已核对摘录 | 核对推荐或执行规则，不接收密钥等凭据 |

`optimizedPrompt` 仍是唯一原生复制正文；四要素和必要未决前提来自同一份 `sections`。提醒展示上限与全部执行前提分别处理，不以只显示八条为理由静默删除其他未决条件。编辑、复制、撤销状态和再次增强契约未更换。

## 6. 真正发现的作品质量问题

1. **新闻篇幅仍不稳定。** 六份新闻正文按事先明确的汉字口径计数，五份不足600汉字，仅一份约663汉字满足600–800；不能选择包含英文、标点和标题的计数方式改判。部分增强组还漏掉MVP或长期资料保留边界。
2. **原文作品也会严重错误。** 教学原文Flash的一题先给“4/9＜2/5”，计算又证明“4/9＞2/5”。两份增强作品没有同一算式错误，但这不证明所有教学输出已可靠。
3. **伪代码与文字承诺不完全一致。** 初批开发作品虽提到迟到响应，但详情 `await` 后仍缺少身份/请求版本再次核对；取消恢复不明时点快照也可能回滚用户编辑。需要明确代码级验收，不以文字说“已保护”判通过。
4. **研究 Plan 仍可能扩大或重复表述。** 两个复合未决点被下游拆成多行重复参数，或附加不必要的候选方法要求；“1200字”的计数口径未澄清，字符数与汉字数应分别列出，不能宣告全部篇幅通过。
5. **正文冗余尚未消除。** 展开证据已减少内部元数据，但模型仍会在背景、任务、验收多处复述一份规则；为保证保真而补回的原句也会增加长度。全面压缩仍需逐规则覆盖验证。
6. **最后补验仍有实际执行缺陷。** Plan作品中的 `applyField(target, source)` 检查 `target` 是否在字段名白名单，却传入字段值；合成例目标为空字符串、来源为非空合成值，结果仍为空。另有作品在文字承诺区分状态，伪代码却归为无匹配或不返回解释列表。部分方案还把接口字段名、请求生命周期和提示位置退回给用户确认。这些是下游实际作品的新失败，不等同于平台重新生成了确认问题；需逐阶段判断优化正文是否漏规则或执行器违反已有规则。

上述问题应分别归因：优化器省略/扩大规则，执行器不遵守已明确规则，或评审口径未定。不能看到下游算错就直接认定 Plan 合并失败；也不能看到一次更高评分就宣称“增强一定有效”。

## 7. 延迟与故障定位

已增加 `context.analyze`、`provider.total`、每次 `model.upstream`、`model.validation` 与 `result.assemble` 安全计时。字段只包含 requestId、稳定阶段、公开模型、状态、耗时及索引诊断，不记提示词或资料正文。

一个34秒级失败回放中，上游三次约12.8、9.1、11.2秒；上下文约19毫秒，结果组装约240毫秒，主要等待来自上游请求与重试。HTTP计时包含网络和响应处理，不等同于纯模型推理；组装嵌套在校验阶段中，不能把嵌套时长再次累计。单例不足以给目标规模p95或判定上下文检索永远不是瓶颈。

O8最终生成的同请求服务端计时为上下文12毫秒、上游9164毫秒、组装539毫秒、校验541毫秒；组装包含在校验中，不应将两项相加再计算。浏览器总计11.186秒包含调度、协议与历史保存等其他开销，不能只按四项求和作为总时长。

本轮54次首批/补批执行中的24次网络失败仍保留。执行器已增加安全异常类型链，报告不会将缺少基线作品误记为增强获胜；这些属于诊断和评测可靠性修复，网络原因尚未证明。

收尾健康核查另有独立联调告警：`/api/v1/health`、liveness与readiness均为200/UP，总体`/actuator/health`为503/DOWN。服务端日志定位为`MailHealthIndicator`的`jakarta.mail.AuthenticationFailedException`；不是根据总体状态猜测Plan不可用。未读取或输出邮箱凭据，也未关闭邮件健康检查掩盖问题。该项应单独修复邮件服务认证配置并验证发信，不计为本轮Plan缺陷已关闭。

## 8. 尚待关闭的验收

- 最终候选按已开放Provider/模型运行固定轮次和独立保留用例；不是反复修到这四例成功即放行。
