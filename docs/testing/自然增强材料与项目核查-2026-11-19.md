# 自然增强如何把外部材料用于项目核查

## 对照资料

本次本地阅读《Qoder增强.docx》全部 16 组对照。原文有两组编号 13。下表记录可迁移的处理方法，以及采用时需要核对的边界。

| 原例 | 可用于增强的做法 | 应核对的边界 |
| --- | --- | --- |
| 1、7、8，地址编码、地区范围、审计字段 | 从界面上的值追踪到数据来源、配置和读写入口，据此回答“现在怎么工作” | 组件名、字段归属、账号与姓名的存储约定需要项目证据 |
| 2、3，多选展示、附件限制 | 把“好用”落到具体操作。多选后查看空间占用，合规与超限文件混选时检查各自结果 | 原文未指定单文件或总量时，保留该区别。移动端适配、新格式和更换组件库各自需要依据 |
| 4、10，按模板或截图生成文档 | 关联参考样式、生成位置和最终可见效果 | 保留模板位置、单位、空格及版式原意。未读到的图片字段不能当作已知 |
| 5、6、9，保存异常、两个界面问题、跨系统字典 | 让执行者沿实际异常和字段关联追踪，多个独立要求分别验收 | 保留对象名称和跨系统编码对应。候选根因需验证，不能先指定故障位置 |
| 11、12、两个 13，档案导入、审核恢复、日志恢复、规范治疗 | 交代记录选择依据、适用对象、字段覆盖、空值和完整业务条件 | 区分待核查规则和现行规则，保留“全部”与“必填”的差别。分析恢复方案和写入正式库需要分别授权 |
| 14，清理文档及文章优化 | 拆开两个目标，各自说明要完成什么和怎样判断效果 | 删除有明确前提。示例数和润色轮数不自动成为硬要求 |
| 15，短信签名 | 将通知转为项目适用条件，从接口调用查参数来源、比对有效值、按结果给出结论或修改建议 | 并列的新旧列表不能证明逐项映射。日期保持通知精度，部署覆盖值不能从代码默认值推定 |

## 失败定位与修复范围

截图中的提示词要求“只依据短信原文作答”，最终让下游缺少判断当前项目状态的依据。截图显示历史评测目录进入了检索结果，当次模型请求和完整片段清单未随截图提供。为定位增强环节，另用同构通知和合成工程材料复现，输入同时包含调用点、环境覆盖配置和历史演练记录。

自然模式由 DocumentOptimizationController 分发至 NaturalEnhancementService，再由 OpenAiCompatibleNaturalPromptProvider 进行范围识别和正文生成。自然服务将通过权限过滤的上下文、有效题答、按开关启用的对话和原始请求交给 Provider。旧版即使收到正确的工程片段，也曾在真实调用中把“需要改什么”理解为修改通知文案。来源校验可以验证引用存在，无法判断一个真实引用被用来回答了哪个问题。

新版在准备阶段分别识别用户委托、用作依据的材料、实际要判断的对象。正文阶段将材料中的定位线索与当前对象的检查步骤相连，有依据才写出具体文件。运行状态取决于外部配置时，只对相关结论保留条件。复杂任务可分段，明确的简短解释保留指定形式。编排沿用原有两个阶段，历史使用保存的策略版本。

## 第 15 例应达到的效果

以下是人工撰写的示范，路径和调用关系经过本地源码核对。它说明下游应做的工作，尚未检查任何部署环境的签名值。

> 根据下附通知，判断当前项目的短信验证码发送是否需要调整签名。沿 AliyunPnvsProvider.java 中的 sendSmsVerifyCodeWithOptions 调用，追踪 setSignName(properties.getSignName()) 的取值。核对 application.yml 中的签名配置及部署是否覆盖 SMS_SIGN_NAME，并留意不同环境是否一致。
>
> 将实际使用的签名与通知中的历史签名比对。仍用旧值时指出应调整的位置和验证办法，已经迁移时说明依据。仅知道配置键时，说清还需核实哪个生效值。新的签名应以该账号实际可用且适用的签名为准。此次交付影响判断和必要建议。

该示范应与实际通知一并交接。独立复制优化提示词时，应在正文保留接口名、日期、旧值和候选值等判断所需的信息。单独留下“见通知”会使下游缺少比对依据。
