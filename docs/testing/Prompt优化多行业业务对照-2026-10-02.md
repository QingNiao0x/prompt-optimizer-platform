本轮是 **API 层业务语义评测**。上传材料使用冻结的文本/代码节选，Plan 经过上下文准备、服务端计划绑定、实际回答、最终增强；两种模式共享同一材料包。确认后调用了前端 `buildRefinedContextQuery` 并保存查询，但最终仍提交同一固定材料集，因此**没有验证真实文件夹索引、浏览器二次召回命中率、办公文件解析、大文件性能、移动端交互或跨用户授权**。案例 ID 包含 retrieval 也不代表做过实际本地检索。

本项目资料仅显式选取 README、Plan 文档、PlanQuestionDialog.vue 和 optimizationRequest.ts 的相关节选。研究与股票材料明确为合成/拟定内容，没有读取真实患者、真实证券行情、账号凭据或受保护文件。

Plan 获得额外回答，直接增强未获得这些回答；本轮比较的是产品交互效果，不是等信息量模型能力。每例不是独立重复三次，补验也不是挑选最好结果；不计算显著性、业务准确率或线上 P95。评审为 Codex 定性复核，不能替代仓库要求的双人业务验收。未把生成的提示词交给下游 Agent 实际完成开发、论文或分析任务，因此“更可执行”是文本层面判断，不能声称已提高任务完成率。

## 2. 评测工具自身的校正

1. 首轮答案卡按关键词匹配，例如“ICD 编码范围”误匹配“地区范围”，“JSON 结构”没有命中“输出格式”。这是**评测工具错误**，不能归罪于模型。8 个受影响/需要精简的案例逐题核对后补生成，未提供的维度明确回答“暂不确定”，不自动采用模型推荐。对应旧、新答案与结果都保留。
2. 首轮项目资料正文前加了“资料范围：原文件第 N—M 行节选”。系统把不同文件的行号说明当作同名业务字段冲突。为消除包装影响，4 个项目案例使用原文节选复验，出处行号仅放在评测元数据。它仍是一条有效的元数据误识别反例，但不能拿来代表普通上传必然出错。
3. “完整地区需求必须零问题”的预设过严：原文只说“下级地区”，没有定义递归所有层级还是一层。该问题有价值；关于具体测试数据、可从实现核查的信息则应减少强制追问。本报告未按原关键词断言机械判分。
4. 本轮校正的是评测材料与答题方法，**没有修复平台业务代码**。首轮失败、校正后未重现和持续存在的问题分别记录。

今后优先使用 `prompt-comparison-reviewed.mjs` 的 collect / finish 两阶段流程。原关键词答题入口须显式加 `--allow-heuristic-answers`，只用于敏感性对照，不默认作为业务确认。

## 4. 影响可信度的具体发现

### P1：推荐不能仅靠词语出现

- 地区材料写的是“当前是否包含下级地区尚未决定”，Plan 却推荐“包含下级地区”，理由为“项目证据明确包含”。未知被误当支持依据。
- 原始需求要求“提示用户是否自动填充”，Plan 却推荐“直接自动填充……无需用户确认”。这是改变业务流程，不只是措辞差异。证据：场景 1 的 `fill_trigger`，首轮最终请求 `dfef6aae-ea03-4ec5-b241-05cfe3fbaf09`；推荐来自该份记录中的 Plan。
- 新闻稿明确面向“开发者、科研工作者和学生”，Plan 仍问招募范围，并推荐排除开发者的“科研工作者和学生”。证据：场景 15 的 `recruitment_scope`，Plan 请求 `c7c2d84b-152a-495a-9bd5-3a4f66a767d8`。
- 通知场景原文同时列邮件和站内信，并未表达偏好，推荐理由却仅用“原始需求明确包含：邮件通知”。

本轮使用独立回答而非自动选择推荐，所以最终结果可以正确，并不说明推荐安全。应比较**完整命题**：主体、动作、对象、条件、否定、量词及范围；“出现某词”“尚未决定”不构成推荐依据。无充分依据可无推荐，不能删掉真实选项或替用户作决定。

### P1：问题和候选项仍可能突破已明确约束

- 新闻稿受众和三项亮点已明确，仍要求再次选择。
- 普通用户指南明确不展示内部参数，候选项却允许面向开发者加入实现细节。
- React 迁移范围是多选，“全部页面”和“仅核心页面”可同时选，存在互斥关系。
- 多记录基线的字段清单在材料中已有证据，却仍问是否只填这些字段。

建议将关键缺口、可选风格偏好、执行时可查事实分开。已知信息只摘要展示；允许补充风格但不强迫逐题确认；候选集合必须服从原始需求和上位约束，互斥值使用单选或显式校验。

### P1：已知/未决/重复提醒仍混用

- React 补验中同时出现“该问题尚未确定：现有前端的鉴权行为具体是如何实现的？”及带解释的同一问题。请求 `f1390083-52a2-40c0-8eca-7bd4b0b3249b`。
- 福建科研补验中，寿命表以绑定问题、规则提醒、模型改写三种形式同时出现。请求 `b0eca26f-f1de-49aa-baec-720a36b4c77e`。
- 法律清单已经确认“高、中、低”，最终仍出现“本次排序按哪个字段、采用什么顺序”。请求 `07bf716b-4c9f-42fa-9e2e-ede84ff6a0ac`。

“暂不确定”后保留真正未决问题是正确行为；问题在于重复表示或领域不符。建议以绑定问题和具体决定主题归并，把新增说明附在同一事项下；新取值、新来源冲突、新业务条件仍保留。不能用 Plan 已确认就清空全部歧义的方式修复。

### P1：否定约束干扰任务分类

统计审计案例只是说“不得把测试样例当作真实业务事实”，两种模式却返回 `TESTING`，并出现“测试可重复执行”等验收内容；业务正文仍是设计报告，造成结构内部不一致。文档/新闻任务亦落到 `FEATURE_DEVELOPMENT`，首轮有不适用的功能测试验收。

需要按用户要交付的对象和动作分类，将引用、否定约束、附件描述与主任务分开。验收标准应针对报告、指南、新闻等交付物；不移除平台权限红线。

### P1：有出处仍可能是无关事实

订单接口首轮 Plan 最终结果插入 `docs/旧研究方案.txt` 的“研究范围：浙江省”，与订单汇总无关；直接增强正确指出附件无关。请求 `bf588b83-c79b-4dea-ba90-59cb0b9b8901`。逐题校正后同一材料未再出现该事实（`df6297b3-1434-45cc-8fe0-3ec3b817793e`），说明输出对确认表达敏感，**不是已稳定修复**。

新闻稿和普通用户指南则被补入内部 `planId` 规则。该规则真实、有来源，但对写作任务价值低。建议区分“时间范围”和“研究地区”等决策类型，按任务主体、文件用途和规则作用范围核对，二次检索与最终事实追加使用相同相关性规则。

### P2：元数据冲突、委托设计与冗余

- 行号说明被当成业务冲突说明来源元数据与领域事实需要隔离；不同文件的章节、页码和范围不能因同名标签直接判冲突。
- 论文场景本来委托 Agent 设计量表/统计方案，部分追问和最终提醒仍要求用户先给出这些设计，增加反复操作。应分清用户必须决定的研究目标与可以交付给 Agent 的设计任务。
- 已确认答案在背景、任务和独立答案区重复出现；通用约束有时又完整重复一遍。压缩重复时要保留来源、决定和权限红线，不能以删信息换简洁。

## 5. 已看到的有效能力

- 真正存在两份阈值冲突时，Plan 主动确认，并保留“严格大于”及等号边界；本例未再次生成旧阈值待确认项。
- 通知选择影响最终任务，站内信的已读状态和用户隔离被保留，邮件的重试规则未变成站内信执行规则。
- 科研数据字典里的地区、CSV、R 和分组能被使用；不是每次都机械问数据格式、技术栈。
- 教育问题与学生基础、教学重点、活动形式相关，最终落实两层练习和无需多媒体。
- 翻译和合成股票两个完整需求均为零问题，证明系统不要求所有需求都提问。
- 本项目代码审阅结果引用到 `previousQuestion`、`draftAnswers` 和 `isGenerating`，没有要求把已有功能全部重做。
- 新闻与论文结果保留 MVP/假设招募/研究未执行等边界，未捏造用户量、实验结果或 P 值。

这些是具体样例证据，不是跨行业准确率保证，也不证明当前所有模型版本都通过。

## 6. 耗时与交互成本

本表来自主比较选取的 17 对输出。Plan 耗时为上下文准备 + 提问 + 最终生成的 HTTP 耗时之和；复核暂停不计入，不是用户从点击到拿到结果的总耗时。单机、串行、小材料，顺序与服务端缓存未完全控制。

## 7. 下一步与关闭条件

| 顺序 | 工作 | 可核验关闭条件 |
| --- | --- | --- |
| 1 | 修复推荐与选项约束 | 地区“尚未决定”不推荐；确认前填充不推荐；三类受众不推荐缩成两类；互斥范围不能同时选；真实有证据的推荐仍可用 |
| 2 | 修复资料用途 / 主题 / 冲突作用域 | 订单不注入研究地区；正文出处信息不当业务冲突；测试任务仍能读取测试资料；真实同业务字段冲突仍被发现 |
| 3 | 修复跨领域分类与歧义归并 | 设计报告不因否定测试词变成 TESTING；法律风险不触发编程排序；同一未知问题可归并，新冲突与子条件不能丢失 |
| 4 | 精简完整需求和委托设计的交互 | 已知受众、格式、范围不重复问；可选偏好不强制；任务明确交给 Agent 的设计项不要求用户先设计完成 |
| 5 | 同版本重新业务验收 | 固定运行服务端构建标识、Provider/模型、任务和答案卡；每例独立重复至少 3 次，全部首轮与失败均归档 |
| 6 | Qoder 对照与双人盲评 | 补齐用户原生增强输出；另做三组同确认信息对照；两位评审独立判分、记录分歧，不能用本报告代替上线门禁 |

建议下一批采用五个用户指定行业各 6 例（完整需求、关键缺口、已知事实、冲突材料、无关/测试资料、长材料规则各一例），30 例 × 每组 3 次独立重复。先预注册原始任务、来源事实、答案卡和硬失败条件；对需求保真、证据相关性、逻辑一致、交付可执行性、提问价值分别按 1—5 分盲评。比较以任务配对，分别报告各领域差异、分歧和不确定性，不把同一任务的多次输出当作完全独立样本。

要验证“让 Agent 更好干活”，还需增加下游执行阶段：相同 Agent/工具权限/预算，软件用隔离夹具和行为验收，文稿用事实与格式盲审，科研用可复现方法检查，股票用合成数据可核对的计算结果；优化平台本身仍不执行用户任务。

**当前结论：已能生成有用的结构化提示词，关键决定型任务中 Plan 有清楚收益；尚不能宣称 Plan 全面优于直接增强或 Qoder，也不能据此正式上线放行。**

```powershell
# 冻结合成案例；准备本项目/多行业节选时添加 --industry

```

答案文件格式：

```json
{
  "case_id": {
    "question_id": {
      "question": "与服务端返回的问题文本完全一致",
      "answer": "从预注册答案卡或明确输入中得到的回答，未知则写暂不确定",

  }
}
```

脚本仅访问本机评测地址，文件写入采用不覆盖模式，校验冻结样例摘要及问题绑定，使用正常浏览器会话，未保存登录 Cookie/密码/验证码。每次模型调用会产生真实的本地优化记录与统计事件；本轮没有删除这些记录、执行迁移、修改平台业务代码或提交 Git。

Qoder 请按压缩包的《操作说明.md》操作：每例独立工作区，显式选择相同资料，运行原生增强并保存第一个完整输出、失败、版本与耗时。不要把平台输出或答案卡提前喂入此基准组；同信息量对照另设组。输出包补齐后再做三方盲评，不能把之前单张截图当成本轮 17 例的 Qoder 结果。
