# 动态平台约束显示与真实验收（2026-10-08）

## 1. 范围与完成条件

本轮只调整优化提示词中的固定“平台强制约束”块：代码任务及明确交付可运行辅助代码的任务显示五条，非代码任务仅显示事实边界一条。任务规则、明确的用户权限、资料限制和未决执行条件仍保留。服务端敏感值检测、文件过滤、身份认证、Plan 所有权、租户与工作区隔离不随显示内容减少而关闭。

本轮实现、编译、相关回归和最终六场景真实接口验收均完成。首轮真实验收发现的否定交付问题修补后，已用同一组输入和同一否定答案重新验证；首轮失败与最终通过的证据分别保留。这是本项变更的定向验收，不替代全平台上线验收。

## 2. 原因与实现

- 原组装器把固定规则、工程要求和用户权限平铺进同一个平台块，无法保证五条／一条的固定数量；前端编辑补回也会把任务规则重新追加到平台块。
- 新增内部不可变 `ConstraintBundle`，区分 `platformMandatory`、`taskSpecific`、`additionalPermissions`。公开 API 仍返回原有 `appliedConstraints` 数组，没有新增请求字段或数据库迁移。
- `TaskIntentResolver` 继续作为唯一共享任务判定入口。主目标结合有效 Plan 答案决定是否交付代码；上传 Java 文件、仅选择 R 作为分析工具、引用代码以及尚未决定是否交付代码，不单独启用代码条款。必要伪代码也不自动等同于可运行代码。
- `ConstraintCompleterImpl.completeForTask` 一次生成分组规则；编排交给 Provider 的扁平规则与结果使用同一份内容。研究附带脚本保留研究主任务，不套用背景 Java 工程的全部开发规范。
- `OptimizationResultAssembler` 在业务保真、冲突处理和普通文本压缩之后追加固定平台块。`PlatformConstraintRenderer` 只清理完整匹配的已知规则；引用、代码块、表格和未知业务条款保留，再次增强也不会把旧平台模板反向当作新业务目标。
- `constraintEditing.ts` 按服务端原结果的来源分组补回 `appliedConstraints`，不在前端重新推断任务类型。
- OpenAI 兼容 Provider 的指令明确由服务端维护固定块，模型负责本次业务限制；不能用这种展示调整规避任何服务端安全校验。

### 2.1 真实测试补出的边界

真实 Plan 生成的问题为“本次交付是否包含可运行的 R 脚本？”。用户答案“本次交付不包含可运行的 R 脚本，仅提供中文报告和空表”在模型正文中被正确理解，但旧分类器只检查句首否定，仍将“交付……脚本”作为肯定交付，导致错误显示五条并追加辅助代码规则。

修补后识别交付物作主语的否定表达，并按子句判断肯定交付。“不提供 Python 代码，但提供 R 脚本”仍启用五条；“提供不超过 30 行的 Python 代码”中的数量限制不被误判为否定。不改变研究主任务、明确的数据限制或其他未决条件。

## 6. 验证边界

- 这是动态固定条款和相关流程的定向验收，不是全平台上线放行或所有开放领域的语义准确性证明。
- 任务分类仍有规则边界；本轮不能证明任意措辞、任意语言都能正确识别。
- 模型有时会在业务约束中改写重复的安全要求。固定块数量与原文由服务端保证；本轮没有实施开放域语义删除，避免误删用户的真实业务限制。
- 历史旧记录不批量重写。前端编辑和撤销以 Store 回归为依据，不能将其写成完整页面点击／剪贴板／移动端验收。
- 安全校验与隔离未因显示逻辑减少而关闭；相关回归通过不等于本轮重新执行了完整安全渗透或生产压力测试。
