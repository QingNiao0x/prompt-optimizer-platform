## 未通过项与代码定位

### BA-01 / P1：词面命中不能作为“最优答案”依据

- 订单资料明确要求“超过五万元时必须先由财务复核”，系统却推荐“大于等于五万元”。推荐理由仅引用“五万元时”。按照推荐项构造夹具答案后，最终任务写成 `>= 50000`，而背景仍保留原来的“超过”。
- React→Vue 场景中，Vuex 4 和 Ant Design Vue 的推荐理由仅为原始需求包含 `vue`。这不能证明它们优于其他兼容选项。此处并非否定这两个库本身，而是没有足够证据支持唯一推荐。
- 科研样例也出现仅由“年龄”等词面匹配支撑方法推荐的情况，不能据此判定该方法是当前数据的最优方案。

代码定位：`PlanRecommendationAligner.align` / `tokens`。选项与需求/上下文的词面交集被赋分，最低证据阈值为 1，无法表示比较运算符、适用范围、当前事实与未来偏好的区别。

修复验收：保留 `>` / `>=` 等边界；推荐必须对应可验证的决定依据，没有充分依据允许不推荐；同一框架名称匹配到多个候选项时不能声称其中一个最优。确认用户主动变更规则时，应明确显示其与原材料的差异。

### BA-02 / P1：带出处的错误资料仍会污染最终结果

统计日志场景首轮抽取 16 张卡片，全部来自 Provider 内部提示词及事实提取策略代码，包括 `FREE_TEXT 必须为 true`、只返回 JSON 等要求。最终背景继续附加这些卡片，并追加 Qoder 调研里的单次处理不超过十万行、引用 SRE 文档等无关内容；合计占满 24 张最终事实预算，另提示 23 条事实超限。

这些片段在原文件中的出处是真实的，但不属于本次统计日志需求的业务规则。**不能把“源码文件中的字符串”直接等同于“当前任务必须执行的规则”。** 本轮未观察到测试中的 CSV/Python 字符串直接成为最终事实；已有测试用途过滤仍有作用，但未解决内部指令字符串与无关文档的问题。

代码定位：`PlanningEvidencePolicy.origin/allows/relevant/overlaps/evidenceLines`、`PlanningFactCardExtractor`、`OptimizationResultAssembler` 的事实保留路径。来源类别和词面相关性不足以判断片段的用途、作用域及约束对象。

修复验收：分别标注业务实现、配置规则、内部模型指令、示例和调研；提取时绑定约束对象与任务目标；保留源码审查这些内部指令的能力，但统计业务设计时不能把它们提升为约束。核对最终关键统计实现证据不再被无关规则挤出。

### BA-03 / P1：自然语言确认没有稳定解除旧冲突

- 原样例回答“本次以新审批方案中的五万元阈值为准。”后，仍保留三万元/五万元冲突。
- 同样的材料，用标准选项“本次采用：五万元”可消除旧冲突。
- 新增八万元时有警告，但比较的是三万元与八万元，而不是优先对照已经确认的五万元。
- 回答暂不确定时，服务端、模型与未决回答合并出了同一阈值的 3 条提醒。

代码定位：`ConfirmedDecisionSet.selectedValue/resolves` 的固定文案和字面取值解析、`ContextConflictDetector` 的取值对选择，以及最终按文案合并歧义的逻辑。

修复验收：优先使用服务端绑定的问题/选项/事实 ID 解析确认；自定义答案不能只依赖“本次采用”前缀；同一决定按主题、对象、作用域和证据合并。新冲突与已确认值比较，无法确定自定义答案含义时继续澄清，不自动吞掉真实冲突。

### BA-04 / P1：跨领域语义被通用关键词规则误判

法律写作样例已经指定普通租房者和按风险等级排序，Plan 仍询问目标读者；回答后最终新增“数字、文本或业务记录”“按哪个字段、什么顺序”等编程式排序歧义。

代码定位：`AmbiguityDetector` 的“排序”分支没有任务领域限定；`PlanQuestionFilter` 不能覆盖该种已知受众表述。本项评估的是问题相关性，没有对法律内容作专业结论。

修复验收：先理解本次排序对象及已给定的顺序，再决定是否存在真实缺口；为非软件排序任务和明确目标受众增加正反例，避免全局屏蔽真正未决的排序规则。

### BA-05 / P1：否定句中的“测试”改变了任务模板

统计审计需求包含“不得把测试样例……当作业务事实”，Plan 和最终结果模板却为 `TESTING`。模型生成内容仍大体围绕统计设计，不能把这个现象夸大为输出全部跑题，但模板路由确实错误。

代码定位：`PromptTemplateRegistryImpl` 优先按“测试/test/覆盖率/用例”等关键词命中，没有区分主要目标与否定约束。

修复验收：以实际交付目标决定模板；覆盖“设计统计模块，不把测试样例当事实”“开发功能并补测试”和真正测试任务的区分。

### BA-06 / P1：问题选项的逻辑关系和事实推断缺少校验

React→Vue 的范围问题允许多选“全部页面”“仅核心页面”“增量迁移”。前两项互斥，第三项是实施方式，无法组成同一维度的有效多选。最终文本还把没有证据的 React Router 写成已有实现。另一阈值案例因只上传方案文档，就推断需要从零开发；没有读到代码不代表项目没有代码。

代码定位：Provider 的提问/增强生成与 `OptimizationPlanningServiceImpl` 的问题结构校验；格式合法并不保证候选项互斥关系合理，模型指令也未形成充分保障。

修复验收：把迁移范围与迁移策略拆成独立问题，校验单选/多选的兼容关系；未提供的依赖和实现状态只能写为待核查或条件分支，不能作为项目事实。

### BA-07 / P2：检索排序存在业务覆盖量缺口

前述真实统计场景两轮都用满 120,000 字符，测试与内部指令代码竞争预算，关键 Mapper XML 未召回。通知的 2 块极小预算对照中，邮件答案先召回邮件代码与站内信代码，邮件配置没有入选；站内信答案则召回站内信代码与配置。这说明答案会改变检索，但不是稳定的完整覆盖。

代码定位：`projectIndexer.ts` 的任务词、符号和依赖排序；当前分数没有充分区分业务目标与材料用途。2 块为本轮刻意压缩的边界条件，不是生产默认参数。

修复验收：按任务类型调整实现/测试/文档预算，补足 Mapper 接口与 XML 的依赖关系；以预期关键事实召回率验证。不能简单屏蔽全部测试文件，测试任务仍须可检索测试材料。

### BA-08 / P1：现有自动门禁同时存在误报与漏报

原翻译例期望最终提示词包含“早上好”“大家”，实际产品正确生成了用于翻译的提示词，没有直接执行翻译，导致该断言失败。另一方面，BA-01、BA-03、BA-04 等严重业务缺陷仍能通过原关键词断言。

代码定位：`scripts/plan-quality-eval.mjs` 的 `finalTerms` 和 `evaluateQuestions` 等检查。

修复验收：按“生成提示词，不直接执行任务”的契约修正翻译断言；增加比较符保真、推荐依据、自定义确认、冲突去重、互斥选项与跨领域相关性断言。不能降低业务标准或把已有 10/11 记录改写成全部通过；新门禁需重新执行真实模型评测。

## 复现与后续顺序

准备本地正常运行的 API 与 Vite 前端，在仓库根目录执行：

```powershell
$env:PLAN_EVAL_BASE_URL = 'http://127.0.0.1:5175'

```

该入口打开临时 Chrome，由操作者完成正常登录和验证码，随后运行原 11 个合成样例并保存独立证据目录；使用真实默认模型，会产生正常模型用量和优化历史。入口不会修改模型配置、扫描本机目录或绕过认证。

本轮额外 8 次结果通过同一脚本导出的 `createAcceptanceSession`、[固定业务夹具](../../scripts/plan-business-cases.mjs) 和浏览器实际索引 API 编排完成，**不包含在上述默认 11 例 CLI 中**。对照时复用同一个有效 Plan，在 `finish` 中分别传入标准五万元、自定义五万元、暂不确定、新增八万元文件、仅代码文件或不同通知答案；React→Vue 使用独立 Plan。真实仓库场景需按相同基线、安全文件清单及 120,000 字符/40 块预算再次建立浏览器索引，不能用手写文件列表替代真实召回证据。

后续建议按以下顺序修复并重跑失败场景：

1. BA-02＋BA-07：先保证选入的事实与真实任务相关，改善业务实现覆盖率。
