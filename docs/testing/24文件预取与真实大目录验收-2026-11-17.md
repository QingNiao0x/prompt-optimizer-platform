## 实现与受影响验证

`FILE_PREFETCH_COUNT = 24` 与 `FILE_READ_CONCURRENCY = 6` 分开控制。六个读取者填充 24 个槽位，结果按来源顺序交给消费者，处理当前组时准备下一组。每份小文件不超过 64 KiB，因此预取组最多 1.5 MiB，当前组加预取组最多 3 MiB；这只是字节缓冲，整个 Worker 还包含正文、词表和待写数据。

大文件保持流式处理。未变化、受保护及被排除文件继续在预读前处理。暂停状态持续有效，迟到的预取结果不会变成新的写入。写入仍串行，原子检查点与按已提交状态显示的进度继续生效。

63 项相关单测、Chrome 与 Edge 各 11 项浏览器检查通过，覆盖预取领先量、最大六路读取、暂停与恢复、600 份多根文件的全文和尾部、进度、存储隔离、迁移、覆盖与回滚。类型检查和生产构建通过，构建保留既有依赖注释和大产物提示。工作台业务 HTTP 与身份使用受控夹具，Worker 和浏览器数据库为生产实现。

## 新发现的问题与后续方案

1. 估算量达到 2 GiB 后，大量文件转成仅元数据，根 README 的正文也无法命中。下一步应核对估算计量、真实占用及浏览器配额的对应关系，制定有依据的容量策略；完整词表、正文和隔离继续作为必须保护的内容。
2. 处理完成与正文完整需要在状态和说明中明确区分。当前 READY、100% 表示本轮范围处理结束，容量降级后的缺失正文仍需显式保留未完成状态，不能据此宣布全项目索引完整。
3. 未满预算时的完整功能回归已通过。真实大目录需在容量问题解决后，重新冻结版本和范围，用同等完整正文开展连续多轮对照，并比较稳定性、内存、暂停恢复及检索结果。不能仅凭本轮耗时较短关闭验收。

## 验收工具问题与原件

首次测试没有取得目录句柄。定位到独立浏览器配置位于待导入目录内部后，将配置迁到系统临时目录，取得了真实句柄。早期拖放失败原件保留，不计实际索引轮次。

基线索引完成后的顺序全文核验耗时偏高，保留已提交数据库，恢复浏览器配置后改为六路并行核验全部已保存正文。索引耗时沿用已完成的原轮次，核验时间独立计算。旧候选连接中断及恢复原件同样保留。最终清理了本轮遗留的独立临时浏览器配置，真实用户浏览器资料未参与清理。
