# 未决交付一致性与 Plan 质量收尾（2026-10-07）

## 1. 问题与实施范围

上一节点的真实科研作品出现：正文说跨字段一致性分母尚未决定，指标表却填入“两日期均格式合法的有效出院记录数”。这是下游作品的业务选择失真，不是仅有提醒重复。用户实际只确认完整性分母，不能将该确认传递给一致性指标。

本节点在既有增强与 Plan 链路增量修复，不修改 API 字段、数据库、索引策略或模型调用预算。平台继续只生成提示词；真实作品由隔离的验收工具调用模型生成，平台不执行用户任务，也不能承诺任意模型都会服从提示词。

实施顺序为：先将未决状态绑定到交付要求，防止正文、表格与伪代码相互矛盾；再补医院提醒的有限换写归并；最后核对明确问题重问及推荐证据的作用范围。每一项均加入相反边界，避免依靠宽泛关键词删掉其他对象的问题。

| 模型修复 | `PromptOptimizationGuidance.ENHANCEMENT` 与 `RULE_CONFLICT` 说明同一未决决定应在全部交付形式保持未决 | 复用既有修复次数，不增加独立模型调用；不能靠正确尾注保留错误口径 |

| 医院提醒精简 | `PlanAmbiguityMerger` 核对唯一绑定事项后规范短核查语句及已知另一院窗口禁止句 | 原需求命名且拥有独立窗口问题的另一院才可归并；新院、新年份和条件不移除 |

| 跨题说明归属 | 同院同年覆盖度未知时的比较处理说明回到已有独立处理项 | 覆盖度状态不等于比较策略；其他年份及新条件不能借“该年”吞并 |
| 示例值指代 | “该示例值”仅从同一道绑定回答的唯一明确示例解析 | 不从另一题借数字；新的90分钟示例值保留 |
| 同项确认复写 | 完整参数已作为未决项登记后，不再附写同一“请确认状态／口径” | 原绑定对象及年份参与判断；条件下的请求、退款分母、新年或另一院继续保留 |
| 低价值追问 | `PlanQuestionFilter` 不追问已规定的确认框／弹窗形态，及已有明确四要素的假设阈值冲突呈现 | 独立权限、覆盖行为、实际具名取值冲突及用户主动要求选形式仍保留 |
| 推荐依据 | `PlanRecommendationAligner` 先核对具名对象及年份，再检验证据及同段审批限定 | 另一机构或年份不背书；保留原段落而非人为切开审批说明。当前真实明确选择及另一业务对象的未知不能被误取消 |

正确的交付示意：

| 指标 | 分母 | 状态与执行边界 |
| --- | --- | --- |
| 完整性指标 | 本次实际回答确认的有效出院记录 | 已确认；仅适用于完整性指标 |
| 跨字段一致性指标 | 待确认 | 确认前不计算该比例，不填入惯例或示例分母 |

伪代码可以声明未决参数和等待状态，不能设置临时默认口径后输出貌似真实的比例。与该参数无关的字段检查、缺失标记和已确认指标继续完成。

## 5. 新发现、剩余范围与下一步

1. 合法零值、费用负数处置规则已知，不代表每个衍生指标的纳入分母也已经确定。提问若新增这类参数，保留并限定回答范围；不能用“原文提过该字段”一概删除。
2. 本次有限语法不能保证任意行业、任意换写或任意模型均正确；HTML／复杂合并表格、英文专业参数及任意伪代码的形式化验证仍未覆盖。具名参数中的“一致性指标”与“跨字段一致性指标”尚会同时出现，须按完整对象与决定关系精简，不能靠类别相同就合并。
3. 实际作品的准确性、完整性与目标篇幅独立验收，API 成功和参数格修复不代表增强在四项质量上全面优于原始。新实证包括格式指标被写为已确认、直接增强作品仍赋予一致性具体口径及条件句被下游当作当前事实；优先校验确认范围及来源状态，不能以增加一个同义词过滤规则宣告所有模型通过。
4. 正式门禁继续覆盖新闻篇幅、资料归属扩展、完整目录／办公材料、编辑复制历史、性能与独立基础业务评审。专业人员核验按用户安排上线后开展，但上线前合成专业场景的真实模型测试继续执行。

下一步先依据最终作品关闭有证据的反例，剩余失败逐项记录，再扩大未参与修复的跨行业对照；本节点不执行生产部署或宣称正式上线通过。

## 6. 模型能力与平台责任的归因边界

`OptimizationPlanningServiceImpl.plan()` 先经 `resolveForPlan` 取得已分析的上下文，组装需求、安全摘要、当前模型和资料归属指导，再调用 `planValidated`。平台对模型候选执行格式、安全、保真与决定策略校验；`PlanQuestionFilter` 过滤有限范围的已知或低价值问题，必问的资料冲突由平台补入，再对推荐依据校准后注册计划。模型负责候选问题的语言理解与专业推断，平台负责输入、绑定、有限过滤与补充；过滤器不能自动恢复模型遗漏的所有必要问题。

`DefaultEnhancementOrchestrator.optimize()` 校验服务端绑定计划及模型一致性，以有效答案构建二次检索词，复用或分析上下文，再检测歧义、合并首次与新增事实及冲突，选定任务模板并补约束。`enhanceValidated` 生成结果，组装与校验共享既有最多三次上游调用预算。当前Plan与最终增强绑定同一 `modelId`，临时换另一模型会要求重新Plan；不是现成的“Plan用强模型、增强用便宜模型”独立路由功能。

OpenAI兼容适配器实际发送 system／user 消息，JSON模式、模型温度、输出预算及思考配置参与调用。JSON可解析和结构校验通过不等于业务事实正确；有限保真规则也不等于跨行业专业解释器。模型能力、输入资料覆盖、指令冲突、确认范围和输出预算共同影响结果。换更强模型可能改善复合条件理解，但无法恢复平台未传入的资料，也不能自动纠正错误合并的事实。

当前平台只交付提示词；下游执行在产品之外，由本轮验收工具另行调用。归因必须先核对增强正文是否保留了对象、参数状态、来源和必要交付，再检查两组执行是否有相同资料、系统指令、模型版本、预算、工具与未截断结果。若增强正文正确而执行忽略其中限制，可记录为该次执行模型的遵循失败；若正文已经将未知改成已确认，应先归为平台或增强模型缺陷。不能仅凭文字更专业就断言“提示词已高质量”。

后续建议分开测平台事实／状态正确率、Plan必要问题与重复率、增强保真与精简、下游实际作品四类指标。先固定增强提示词更换执行模型，再固定执行模型更换增强模型，并保存中间输入、模型版本、首次失败和多轮输出，才能逐步区分影响。已有充分需求允许少改，评测目标是关键规则不退步且代表性任务总体更可用，不强求所有原文每次改写都显著提升。

官方依据：[OpenAI提示工程指南](https://developers.openai.com/api/docs/guides/prompt-engineering)说明不同模型类型及同系列快照会表现不同，并建议固定版本和建立评测；[模型优化指南](https://developers.openai.com/api/docs/guides/model-optimization)要求用代表性真实输入持续测量。上述建议是结合本项目代码作出的工程推论，不是对本轮两个DeepSeek型号的通用能力排名。
