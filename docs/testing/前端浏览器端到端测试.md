# 前端浏览器端到端测试

## 测试目的

`apps/web/e2e/prompt-workbench.spec.ts` 使用 Playwright 验证用户在真实浏览器中的工作台操作。测试拦截 API 并返回固定数据，不连接真实模型，也不消耗 Provider 额度。

工作台需要分别覆盖默认直接增强和用户主动开启的 Plan 路径。Plan 路径的核心断言包括：

1. 有文件时先出现上下文发送确认；
2. 请求顺序为 `/context/planning → /optimizations/plan → /optimizations`；
3. 计划请求只携带 `contextId/version`，不重复携带文件正文；
4. 最终请求携带 `planId`、同一上下文引用和全部回答；
5. 用户回答完成后再次确认最终选中的上下文；
6. 最终页面展示结构化段落，不再展示待确认事项。

直接增强路径的核心断言包括：

1. 首次访问时 Plan 默认关闭，按钮显示“直接增强提示词”；
2. 不调用 `/context/planning` 和 `/optimizations/plan`；
3. 有文件时只按原始需求检索并确认发送一次；
4. 最终请求使用 `templateCode=AUTO` 和 `planConfirmation=null`；
5. 结果允许显示 `ambiguities`，再次增强按钮明确显示“直接再次增强”。

首次主动开启还需验证说明弹窗的接受、拒绝和刷新后偏好保持。用例应自行通过 `localStorage` 配置初始状态，不能用全局 `beforeEach` 强制开启 Plan，否则会掩盖默认路径。计划会话过期用例先模拟最终接口返回“确认问题已过期”，再关闭旧问题弹窗、重新点击“先确认并增强”，断言新 `planId` 能完成最终生成。

## 本地运行

先安装依赖和 Playwright 浏览器：

```powershell
cd apps\web
npm.cmd install
npx.cmd playwright install chromium
```

运行桌面 Chrome 项目：

```powershell
npm.cmd run test:e2e -- --project=desktop-chrome
```

运行移动端项目：

```powershell
npm.cmd run test:e2e -- --project=mobile-chrome
```

Playwright 配置会自动启动 Vite 预览服务。若已有相同端口的旧服务，先停止旧进程，避免测试连接到过期构建。

当前工作台用例会在同一站点来源下操作 IndexedDB 和浏览器私有文件系统（OPFS），并验证页面重新打开后的清理行为。`playwright.config.ts` 因此固定使用一个 worker 串行执行，避免多个用例同时争用本地索引和页面懒加载资源；接口 Mock 仍由各用例独立注册。

## 上下文时序测试写法

测试为三个接口分别注册路由，并用数组记录调用顺序：

```ts
const order: string[] = [];

await page.route('**/api/v1/context/planning', async (route) => {
  order.push('context');
  await route.fulfill({ status: 200, json: planningContextResponse });
});

await page.route('**/api/v1/optimizations/plan', async (route) => {
  order.push('plan');
  expect(route.request().postDataJSON()).toMatchObject({
    planningContext: planningContextReference,
  });
  await route.fulfill({ status: 200, json: planResponse });
});

await page.route('**/api/v1/optimizations', async (route) => {
  order.push('final');
  expect(route.request().postDataJSON()).toMatchObject({
    planConfirmation: {
      planId: expect.any(String),
      planningContext: planningContextReference,
    },
  });
  await route.fulfill({ status: 200, json: optimizationResponse });
});

expect(order).toEqual(['context', 'plan', 'final']);
```

开启 Plan 且有文件时会出现两次发送确认。第一次的操作名是“生成确认问题前分析上下文”，用于让后端产生安全摘要；第二次的操作名是“生成最终提示词”，用于发送根据答案重新检索的上下文。关闭 Plan 且有文件时只有一次“直接增强提示词”发送确认。测试应按操作名定位对应弹窗，再点击“确认发送”，避免退场动画期间命中错误按钮。

## 常见失败定位

| 症状 | 检查位置 |
| --- | --- |
| 点击增强后没有计划弹窗 | 先确认 Plan 开关已开启；有文件时再检查 `/context/planning` mock 和第一次发送确认 |
| 计划请求缺少上下文引用 | 检查 `preparePlanningContext()` 是否成功保存响应，以及 `buildOptimizationPlanRequest()` |
| Plan 零问题测试卡在弹窗 | Plan 仍会进行第二次发送确认，需要再点击一次 |
| 直接增强意外调用计划接口 | 检查测试是否残留强制启用 Plan 的初始化脚本，以及 `continueEnhancement()` 的分流 |
| 点击 Plan 开关超时 | Element Plus 的原生 `input` 不可见；点击可见的 `.switch-control` 标签，再对 `role=switch` 断言状态 |
| 最终请求缺少回答 | 检查 `PlanQuestionDialog.vue` 的 `confirm` 事件和 `generateFinalPrompt()` |
| 本地目录测试没有召回文件 | 等待索引状态为 `READY`，并检查 IndexedDB 测试数据和查询词 |
| 全量并发测试偶发找不到页面 | 确认 Vite 预览端口没有旧进程，使用核心控件出现作为页面初始化条件 |

更完整的业务与接口说明见[内置 Plan Mode](../12-内置Plan-Mode交互与接口.md)和[上下文感知 Plan Mode 实现教学](../development/上下文感知Plan-Mode实现教学.md)。
