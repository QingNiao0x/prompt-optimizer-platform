# 提示词增强与 Plan：最小必要干预、实施顺序与上线验收

本文集中维护提示词增强与 Plan 的开发原则、实施依赖和验收要求，适用于后续开发与 AI 会话；这些要求不代表相关能力已通过验收。协作入口见 [AGENTS.md](../AGENTS.md)，产品介绍与使用说明见 [README](../README.md)。

当前完成状态、调用预算、未完成项及最新节点统一见[当前待办](./待办事项.md#current-enhancement-status)，源码版本、模型原件与实际作品见其中链接的评测报告。先核对已有证据。待办只供查阅；未关闭的门禁不授权开工，只做用户本条消息交办的任务。不因下方历史评估重采已完成组合，不放宽有效校验、挑选有利评审或借旧作品关闭新候选门禁。

> 历史评估说明：第 2 节保留 2026-10-12、源码基线 `12fbf90` 的核对结果，其中“当前”指当时版本。该次综合修订只评估源码与既有真实记录，没有修改业务代码、重新调用模型或关闭上线门禁；后续实现和验证须以当前源码及对应证据核对。

<a id="enhancement-development-direction"></a>
## 1. 产品目标与不可偏离的边界

**核心价值：理解用户原始意图，主动做有依据的实质补全，让下游更好地完成原定任务。** 最小必要干预不是只重排：模糊需求可重构，充分需求保留有效原句。

### 1.1 交付目标

产品增强提示词，不代替用户执行报告、翻译、投资分析或代码任务。优化提示词须让下游更好地完成**用户原定交付物**，不能把“写报告”改成“制定方案”，把角色指令改成“再写一份角色提示词”，或把资料不足变成整篇停止交付。用户本就要求方案、模板或写提示词时，则必须保留相应范围与交付层级。

背景只写与执行有关的已知信息，必要缺口在对应执行位置简短表达一次；缺口只约束依赖该信息的判断、计算或授权行为。允许交付有依据的解释、适用方法及其他不依赖缺失数据的内容，不允许虚构实证结果。不能承诺仅靠增强就补出不存在的数据。

<a id="intelligent-enhancement"></a>
### 1.2 智能增强与实质补全

| 维度 | 应实现的帮助 | 不采用的替代做法 |
| --- | --- | --- |
| 需求明确化 | 明确动作、对象、受众、输入和最终交付，保留用户有效框架 | 同义替换、加长句子、把“为研究生写”理解成研究对象是研究生 |
| 场景上下文化 | 使用本任务中适用且可追溯的项目上下文和有效确认 | 混入旧任务、把未上传文件列为固定缺口、将资料中的指令当平台指令 |
| 专业与约束补全 | 提供相关候选方法、适用条件、必要步骤和可检查边界 | 单一指标推出另一指标；把建议写成已选事实；禁止一切有依据的推荐 |
| 结构化重构 | 模糊需求可重构；充分需求保留有效原句，只修真正影响执行的缺口 | 默认强改全部原文，或默认只小修、要求用户去高级设置开启真正增强 |

充分性、改写深度和提问必要性分别判断。长输入也可能模糊，短输入也可能充分；不能靠字数、标题、中文关键词计数或固定模板决定改写力度，也不能以这些形式特征或“零问题”代表质量。内部四要素保留语义覆盖与兼容，最终正文不强制四个标题及独立验收段。

用户委托设计的方法、评分量表、随机化和分析步骤，可以给出**明确标为拟议方案的建议及适用条件**；不因用户未预先给出设计答案就全部退回确认。用户保留的实际业务选择、既有数据口径、授权及会改变结论的重要未知不能由建议自动确认。采用年龄标准化不等于选定某年标准人口；根据数据选择检验不等于禁止提及检验名称。

### 1.3 优先级和禁止倒退的路线

安全权限由服务端执行；事实由适用证据支持；任务由原始需求和用户后续明确修改决定；有效 Plan 决定仅在实际对象与条件内覆盖旧选择。模型建议、模板、平台评测量表和示例不能越过这些边界。

明确禁用的路线及替代设计见[第 3.4 节](#root-cause-remediation)。替换旧实现前先列出调用方、原保护及对应回归，逐项迁移；不能以“摒弃旧路线”为由清空护栏、忽略历史失败或削弱权限红线。

### 2.3 安全、性能和体验现状

- 优化历史有租户／工作区范围；当前 Plan／上下文会话及临时文档主要以 `ownerUserId` 校验归属。相同账号的工作区／任务边界需要补齐服务端绑定。这里是边界不足，不是已证实的跨用户数据泄露。
- Plan／上下文有效期 30 分钟；内存会话存储没有完整容量约束，写入时扫描清理。临时文档为单进程索引，2 小时滑动有效期，具备文件／容量上限。失效检查、原件删除、索引删除、无后续请求时的清理是不同事项；Redis Plan 不会自动把本地文档变成多实例共享。
- 默认本地索引配置叫 `SESSION`，但符合条件的文件分块正文、元数据及目录句柄会写入 IndexedDB，默认清理参数是 7 天。它与“默认不持久化源码”意图存在差异；不通过改文案扩大保留许可。页面清空、不申请持久存储、实际擦除不是一回事。
- 增强适配器将改写策略同时放入 JSON 输入与 system 指导，增加重复；组装链也有多次扫描和追加。模型调用通常是长耗时来源，但尚无足够分段负载数据证明各项贡献，先测再优化。
- 单次生成的格式／业务修复共享至多三次尝试；不是整个 Plan 工作流最多三次。前端 HTTP 超时为 70 秒，旧请求失效目前不等于网络与供应商任务取消。长请求的预算、取消及并发槽位释放需一起设计。
- 重算既有候选五的 28 次增强 HTTP 记录（没有新请求），Flash／Pro 各 14 次：p50 约 2.75／2.66 秒，p95 约 15.93／23.24 秒。用最近秩计算，因样本少 p95 等于各组最大值；不含用户答题时间，不代表 Plan、多用户、长材料或主线程性能。
- 未保存草稿已有保护，实际发送范围可见；仍缺原始／当前版本比较、界面撤销及再次增强的独立原始基准。耗时阶段、取消后费用状态和跨标签页资源状态不应依靠用户猜测。

## 3. 目标逻辑与逐步替换方案（以下待实施，除非单列已实现）

### 3.1 怎样决定补全、保留还是提问

| 情况 | 处理方式 | 例子与边界 |
| --- | --- | --- |
| 当前任务中已有适用证据 | 直接使用，记录来源与适用范围，不重复问 | 项目实际使用 Java 21；用户明确研究中国，不能继续问国家。旧项目／引用材料的地区不能套给新任务 |
| 用户委托的方法设计或普通执行细节 | 给有依据的推荐、适用条件和必要替代路线；明确是拟议执行方案 | 要求“设计评测”时可建议量表、随机化与复测办法；不得写成用户已选、已实施或已获得结果 |
| 只有用户能定且实质影响质量的选择 | **Plan 必须提问**，解释不同答案将改变什么；可给建议但不预选为确认 | 发布对象、真实地区、授权范围、不可逆行为、实际分母／已用口径、相互矛盾且无权威依据的来源 |
| 不影响主要结果的组织习惯 | 合理组织，允许编辑，不增加必答问卷 | 普通邮件分段、标题措辞、用户已委托的表格呈现方式 |
| 事实或数据确实缺失 | 不补造；局部说明“无法从现有资料推断”及判断所需最少信息，继续其余原定交付 | 有收入数据可算同口径增长率；无市场规模／份额口径或销量／价格证据，不能断言份额／需求变化 |
| 真实来源冲突或确认出现新条件 | 保留各来源，定向提问，不静默择一 | 不同年度机构同名指标不能合并；确认一个方法不能连带确认标准人口 |

“影响质量”须能解释答案如何改变交付、结论、输入处理或权限；不以模型未校准的置信度当概率。题目中既有普通展示问题又有真实业务选择时，拆分或保留实质问题，不能整题关键词删除。

直接增强尊重用户不开 Plan 的选择：重要未知在界面可见，并在复制正文中局部约束相关步骤；提供转入 Plan 的入口，不强制把整份任务换成问卷。用户明确“先问再写”时保留该要求。Plan 用户回答“不知道”时，展示可理解的候选及影响，记录未知或待选；不能伪造确认。确实没有重要问题才跳过问答。

### 3.2 共享任务视图与变更依据

沿用当前 `EffectiveTaskView`，不重新建立平行识别器或一次改造全部 API。先覆盖高风险要求，逐步增加：

1. **任务身份**：服务端用户／租户／工作区，加本次任务、材料及有效要求的版本。任务标识只用于关联，不能代替鉴权。
2. **原始基准与有效意图**：原始提示词、用户后续明确修改、当前稿分开；动作、交付物、执行者、受众、研究对象分别表示，模型自行添加的内容不升级为用户要求。
3. **证据与要求**：稳定 ID、来源类型（用户要求／绑定确认／适用资料／模型建议）、原文位置或摘录、对象、属性、机构／年份／版本、条件、否定、比较符、数值单位和状态。不存在与未说明必须分开。
4. **决策与依赖**：题目及有效答案、作用范围、被取代旧选择、依赖的资料／段落、仍未决子项。完整待决集合与本轮展示题目分开。
5. **改动清单**：实际缺口、补充或替换位置、理由和依据。充分需求优先局部修改；模糊需求可重构，但必须解释新增内容服务哪个目标。该清单供校验和可展开说明，不整份塞入复制正文。

模型同次返回的缺口和改动清单是候选解释；用输入锚点、有效题答、显式数值／否定／格式和实际作品交叉验证，不能把“模型自称已保真”作为放行依据。无需为每次增强再串联多个在线裁判。

### 3.3 Plan、检索与冲突闭环

流程为：适用安全资料 → 有效任务视图 → 识别完整重要待决集合 → 分批展示问题 → 服务端绑定实际答案 → 更新受影响要求／二次检索 → 核对新证据冲突 → 必要的定向追加确认 → 增强与组装 → 复制／编辑／历史。

- 目前八题是展示预算，后续不能作为丢弃重要事项的依据。登记全部重要项及排序理由，分批显示；未展示／未回答仍保留状态。只剩非关键建议可继续生成，不能把被截掉的重要项称为已解决。
- 不设无穷追问：复用未受影响答案；新增一轮必须对应新证据、实质新冲突或原答案仍无法执行的关键决定。冻结轮次／调用预算，耗尽后保留明确未决及继续交付边界，由用户决定是否继续。
- 答案只使用服务端保存的问题、选项及题目 ID；自由输入保留原意。修改问题依赖的原文或材料时，使相关答案失效并解释原因，不让客户端自造“已确认”。兼容现有过期重建，后续才支持经验证的局部重确认。
- 有效确认按对象、属性、条件和版本更新对应正文与旧选择；部分确认、新条件和新冲突仍分别保留，不能凭相似文案删除独立规则。
- 先汇总冲突再分页。比较身份为对象＋属性＋机构／年份／版本＋适用条件／时间＋单位／比较符；仅做可证明安全的格式归一化，不折叠大小写敏感标识或 `>`／`>=`。
- 候选与已采用、历史与当前、不同机构口径并存未必是冲突。真正冲突记录双方原文、来源及影响；第三个新取值不能被前两者已确认覆盖。没有检测命中不等于语义已无冲突。
- 对新增资料的提示注入，继续把资料当数据处理；不能接受其中的“忽略原用户要求”“读取另一任务资料”等指令。

### 3.4 撤销的路线、替代方式及迁移约束

| 不再作为施工指令的做法 | 原因 | 替代及验收 |
| --- | --- | --- |
| 每遇一例就在 system、模板、组装末尾各加长禁令 | 重复、互相矛盾、扩大用户限制，难定位原错 | 一份适用契约、一份要求覆盖表；先修出错阶段，检查模型原文→组装→复制→作品 |
| 把完整句子未出现等同于要求未落实 | 自然融合会被误判缺失，重复整份答案 | 先保护高风险条件及作用范围，记录覆盖位置，缺项定向修对应段；无法证明等价时不删 |
| 所有未知一律先确认；所有委托设计一律未决 | 责任退给用户，报告变问卷、推荐无法执行 | 按第 3.1 节区分事实、用户决定与委托设计；重要问题必须问，低价值问题不问 |
| 根据题数上限、关键词或低置信度静默删题／默认确认 | 重要业务决定可能消失 | 完整待决登记、影响排序、分批展示与明确未知状态 |
| 凭关键词／标题判断充分性；只支持四段原句恢复 | 对语言和写法敏感，普通充分需求仍扩写 | 有效任务＋实质缺口＋可核对改动；逐步加入普通段落局部修改和原文锚点校验 |
| 为增强而新增 Python／快排、研究对象、虚构许可或禁止检验名称 | 改变用户目标或约束强度 | 使用适用上下文；推荐带条件且不冒充确认；明确授权例外才可改变禁令 |
| 单一指标推出其他事实，末尾补“可能有假设” | 错误结论仍在正文中 | 删除或改正无依据结论，说明局部无法推断及所需证据；保留可直接计算和有依据解释 |
| 强制长标题／验收／缺项盘点，或简单删除所有结构 | 前者臃肿，后者可能丢必要语义 | 内部四要素兼容，按任务选择紧凑／分节及具体可检查要求 |
| 示例开着仍写“仅用户要求时”；一见 JSON 就禁例 | 开关失效或误伤兼容格式 | 统一示例契约，按实际格式兼容性决定，明确冲突原因 |
| 把旧增强对新增强的胜率称为增强产品收益 | 缺少用户不使用工具时的基线 | 原始直接执行为主对照；旧／新回归单列；Plan 使用同实际确认信息 |
| 不断采样直到通过，只报成功轮或平均分 | 掩盖严重退步、成本和随机性 | 修改前冻结判据，保留首次失败，有限迭代，任何严重退步阻断相关开放范围 |
| 靠前端清空实现隔离，或把发送称为已使用／理解 | 旧响应、服务端缓存和本地保留仍存在 | 服务端资源绑定和生命周期验证；仅承诺可证明的实际发送状态 |

上述替代是新方案，不等同已实现。每撤下一条专项护栏，都须保留其保护对象、反例和接替位置；授权、敏感过滤、隔离、逻辑删除不交给模型判断。

### 3.5 示例契约

2026-10-22“示例参考”开关及前后端实现已按用户要求退役。示例要求只来自原始提示词和实际题答，不再自动添加开关条款；下方历史节点中的开启／关闭语义不作为当前开发要求。

模型内部改写示范与下游回答示例分别处理。本轮三份完整内部示范仅用于NATURAL/12受控候选，与当前任务来源隔离，未作为默认采用；[真实对照](./testing/自然增强实质补全与内部示范对照验收-2026-10-22.md)尚未证明稳定明显收益。不能因建设内部示范恢复用户开关，或要求所有下游作品都包含示例。

用户明确要求下游示例时，优先用现有真实资料中适用的小例子；允许且有益时使用明确标记的演示输入／输出，但不能充当真实数据、实证结果或已确认参数。用户禁止假设／虚构数据时，不能自行新增“测试例外”；选择不违约的真实、符号或格式示范，无法兼容时明确说明。严格 JSON 的允许字段中可以有示例，不能任意增字段；纯译文、禁例或固定格式与示例确实冲突时，服从明确限制并在正文外说明。

来源事实、直接计算、条件说明分别判断。仅“标了虚构”不能解除用户禁令；用户并未禁例时，也不能为某个测试强加一律禁止数值示例的产品规则。

### 3.6 输出与编辑闭环

在现有 `COMPACT`／结构化协议上推进，不另起完整块编辑器作为前置条件：

- 充分自然段只改有实际收益的位置，保护句内否定、数值、截止范围和交付层级；允许无须改动。模型返回局部修改时检查来源锚点、范围重叠和硬约束，失配进入既有有界修复，不默默全篇重写。
- 简短邮件用紧凑自然语言，翻译保留行数／占位符／只输出译文等要求，严格 JSON 保留 schema 和禁额外输出；增强提示词自身不必假扮成下游 JSON。复杂报告沿用用户有效框架，再补必要步骤和验收。
- 内容只服务原定任务，不为凑标题增加交付、验收长段、缺项盘点或整份 Plan 答卷；有效题答融入对应执行要求。
- 组装只有一个最终职责：应用有效决定、补真正缺项、校验覆盖、呈现。逐步收敛契约的追加行为；安全约束、独立对象、例外和来源冲突不能因相似而丢失。
- 前端展示、复制、编辑、撤销、历史恢复必须由同一版本正文／格式产生。简短变化说明放正文外；必要执行依据、关键限制和实际未决仍随复制，不让用户还得手动补答案。
- 保留不可变原始基准、当前稿、用户明确新增要求及可选改进目标；再次增强区分用户编辑与模型建议。新增目标可更新有效需求，但保留来源；不把上轮扩写当用户已授权。需要重新确认的只限受影响决定。
- 编辑失败留全稿并定位错误，成功后才退出；接通已有撤销及前后比较。页面内存版本不冒充数据库持久化版本；未经另行设计不覆盖历史记录。

## 4. 安全、性能和前端体验的工程方案

### 4.1 上下文安全与保留策略

保留已实现的任务／身份版本隔离、实际发送清单、失败保稿、动态权限及敏感过滤；不为缓存或提速扩大材料使用与保留范围。

| 资源 | 后续实现与边界 | 必须通过的验证 |
| --- | --- | --- |
| Plan、上下文快照、临时文档和缓存 | 服务端绑定当前用户／租户／工作区及任务／材料版本；每次访问先鉴权再复用。旧缓存不兼容时明确过期重建 | 同账号换工作区／任务、异账号、伪造 ID、登出重登、旧请求迟到均不能读写越界；不宣称当前已覆盖全部 |
| 本地索引／草稿 | 纠正默认 `SESSION` 与实际 IndexedDB 保留差异；默认会话资料尽量内存化，确需跨页缓存须限定生命周期并如实告知；用户显式保留设置单独处理 | 刷新、关闭、到期、异常退出后的实际存储核对；升级不得静默清空用户明确选择保留的资料 |
| 临时源文件与索引 | 保留现有限额，补账户维度与全局容量、无访问时清理、失败重试和资源统计；滑动 TTL 与最大生存期分开配置 | 原件解析成功／失败均清理；索引到期不可读；空闲后物理回收；容量满明确拒绝，不静默挤掉有效 Plan |
| 多实例部署 | Plan 共享存储与文档本地存储分别设计；上线拓扑只承诺已经验证的能力 | 两实例切换、失效、所有权和删除一致；共享文档未实现则限制部署拓扑，不假称 Redis 已解决 |
| 历史与遥测 | 历史继续按租户／工作区和逻辑删除过滤；指标只记必要元数据，历史正文可能含资料衍生信息须告知 | 不输出密钥／完整用户正文日志；不采集用户材料作训练评测；新持久化字段使用前向 Flyway 和准确数据库注释 |

资料覆盖状态继续复用 P0 的“完整／部分／未发送／未知及原因”，绑定请求和资料版本，区分 Plan 准备与最终增强。预览取同一安全表示；“优先参考”必须有预算分配和未纳入提示，不能绕过敏感过滤或承诺模型已理解。缓存键包含适用范围、有效需求／答案、材料和安全策略版本；鉴权失败不能命中返回缓存。

### 4.2 性能与资源预算

先补齐流程标识和分段计时：浏览器索引、上传／解析、检索、过滤、Plan、二次检索、Provider 每次尝试、组装、历史保存、渲染／复制。记录输入规模、实际 Token、首次成功率、修复次数、p50／p95、峰值内存与拒绝／取消；嵌套阶段不得重复相加。供应商不返回用量标为未知，不虚构零成本。

优化按测量执行：去掉同一改写指导的重复传输；共用已验证解析结果，减少重复全文扫描；只有需求、答案、材料及安全版本相同才复用安全快照；二次检索不是一律删除。浏览器读取和解析在现有 worker 基础上做有界批次、背压；列表虚拟化等仅在长任务测量证明需要时引入。维持模块化单体，不为本轮质量任务拆微服务。

以下为**待实测的首发预算草案**，不是已达到的性能。ME-00 先冻结硬件、浏览器、模型配置、并发、材料和计时边界；若试测不合理，先记录原因并调整预算再冻结候选，不能在结果失败后偷偷放宽。

| 范围 | 首发目标与测量条件 |
| --- | --- |
| 短任务交互 | 固定桌面与移动测试环境，增强按钮／编辑／取消可见反馈 p95 ≤ 100 ms；8,000 字输入和既有结果的编辑／复制反馈 p95 ≤ 200 ms；不含系统剪贴板权限等待 |
| 平台自有处理 | 已完成解析、最多 40 片段／120,000 字符的请求，排除供应商等待与用户答题，平台阶段总 p95 ≤ 1 秒；不把上传／OCR 等额外工作藏进排除项 |
| 真实模型阶段 | 分模型记录；普通直接增强端到端 p95 ≤ 30 秒，复杂增强每个活动 HTTP 阶段 p95 ≤ 60 秒；现有 70 秒客户端超时前返回成功或可恢复失败，不靠无限延长超时 |
| 尝试与总调用 | 保留单阶段至多 3 次格式／业务尝试并加总时限；Plan 与最终增强分别计数，同工作流累计预算可见。用户答题时间不计运行超时；追加确认须独立计入，不藏在“重试”里 |
| 大材料与并发 | 固定 1,000 文件候选、单份 50 MiB 支持文档及 5／10／20 并发档分别测量，记录解析速度、主线程长任务、内存、拒绝率和费用；按真实容量选择开放并发，超出时明确限流，不无界排队 |

取消先确保不写回旧任务，再接入客户端中止、服务端协作取消和并发槽位释放；供应商未确认中止时注明可能已耗用，不承诺取消等于零费用。安全隔离和关键冲突不能为性能目标被跳过。大文件、过期、429、超时、断网后的恢复路径计入体验验收。

### 4.3 前端状态与兼容

沿用三栏、Pinia、Element Plus 和现有样式变量。围绕“编辑 → 解析／检索 → 待确认 → 生成 → 成功／可恢复失败／已取消”展示真实阶段，复用任务／上下文版本；不显示虚构进度百分比，不让旧阶段清掉新任务 loading。

Plan 明确说明每个重要问题影响什么，已回答与仍未决分开；更改资料／答案只重置实际失效部分，过期保留可恢复的用户输入但重新校验确认适用性。未保存草稿、服务失败和导航退出继续保护；跨账号／工作区清理旧任务数据。390／820／1440 像素、键盘操作、长题答、错误焦点和移动端复制都需验证。

兼容已有接口、四要素、格式与历史元数据。新增字段先可选且能读旧记录，公开模型 ID 与路由不混用；数据库使用前向迁移。新增模型／版本按自身质量和能力验收，不把 Flash 的通过推给 Pro 或其他 OpenAI 兼容供应商。

| ME-05-A 资源归属与保留 | 用户／租户／工作区／任务版本贯通会话和临时资料；纠正本地默认保留，容量与空闲清理，多实例边界 | 可与 ME-01-A 并行，依赖 ME-00 的身份基线 | 正常及越权矩阵、实际存储清理和多实例／限单实例配置验证；不修改历史删除语义 |
| ME-05-B 性能与状态 | 分段指标、预算、重复处理热点、取消、限流和真实阶段状态 | 先测 ME-00；优化后复验相关包 | 同工作负载前后 p50／p95／Token／内存与失败率，超时和恢复、负载及前端体验达冻结目标 |
| ME-06 最终冻结放行 | 固定代码／模型／协议，补跨行业、留出题、组合、同账号真实浏览器、全仓库及发布演练 | 上述相关开放范围各包通过 | 第 6 节 G1—G8 全部通过或明确缩小未验证开放范围；不能靠关掉关键问答来规避质量验收 |

<a id="remediation-priority"></a>
### 5.1 下一轮执行顺序与停止条件

1. **先固定证据与判据（ME-00-A）**：补原始直接作品和 Plan 公平信息流，冻结失败快照；重放已有保护。核对同一个测试账号，不重复注册。
2. **先修需求是否正确（ME-01-A、ME-03-A 首段）**：受众／对象、拟议设计／用户保留选择、事实推断和普通充分原文；并行规划 ME-05-A 的资源作用域，不能让共享视图扩大缓存范围。
3. **再贯通重要问答与正文（ME-01-B、ME-02-A/B）**：全量重要待决登记、准确冲突、确认融合、旧选择失效和示例一致；每包做真实定向作品，不等最终总测才发现错误。
4. **完成体验和资源闭环（ME-04-A、ME-05-A/B）**：复制／编辑／撤销／历史／再次增强、生命周期、取消与预算；已有 P0 样例持续回归，不重做已通过基础功能。
5. **冻结候选（ME-06）**：先定向通过，再扩到第 6 节全矩阵及留出题；固定同一候选，不混用不同修复版本的最好结果。

每个节点写出一个可证伪的根因假设、修改位置和验收；同一假设连续两个候选仍出现相同严重失败时，停止扩大采样，重新审查职责划分、评测工具和证据，不继续叠禁令。只暂停受影响能力的放行；按归因决定修公共路径、撤回策略或延期，保留失败与未验证范围，不自动围绕单个专业题继续开发，也不伪装所有功能完成。调用／费用预算在开跑前确认已获授权的范围；授权范围变化或预算不足时停止相应外部调用，已授权的独立工作继续。

<a id="acceptance"></a>
## 6. 上线前验收协议

### 6.1 对照对象、信息和模型控制

| 对照轨道 | 比较什么 | 能说明什么／不能混称什么 |
| --- | --- | --- |
| 产品收益 | 原始提示词直接执行 R0 vs 新直接增强后的复制正文 N0，各自生成实际作品 | 回答“不用本工具”与“使用本工具”谁更好；不是仅比较提示词长短或四要素 |
| 修复回归 | 旧增强 O0 vs 新增强 N0 的实际作品，同时看提示词变化 | 说明相对旧实现是否进步；不能替代 R0，也不能称为增强绝对收益 |
| Plan 同信息 | 原始需求＋逐字有效答案 R+、直接增强获得同样信息 D+、实际 Plan 复制正文 P+ | 隔离确认信息整合的价值；各组获得相同实际答案，评测器不得给 P+ 漏掉的答案补课 |
| Plan 自然流程 | 不追加答案的自然直接路径 vs 正常问答后的 Plan 路径 | 衡量提问带来的真实产品收益及用户负担；因信息量不同，不能称为同信息比较 |

同信息需要保存问题、逐字实际答案、来源、产生时间及各组接收的信息；不能用“同题”“都写有公平对照”代替。R+ 只附实际题答及必要归属，不偷偷加入增强后的推理和组织指导。用户未回答的事实不得由脚本替用户选定。

隔离改写价值时，各臂使用同一份安全资料快照、相同权限与可用工具、执行模型版本、参数、上下文及输出预算；输出上限须容纳原要求。另测端到端资料检索质量时，单列资料选取差异，不把信息不等的收益全归于改写。先固定同一执行模型比较，再用第二执行模型验证稳健性；增强模型与执行模型分别记录，不能同时换两者却只归因一方。

原始组每轮也实际执行，不反复复用一份幸运／失败旧作品。旧原件无法重放时仅作历史参考。随机顺序和匿名 A/B 标签生成后锁定，不修改失败样本；真实用户材料另需相应使用授权，默认用合成或已获授权测试材料。

### 6.2 样本、轮次与证据

- 沿用[实际交付闭环评测](./testing/提示词实际交付质量闭环评测.md)与[跨行业方案](./testing/Plan-Mode深度评估与跨行业测评方案-2026-10-04.md)的至少十二类：软件开发、项目／用户文档、翻译、新闻传播、教学、机关／企业报告、数据分析、研究生论文、医院管理、医学研究、法律、金融研究，各一份中等需求和长需求，共至少 24 个主场景。另加短邮件、纯译文、严格 JSON、纪要、开放创作、角色工作流、口语／错字与混合材料；充分／模糊需求分别核验。专业样例用合成或已获授权资料及核实证据评分。
- 中等需求约 300—800 中文字符，长需求约 2,000—6,000 字符，仅作采样区间，实际字符和 Token 分别记录，不变成产品长度限制。长材料另测文首／中段／尾部、冲突来源、旧版本、测试夹具和检索预算溢出，不能用长原始提示词代替长资料验收。
- 加入本节 6.5 的故障回归，以及直接／Plan × 示例开／关、无／长／冲突材料、正常与过期修改等覆盖矩阵；明确每个组合落在哪些代表题，不强制无意义的全笛卡尔积。
- 拟开放 Flash／Pro 至少三轮；区分重新生成增强提示词与同一复制正文重复执行。高风险案例两种波动都测，先制定请求数和费用上限，不将重试排除于成本之外。TokenHub 超时／截断修复继续按既有决定延期，不纳入本轮开放模型；新增路由或模型快照另过适用门禁。
- 至少 25% 主场景在调参前封存，不进入系统提示词、规则开发或试跑；本轮七题和此前八题均不再算未见题。封存题出现失败后可转修复集，但最终另补留出题。
- 冻结原题、旧输出、资料、有效答案、开关、账号／范围、提交及变更哈希、公开模型 ID／路由、参数、时间、工具版本和本轮预算。保存模型原文→平台结果→真实复制正文→下游作品，原件只读，错误解析和漏采明确标记。
- 答案卡预先写明关键事实、允许的设计空间、重要未知、硬约束及容差，不规定唯一完整范文；不能见到候选作品后再追加有利的规则或把平台测试量表当成用户研究已选量表。
- 文本类留作品，代码需编译／行为测试，严格 JSON 解析及 schema，译文核对行数／时间／否定，字数依用户语言口径独立计数；不能靠模型自报完成。超时、截断、失败请求计入完成率，不能从分母悄悄排除。

### 6.3 盲评、胜平负和阶段归因

两名独立评审先只看到用户原始要求、适用资料／答案和匿名作品，分别评价准确性、完整性、清晰度、可执行性。评审身份、模型／版本及是否 AI 必须披露，独立 AI 评审不能写成领域专家。再解盲检查提示词、平台组装和复制，定位错误发生阶段。

未来统一使用 **1—5 分**锚点：1 无法完成或严重错误；2 需大改；3 基本可用但有实质缺口；4 满足任务仅需小改；5 充分满足且表达精确。各维度分别评分，记录具体证据、用户还要改什么，不奖励篇幅和新增章节。历史 0—4 或其他评分不回算成同一量表。

- **胜**：增强作品在任务完成或至少一个质量维度有可指出的实质改善，其他维度无实质退步，且无新增硬约束违反。
- **平**：两边均满足任务，没有稳定、实质的优劣；不同文风不自动算胜。
- **负**：增强新增目标、事实、授权或硬格式错误，或造成实质交付退步；局部更流畅不能抵消。
- **双方失败**：两边都未达到基本任务或硬门槛，单列，不并入平。请求失败／未完成作品及评审待裁决另列，仍进入完成率分母。

先按用户要求和有效事实判断，再诊断平台新加约束。用户禁止假设数据却出现例外是严重保真失败；用户未禁止且合理标明的演示说明，不因平台随意扩大禁令就直接等同虚构事实。新增规则本身是否适当也是被评对象。研究建议不得冒充已选参数，符合授权的设计建议也不能因不是原句而机械判错。

分歧必须保留各自证据，交第三独立复核或人工裁决；无法裁决记未决，不挑更好看的一份评分。按题目而非请求数报告独立样本数，重复轮次单列，不把相关采样当独立统计显著性。按任务类型、充分性、模式和模型报告胜／平／负／双方失败、严重错误、完成率、修订负担、耗时和成本；均值／区间只作与样本规模相符的描述。

具体归因和策略处置须执行以下流程；判定下游违约不自动触发追加指导，也不免除对应作品的质量门禁。

<a id="attribution-and-strategy-evaluation"></a>
#### 6.3.1 精准归因与下游策略评估（跨会话硬约束）

本节适用于真实评测、根因分析、响应校验、增强／Plan 模型指导、模板与篇幅策略调整，以及为生成质量进行的性能成本优化。先明确缺陷归属，再决定是否修改；不把所有失败统称为平台缺陷或模型能力不足。

**先核对证据链。** 固定原始提示词、适用资料、实际问题与逐字答案、示例开关、源码／策略、增强与执行模型及参数，按顺序比较实际模型输入 → 增强原始响应 → 平台组装 → 可复制正文／历史 → 下游实际作品 → 评测判断。记录错误首次出现的位置、对应原句／字段、可能的诱因和证据范围。已有完整证据先离线核对；新源码不得借旧作品宣称验证通过。

| 归属 | 判定依据与必要核对 | 处理方式 |
| --- | --- | --- |
| 平台系统缺陷 | 平台指导、上下文选取、组装、确认融合、规则／作用范围或复制／历史路径引入遗漏、错误、冲突；也包括校验器错误拒绝合法响应 | 在已授权范围内修复对应代码；核对共享调用方，验证受影响路径与正反例，保留安全、权限、隔离、动态约束及既有交互 |
| 增强模型问题 | 模型原件已改变目标、引入歧义或违反响应协议；必须先检查它实际接收的指导和材料是否正确一致 | 若平台输入／指导或校验有缺陷，分别修复平台；其余评估局部指导或有依据的兼容适配，不静默删除重要歧义、伪造确认或放宽有效校验 |
| 下游模型问题 | 最终复制正文保留目标、事实、重要规则和有效确认；任务所需信息已在对应范围内充分且无冲突，实际执行仍发生违约、遗漏或幻觉 | 进入下述策略评估。单次作品只证明该次下游失败，不能据此宣布稳定能力不足或立即全局追加约束 |
| 评测工具问题 | 工具漏判／误判，错误计数，另补平台遗漏答案，改写输入、正文或作品，或把辅助脚本失败当产品失败 | 修复工具及必要派生结论，保存原件、旧判定和更正依据；不据此修改产品规则或挑选有利评分 |

错误首次出现的位置不等于唯一根因：平台指导可能诱发增强错误，增强歧义可能传给下游，模型原件与组装也可能分别出错。证据不能区分时记为**混合归因或未定**，列出缺少的证据；任何后续请求须在既有授权与预算内。Plan／增强阶段的无效响应尚无下游作品时，不能称为下游能力问题；正确响应被误拒绝时也不能只归咎模型。

**下游问题必须评估，但不一定修改提示词或平台。** 区分偶发失误、已有证据支持的稳定违约、资料不足和能力边界，记录影响、可行性及不干预的理由。资料缺失只限制依赖部分，不靠提示词补造数据；高风险失败仍保留，不因暂不采用策略而减轻其验收等级。

**按最小干预提出候选。** 先消除有证据的歧义、重复和冲突，再评估必要的局部说明、适用上下文或专业建议；保持用户原定交付及重要未知状态。每个候选列出一个可证伪的假设、目标指标、适用条件、最小变更、性能／泛化风险和撤回位置。不能围绕单个样本在 system、模板、组装末尾反复叠加禁令，不能无依据强制方法、增加交付、扩大删除范围或开启额外自检／重试。更换模型、增加工具或请求次数是独立策略，须单独归因且满足已有授权，不计为单纯提示词修复。

**验证收益及副作用。** 执行第 6.1 节的信息与模型控制；主要质量比较仍为原始提示词作品与当前优化提示词作品，旧／新策略另作修复回归，Plan 同信息与自然问答分轨。冻结每次变更及判据，避免同时更换多个因素后只归因一个。使用固定失败、同目标的正常措辞与条件变体、充分需求、开放任务及适用反例；未见样例／留出题与已调优样例分别报告。反例包括独立对象、新条件、否定／例外以及原文重要确认，检查细化指导是否使正常变体失效、探索空间收窄或引发逻辑冲突。

- 准确性、完整性、清晰度、可执行性分别评价并给实际证据，保留两位独立评审的身份、分歧、胜／平／负／双方失败。AI 辅助评审不称人工专家；篇幅、数值、格式与代码行为独立检查，平均分不能抵消目标改变、事实错误或重要规则反转。
- 同时报告整条链路及分阶段耗时、输入／输出 Token、实际请求与重试、首次成功率和失败率；嵌套耗时不重复相加，有足够样本时报告 p50／p95，样本不足说明口径和限制。增强、Plan、执行和付费评审分别计数，失败请求不遗漏；未返回用量记未知，价格未核对不伪造金额。不能只看下游生成更快，或用失败、短缺作品证明同等质量下成本更低。
- 在候选冻结前明确可接受的新增耗时、Token、调用次数及正常变体要求，服从第 4.2 节与实际批准协议。阈值是预先登记的验收条件，不能在失败后放宽；不把未经验证的全局百分比变成产品保证，也不通过削弱权限、重要提问或用户硬约束换取性能。

**采用、撤回或保持待验证。** 只有目标指标有明确实质收益、其他质量维度及充分／开放需求无实质退步、相关正常变体通过、成本符合冻结条件且未新增严重错误，才按已验证适用范围采用。收益不成立、成本不可接受或正常变体出现僵化／逻辑冲突时，撤回候选策略，保留原有保护及首次失败。证据不足记待验证；允许有依据地不采用干预并登记模型局限，但对应失败、未覆盖范围和 G1—G8 仍保持原状态。能力开放范围只能显式调整，不能静默降低承诺或挑成功重跑。

每次策略评估在节点报告／交接中填写以下记录，未测项写明未知；这些字段属于开发证据，不自动追加到产品复制正文：

| 必填记录 | 内容 |
| --- | --- |
| 症状与归属 | 失败原件／版本，错误最早位置与原句／字段，归属及依据，混合／未定原因 |
| 候选与可行性 | 假设、最小变更、适用范围、目标指标、预期收益及新增风险；不干预理由也记录 |
| 验证与成本 | 固定对照条件、实际四维与硬检查、正常变体／充分／开放／留出题、独立评审分歧、耗时／Token／尝试及预算 |
| 处置与边界 | 采用／不采用／撤回／待验证，代码和撤回位置、未通过／未覆盖项、对应门禁及下一步 |

本节约束开发和评估过程，不扩张平台执行用户任务的权限；文档落盘、局部测试或一次成功作品都不能代替完整实际验收。

### 6.4 G1—G8 放行门禁（全部为待完成目标）

**门禁按拟开放的模型／能力及冻结任务范围判定。** 历史专业案例的“未通过”是证据状态，不自动增加一项通用开发任务，也不要求逐个领域达到专业结论正确。公共机制缺陷、实质退步及既有承诺的缺项仍按对应门禁处理；专业细化的排期见[当前修复与验收范围](./待办事项.md#enhancement-remediation-scope)。既定代表性评测、失败记录和未覆盖项继续保留；本次范围澄清不把失败改为通过，不改变数值判据或静默缩小已承诺的开放范围。

| 门禁 | 通过条件与阻断规则 |
| --- | --- |
| G1 意图与事实保真 | 冻结候选的回归及留出集中无严重目标降级、虚构事实、用户禁令例外、跨对象确认、权限越界；出现即阻断对应模型／能力，不由总分抵消 |
| G2 重要提问与冲突 | 标注的关键未知／真实冲突召回 100%，关键题具备提问或适用证据已解决的记录；确定已知／委托事项不得假确认。全部标注题的问题必要性精确率、冲突精确率／召回率目标各 ≥95%，同时报告样本量；关键漏项零容忍 |
| G3 确认、示例与一致性 | 实际题答只作用于确认范围，旧选择同步失效；独立条件无误删；示例有效模式与开关／原文一致。显示、复制、编辑、撤销、历史和再次增强的有效要求一致 |
| G4 实际增益 | 模糊需求对 R0 的胜多于负、四维平均均不下降，并有具体任务完成收益；充分需求无可复现的实质退步。按模型／领域分别判，不能只报合并总分；自然 Plan 与同信息 Plan 分轨达标 |
| G5 实际作品可用 | 拟开放范围内的固定格式、编译／行为、数值／字数和原定交付按题通过；评审意见与原始要求及独立检查核对，确认的实质失败须修复复验或显式调整对应模型／能力的开放范围；失败、未评审及分歧不能当通过 |
| G6 安全与前端闭环 | 同一个正常测试账号完成全部正向场景；跨身份测试复用已有受控账号／身份夹具。任务／工作区隔离、TTL／清理、容量、注入、失败保稿和桌面移动完整链路通过，无重复注册规避状态问题 |
| G7 性能与成本 | 达 ME-00 冻结的第 4.2 节目标；同负载报告 p50／p95、尝试／拒绝／取消、Token 和内存；无无界排队／重试、旧请求占槽泄漏，超出容量有清晰失败与恢复 |
| G8 工程与发布 | 与变更相符的单元／集成／真实浏览器、全仓库必要检查、数据库迁移和备份恢复演练完成；跳过逐条说明，不等同通过。拟开放模型、部署拓扑、配置和回退方案可审查，未获发布授权不部署 |

每个能力在所有相关门禁通过后才标记“验收通过”，上线还需发布授权。限定范围发布必须显式调整产品开放能力与说明，不能静默隐藏重要问题或降低原有任务承诺。新版本／新路由重跑受影响矩阵；保留上一候选的证据、可回退代码和配置，Flyway 不回改历史迁移、不清空用户历史。
