# 百万级文件扫描与本地项目索引方案

## 1. 设计边界

项目索引和模型上下文是两个不同概念：

- 项目索引负责扫描、分类和记录所有符合条件的源码；
- 项目源码按代码块保存在浏览器本地 IndexedDB，不写入 Pinia；
- 每次增强提示词前，根据原始提示词从索引中检索相关代码块；
- 只有检索结果会进入 HTTP 请求和模型上下文；
- 400 万字符是后续可配置的模型上下文绝对上限，不是项目索引上限。

## 2. 当前实现

```text
用户选择目录
  ↓ File System Access API
Web Worker 按同一份范围规则预统计文件句柄（不读正文）
  ↓ 提供实际处理总数
流式遍历，并以 6 路有界并发读取文件元数据及小文件正文
  ↓
排除依赖、构建产物、日志和敏感文件
  ↓
文本检测、语言分类、符号与导入关系提取、6,000 字符分块
  ↓
按批次写入 IndexedDB
  ↓
Pinia 仅保存 projectIndexId 和索引摘要
  ↓
根据提示词检索相关代码块（默认最多 120,000 字符）
  ↓
发送后端进行上下文分析或提示词增强
```

已实现能力：

- Chromium/Edge 优先调用 `showDirectoryPicker()`，不再预先构造完整 `FileList`；
- 目录和文件通过异步生成器逐项产出，不设置 50,000 个扫描项上限；
- 先轻量预枚举，再按同一份范围规则读取：统计阶段显示已发现数量和不定进度；索引阶段显示实际已处理数/总数、百分比、吞吐量、当前路径和预计时间。预统计增加一次句柄枚举，以换取明确总量，不读取源码正文；
- 正式遍历按 64 个句柄组批，并以最多 6 路并发读取文件元数据；结果仍按原目录顺序产出；
- 不超过 64 KiB 的小文件最多 6 路预读，采样和分块复用内存 Blob；预读缓冲至多 384 KiB，大文件继续流式读取。敏感路径和未变化的完整索引在预读前排除，全文词表、分块内容和检索逻辑不裁减；
- 目录遍历、文本读取、分块和 IndexedDB 写入在 Web Worker 中完成；
- 每批最多写入 200 个文件记录、300 个代码块或约 4 MB 待写数据，避免完整项目常驻内存；
- 索引进度按文件数、时间或大文件读取字节数节流上报；只有完成持久化后才报告 100%，达到扫描上限时不能伪报全量完成。100% 表示范围内文件均已处理，不代表跳过或失败文件已有全文；
- 支持常见前后端源码、工程文件以及无扩展名文本文件；
- 未知文件通过内容采样判断文本或二进制，不再只依赖扩展名白名单；
- `node_modules`、`.git`、`target`、`dist`、日志目录和编译产物默认不遍历；
- 包管理器缓存目录 `.m2`、`.npm`、`.npm-cache`、`_cacache`、`.pnpm-store` 在遍历子项前排除，本地索引和 `webkitdirectory` 回退共用这组规则，目录名匹配不区分大小写；普通业务目录（如 `business-cache`）、根项目清单和用户文档继续保留；
- 默认读取所选根目录的 `.gitignore`，使用固定版本 `ignore@7.0.5` 处理相对路径、通配与否定规则；用户可在上下文面板关闭此项，强制敏感文件及依赖/构建目录过滤仍生效。仅根目录规则生效，不宣称支持嵌套 `.gitignore`、Git 跟踪状态或全局 Git 排除规则；
- FileList/拖入材料在源码和办公文档分流前使用同一份根目录规则，排除的文档不会先进入上传确认列表。没有项目规则时，不再仅因业务目录名为 `tmp` 或 `temp` 而一律排除；
- `.env`、私钥和证书等敏感文件不进入索引；
- 默认 50 MB 阈值仅作用于没有已知语言的文本；已知源码继续完整流式索引，仍受总索引容量限制。这是现有代码行为，修正文档此前“所有源码均限 50 MB”的错误说明；
- 本地索引按连续正文分块，目标为 6,000 字符，按结构边界可延长至最多 12,000 字符；相邻块不额外重复正文。临时文档索引使用独立分块策略；
- 索引阶段提取类、接口、函数、方法等符号，以及 Java、TypeScript、JavaScript、Python 等源码中的导入引用；
- 扫描过程中可以按批次暂停，已完成批次和检查点保留在 IndexedDB，继续时跳过未变化文件；
- 已完成索引支持增量更新，只重新读取新增或发生变化的文件，并清理已删除文件的元数据和代码块；
- 检索词覆盖每个有界代码块的完整正文，避免只索引前 40 个词而遗漏后段规则；单行 TXT、压缩 JSON 也分块，最大 12,000 字符，不拆断 UTF-16 代理对；
- 大文件在读取过程中也按批次写入；未读完的指纹标为不可复用。读取失败会清除该文件部分块，存储写入失败会明确终止索引；
- 自动目录索引跳过 `.codegraph`、`playwright-report` 和 `test-results`，避免生成报告挤占业务上下文；用户仍可主动添加需要分析的报告文件；
- IndexedDB 第三版增加 `projectId + lastSeenScanId` 复合索引，增量完成后只遍历旧扫描标记，而不是再次扫描全部当前文件；
- IndexedDB 第四版改用短数字键建立全文词索引，完整词表只保存一次；正文、词表和映射在同一事务内维护，旧库通过升级事务迁移，不减少源码或检索范围；
- 清空操作先同步移除页面状态，再用一个事务按主键范围删除项目文件、代码块、摘要和目录句柄，避免重复逐条删除造成数秒等待；
- 不支持 File System Access API 的浏览器继续使用 `webkitdirectory` 回退流程。
- 设置页提供项目上下文与隐私配置，并显示浏览器为当前站点分配的存储用量和配额；
- 索引会记录保留方式和过期时间；清理流程仅自动删除到期数据。失败任务的已提交批次保留到原定期限，用户可继续或主动删除；
- 分析或增强前默认展示将发送的代码片段数量和字符数，由用户确认后再发送；
- 当前页面选择的项目索引编号和上传文件列表不做恢复；刷新、关闭或重新打开页面后，左侧上下文列表保持为空。

## 3. 本地存储结构

IndexedDB 数据库 `prompt-optimizer-project-index` 包含：

| 对象仓库 | 内容 |
| --- | --- |
| `projects` | 索引编号、根目录、状态、文件和代码块统计 |
| `files` | 路径、语言、大小、修改时间、优先级、代码块数量、文件符号和导入引用 |
| `chunks` | 分块内容、所属文件、语言、顺序、符号、导入引用和优先级 |
| `chunkSearch` | 短数字键、原片段 ID 和一份完整词表；原片段 ID 唯一，词表使用多值索引 |
| `chunkSearchKeys` | 每块最多 256 个数字键与原片段 ID 的映射，供词查询批量还原候选 |
| `sources` | 项目编号和用户授权的本地目录句柄，用于继续索引与增量更新 |

`chunkSearch.searchTerms` 使用多值索引，以短数字主键减少每个词重复存储长路径造成的容量放大。词查询通过映射还原原片段 ID，按原字符串主键顺序裁剪候选；公开读取接口在同一个只读事务内还原完整词表，片段契约保持不变。检索时纳入关键清单文件，再按路径、标识符和中文词组召回。候选查询最多覆盖 64 个去重词，超限时保留前后各 32 个以兼顾原始需求和确认答案；每 8 个词并发查找，合并全部词的命中后再裁剪，不让前几个常见词提前耗尽候选名额。最终仍按相关性和字符预算排序、截断。

当前检索排序综合考虑：任务中的类名/函数名等符号、路径和正文匹配、当前打开文件、用户手动提供的文件、最近一次增量索引发现的新增或修改文件，以及高相关代码直接导入的文件。单个文件采用动态代码块配额：普通文件 3 段，最近变更文件 4 段，任务符号命中的文件 5 段，当前打开文件 6 段，用户固定文件 8 段；仅作为直接依赖或关键工程配置时最多 2 段。多个条件同时满足时取最高配额。最终仍受总片段数和字符预算限制，避免超大文件占满全部模型上下文。工作台会展示所选文件及“当前打开文件、任务中的符号、直接依赖”等选择原因。

Web 版无法直接执行 `git status`。目前“最近变更文件”来自增量索引识别到的新增和修改路径；将来 IDE 插件或本地代理可通过相同检索接口传入准确的 Git 变更列表和编辑器当前文件。

增量索引使用“索引格式版本 + 文件大小 + 最后修改时间”作为快速指纹，当前格式版本为 4。旧格式文件在下一次增量更新时重建检索词。数据库结构版本也为 4，但与索引格式独立：本次数据库升级在一个版本事务中迁移已有完整词表并移除旧长主键词索引，失败整体回滚；不因结构迁移而把旧格式文件标成已重建。每轮生成 `scanId`，只有完整遍历才清理未出现的旧记录；暂停或达到扫描上限时保留尚未遍历的记录。同大小且修改时间未变化的外部编辑仍可能无法被快速指纹识别，需要重新选择目录完整建立索引。

同一页面内暂停后继续索引时，不会序列化 JavaScript 异步生成器的位置。系统会从目录起点重新遍历，但已经写入且指纹未变化的文件只更新扫描标记，不会再次读取正文和分块，因而仍能低成本继续。页面关闭或刷新后不自动恢复该项目到左侧面板；IndexedDB 中的本地索引数据仍按用户选择的保留期限和设置页清理操作管理。

## 4. 当前安全限制

2026-10-31 失败恢复：完整文件批次与检查点在同一个 IndexedDB 事务内提交；配额或其他异常使当前批次回滚，不能把未提交数量记成成功。空异常也显示可操作原因，失败页提供“继续索引”。继续时重新遍历并校验指纹，已完整保存的文件复用、残缺文件重新读取。失败状态写入再次失败时保留原始异常和内存检查点；刷新页面仍按既有规则清空选择，不承诺跨刷新自动恢复目录。存储空间不足不会无条件自动重试或删除其他项目。

| 层级 | 当前值 |
| --- | ---: |
| 未知语言文本的单文件软阈值 | 默认 50 MB；已知源码受总索引容量限制 |
| 标准 Web 模式扫描文件数 | 1,000,000 |
| 标准 Web 模式本地索引软上限 | 2 GB，且不超过浏览器剩余配额的 80% |
| 单个代码块 | 目标 6,000 字符，结构边界最多延长至 12,000 字符 |
| 代码块重叠 | 当前本地索引按连续正文分块，不额外重复正文；临时文档索引有独立分块策略 |
| 默认模型检索上下文 | 120,000 字符 |
| 后端单次文件数量 | 1,000 |
| 后端上下文分析总内容预算 | 64 MiB，单个内联文本最多 5 MiB；模型上下文仍另受片段预算限制 |

这些值属于第一阶段安全默认值。项目索引和模型上下文分别计量：标准 Web 模式最多扫描 100 万个文件，本地索引受 2 GB 软上限和实际浏览器配额共同限制；模型请求仍只携带最多 120,000 字符的相关片段。

设置页同时展示以下预留档位，但当前不可启用：

- IDE / 本地代理模式：200 万文件、10 GB 本地索引、300,000 字符任务上下文；
- 超长上下文模式：绝对上限 400 万字符，但启用前必须完成模型能力检测、请求体分片和服务端限流验证。

## 5. 浏览器能力边界

- File System Access API 主要适用于 Chromium 和 Edge，并要求安全上下文；本地 `localhost` 可以使用。
- 用户取消目录授权时不创建索引，也不显示错误。
- 浏览器可能拒绝持久化存储或动态调整 IndexedDB 配额；页面显示的是估算值，索引过程仍需处理 `QuotaExceededError`。
- “临时保留”不会向浏览器申请持久存储保护；浏览器异常退出时无法保证立即删除，因此还会使用 1/7/30 天到期时间兜底清理。
- 普通 Web 模式不能保证所有设备都稳定处理百万文件。百万级和高隐私项目最终应接入本地上下文代理或 IDE 插件。

## 6. 验证

- 单元测试覆盖超过 1,000 个文件仍完整消费、未知文本识别、日志排除、大文件分块尾部保留以及按字符预算检索；
- 目录源测试覆盖嵌套目录遍历和 `node_modules` 提前跳过；
- 目录源测试覆盖预统计结果、依赖目录跳过、6 路并发上限和输出顺序；
- 包管理器缓存测试验证缓存目录不会执行子目录枚举或文件读取，备用文件夹上传同样过滤；真实 IndexedDB 测试验证完整增量更新会清除旧缓存条目，同时保留源码与无扩展名业务文档；
- Playwright 使用浏览器私有文件系统创建真实目录句柄，验证句柄可传入 Worker，并成功写入 IndexedDB；
- Playwright 同时验证增量更新、暂停继续、点击清空后 1 秒内移除页面索引状态，以及刷新页面后不恢复旧的上传列表和项目选择；
- 单元测试覆盖增量扫描的新增、修改、未变化、删除统计，以及每 200 个文件保存暂停检查点后继续；
- `npm run benchmark:index` 独立执行 100 万条合成文件元数据的增量扫描基准，不进入日常 `npm test`；
- 前端类型检查、单元测试和生产构建均需通过。

百万文件基准主要验证增量扫描循环、批次查询和内存保持是否退化，不等同于真实磁盘、浏览器 IndexedDB 或百万份源码正文的端到端性能。真实结果仍受磁盘、目录结构、文件大小、浏览器配额和设备内存影响。

### 6.1 文件夹索引变慢的定位与回归

“正在建立本地项目索引”发生在浏览器 Worker 内，尚未向后端调用文档向量化、摘要或 Plan 模型。不能用调整模型输出 Token 上限解决这个阶段的慢速。2026-10-30 起增加轻量预统计及真实百分比；当前文件路径随进度展示，单个大文件的读取字节仍用于内部节流。文档上传另按已传字节展示百分比，完成上传后显示解析阶段，不能把解析阶段进度当作上传字节比例。

2026-09-27 对当前工作区做仅含路径、大小的检查时，发现 `.m2` 有 1,818 个文件、122.57 MiB，`apps/web/.npm-cache` 有 893 个文件、204.20 MiB（其中 889 个没有扩展名）。旧目录规则没有排除它们：缓存包被无谓枚举，能通过文本探测的缓存还会进入全文分块和多值检索词写入。完整词表修复扩大了这类非业务材料的写入成本，但不能通过恢复“每块只取前 40 个词”规避问题，否则会再次丢失文档后段规则。

回归命令（在 `apps/web` 执行）：

```powershell
npm.cmd test -- src/features/project-index/fileSystemDirectorySource.test.ts src/composables/useProjectFiles.test.ts
npm.cmd run test:e2e -- project-index-performance.spec.ts project-index-retrieval.spec.ts --project=desktop-chrome
```

`project-index-performance.spec.ts` 使用合成文本和浏览器真实 IndexedDB。对照组仅模拟旧目录过滤遗漏：9 个缓存文件与 3 个有效文件一起索引；修复组只遍历 3 个有效文件。一次本机运行中建索引分别约 5,785 ms 和 26 ms。测试同时验证缓存读取次数为零、增量清理 9 条旧文件记录、保留 3 个未变文件，以及中文尾部规则仍可召回；另一组 240 份文档继续验证完整词表和尾部检索。耗时仅用于诊断，断言针对读取次数与检索结果，不设跨设备不可靠的毫秒阈值。

上述数据不是用户真实目录在浏览器中的完整耗时，也不代表模型业务准确率验收。上线前仍需在目标设备实测真实目录的耗时、内存、检索覆盖率和失败率。旧版已建立的完整索引可通过增量更新清除缓存条目；正在运行的旧 Worker 需要重新开始索引才能使用新规则。

后端 `PlanningDigestSelector` 在单次选择中为每份摘要计算一次排序分数，并复用已编译的匹配规则；相关性权重、业务文档保底、目录覆盖和摘要数量预算保持一致。办公文档仍通过后端受限线程池流式解析、向量化及摘要；各阶段耗时通过 `document.index.stage.completed` 记录，具体字段见部署运维文档。

### 6.2 2026-10-30 数量与完整性口径

- `discoveredFiles = indexedFiles + metadataOnlyFiles + ignoredFiles + failedFiles`：分别为本轮范围内已处理、完整全文、空文件/部分索引、类型或安全跳过、读取失败；四类结果互斥。
- 项目规则排除的目录与文件另计；不枚举已排除目录的子项，不猜测它们内部有多少文件。界面可展开最多 20 个被排除目录。
- `FileList` 达到扫描/选择上限的剩余文件报告“未扫描”，不能混入“已确认忽略”。办公文档多条解析提醒也不能当作多个文件失败。
- 容量不足的残缺文件使用不可复用的指纹；已有非空元数据记录也须重新尝试。空文件在增量刷新前后维持相同统计类别。
- 索引摘要新增可选阶段计时：预统计、读取/分块/元数据与其他处理、批量写入、合计。批量写入计时不包含最后的摘要提交；不把这些粗阶段当作单独的 CPU/磁盘精确耗时。
- 本轮实测与限制见 [文件上传与本地索引进度验收](./testing/文件上传与本地索引进度优化-2026-10-30.md)。

旧版历史验收：2026-10-30 的 21,494 文件范围在临时浏览器中触发 `QuotaExceededError`，空异常信息又造成界面无法解释失败；普通磁盘配置的补验因浏览器连接关闭未完成。该原件继续保留，后续修复结果见下节。2 GiB 是当前实现的估算索引预算，不是实际数据库占用上限保证，站点配额估算也不能保证下一次事务成功。Word、Excel、文字层 PDF 和分片 TXT 的真实后端样例已通过，详见[补充验收报告](./testing/真实项目首导与文档上传验收-2026-10-30.md)。

### 6.3 2026-10-31 大目录容量放大修复

短数字键方案在同输入浏览器样本中将占用从 262.6 MB 降至 100.2 MB，完整词表、正文和候选顺序相同；常见词查询增加了数字映射步骤，不能据此承诺所有查询更快。

真实本项目目录完成 21,536 个文件处理：完整全文 21,284、仅元数据 16、规则跳过 236、失败 0，23 份分布抽样的正文与尾部全部一致。整库高层选取检查误将带 `#chunk-编号` 的返回路径与原路径直接比较，原失败标志保留；修正脚本后的三个真实文件定向选取通过，尚未重复整库选取检查。

本轮合计约 37 分 31 秒，写入仍占约 93.4%；估算预算距 2 GiB 上限仅约 29.5 MiB。因此容量放大缺陷已有工程修复和真实目录证据，导入速度、容量耗尽恢复、接近配额的大旧库升级、16 万文件及跨设备验收仍未闭合。详细范围与原件见[修复与复验报告](./testing/大目录索引容量放大修复与复验-2026-10-31.md)。

### 6.4 2026-10-31 数量核对与根文件检索

本轮候选目录 21,578 个文件处理完成，分类总数与数据库元数据、片段数一致，23 份正文及尾部抽样一致；原件中的根目录 `README.md` 漏召回已定位并修复。普通根文件名现在进入精确候选，但必须匹配当前项目已索引文件才限制范围；不存在的文件名仍回退普通检索，URL、邮箱不参与本地路径匹配。
