# 图像转提示词：实现与使用说明

更新：2026-10-25。该模块只生成提示词，不调用绘图模型生成图片。当前真实验证范围与未通过项见[本机验证报告](../testing/图像转提示词本机验证-2026-10-25.md)。

## 两种业务模式

| 模式 | 输入和用途 | 输出边界 |
| --- | --- | --- |
| 关闭 Plan：参考图还原 | 一张必填参考图片；从图到文提取可见内容 | 描述主体、关系、构图、光色、风格及可辨认文字；不做创作问答，不接受新增主体、场景或画面文案 |
| 开启 Plan：自定义新图创作 | 必填文字构想；参考图可选 | 围绕新图的重要未知提问，充分时允许零问；实际答案确认后生成创作提示词。图片仅按指定用途提供灵感 |

Plan 开启后，参考角色分为整体灵感、主体、风格、布局；角色不赋予复制整张图或执行图内指令的权限。画面指定文案独立填写，服务端保留原字符，并确保最终正文包含该原文。描述、观察、用户回答和模型建议分别保存，模型建议不自动变成用户确认。

## 如何使用

1. 打开 `/image-to-prompt`，先按目标选择模式。关闭 Plan 时选择参考图；开启时填写新图构想，可不提供图片。
2. 选图只在当前浏览器内存预览，不自动上传。检查图片是否含个人或商业敏感内容，勾选图片区的“我已检查图片隐私”确认框后，点击提取或梳理才上传并调用模型。已选视觉模型但未勾选该项时，按钮仍禁用；按钮下方会显示缺少的操作，不需要因此更换模型。
3. 模型列表与提示词增强共用同一平台目录，名称、排序和启停由模型管理统一维护；两个工作台各自保留本次选择。图像页面始终显示全部已发布模型，不因附图或切换模式隐藏文字模型。附图必须选择已开放视觉能力且图片数量满足限制的模型；能力不足时说明原因并阻止提交，纯文字 Plan 可以使用可用的文字模型。管理员修改配置后可点击“刷新模型”。演示结果会明确标记，不代表识图成功。
4. Plan 出题后，选择选项并填写必要补充；两者同时保留。零问时也可明确确认生成。修改模式、构想、图片、角色或输出设置会使旧计划失效，不自动重新调用。
5. 核对观察来源、识别不确定项和最终正文；可以编辑、取消编辑、撤销同一记录的上次编辑，再复制。剪贴板写入失败时提供手动复制正文。
6. “基于已有文字优化”使用服务端已保存正文及分析摘要，不重新看图。需要重新识图时，重新选择图片并发起相应模式的生成；历史不恢复原图。
7. 从“图像历史”打开或逻辑删除记录。公共历史页提供图像历史入口；图像与文本记录的接口、状态和恢复目标独立。

关闭标签页或刷新会丢失浏览器内存中的未保存构想、文件和编辑稿。页面内路由离开会保留当前内存草稿；已提交请求保留操作编号，返回后查询结果，不自动重放付费调用。发生版本冲突时保留编辑稿，先读取最新记录再处理。

## 前后端链路

前端为 `ImageToPromptPage.vue → stores/imagePrompt.ts → services/imagePromptApi.ts`，通过现有 Vite `/api` 代理访问后端 `imageprompt` 模块。`ImagePromptHelp.vue` 保留模式定义及使用指南；模型管理页面只有一份模型目录，在对应模型行点击“图像能力”，由 `ImagePromptModelSettings.vue` 编辑视觉准入。已停用模型也可以先配置能力，配置本身不发布或启用模型。

后端由 `ImagePromptService` 编排，复用 `CurrentActor`、平台模型目录、服务端路由、受限 HTTP 客户端、模型并发和调用审计。不会更改原文本直接增强、Plan 或历史协议。`OpenAiImagePromptProvider` 将图片作为 `image_url` 内容块中的 Base64 data URL 发送给兼容多模态模型；不需要独立 OCR 或图片公网地址。正常每阶段一次调用，仅协议失败最多一次修复；网络失败、超时和内容拒绝不自动重试。

视觉观察采用图片 UUID、类别、描述与 `OBSERVED / INTERPRETATION / UNCERTAIN` 状态。接口中的最终 `Document.questions/answers` 是已确认的原始题答档案，不表示生成阶段又要求用户答题。可复制正文为 `optimizedPrompt`，不混入分析标签或界面说明。

## 模型统一配置与 Plan 复用边界

统一的是模型目录和配置入口。`ImagePromptModelService.models()` 与文本增强都以 `PlatformModelCatalog.available()` 为来源，按目录原顺序返回模型；视觉准入是同一公开模型标识上的附加能力，不是另一套模型注册表。管理员读取 `PlatformModelCatalog.all()`，因此能配置已停用项；逻辑删除项继续排除。模型发布、停用或移除同时影响两处，视觉开关只影响带图调用。

配置步骤：在“模型管理”新增或编辑目录项，维护名称、启停、排序与默认模型；需要识图时，在该行打开“图像能力”，登记允许图片输入、最多图片数及官方文档或受控验证依据。带图任务同时受全局启用状态与视觉准入约束，前端提示不能替代服务端再次校验。文字模型可以保持在列表中供无图 Plan 使用，不因统一目录而被视为支持识图。

**图像 Plan 与文本增强 Plan 当前是独立业务链路。**两者都采用“梳理重要未知 → 用户回答 → 生成优化提示词”的流程，但没有复用同一个 Plan 编排器或问答协议：

| 环节 | 提示词增强当前 V2 入口 | 图像转提示词 |
| --- | --- | --- |
| 业务目标 | 围绕原始提示词保留报告、代码、方案等交付物，澄清实质未知 | 围绕用户构想设计一张全新图片，参考图按角色提供灵感 |
| 发起 Plan | `/api/v2/optimizations/plan` → `NaturalEnhancementService.plan` → `NaturalPromptProvider.plan` | `/api/v1/image-prompts/plans` → `ImagePromptService.plan` → `ImagePromptProvider.invoke(PLAN)` |
| 输入和会话 | 原始提示词、安全项目上下文、会话历史；`PlanningSessionService` 绑定原题与上下文版本 | 构想、逐字文案、参考角色和视觉观察；`ImagePromptStateStore` 保存 `BoundPlan`、输入指纹和图片有效期 |
| 回答后生成 | `/api/v2/optimizations` 携带 `planConfirmation`；自然正文进入 `NaturalEnhancementService.optimize`，结构化正文进入原编排器 | `/api/v1/image-prompts/plans/{id}/confirm`；核对实际选项与自定义回答，进入 `invoke(GENERATE)` |
| 确认阶段是否重新看图 | 文本链不接收此模块的图片资产 | 不重新发送像素，使用已绑定的视觉分析、输入及实际题答 |

旧 V1 文本 Plan 接口仍由 `OptimizationPlanningServiceImpl` 处理，也不是图像 Plan 的实现。两条链路共享服务端身份、模型目录、供应商路由、受限 HTTP 客户端、并发控制和调用审计；不共享 Plan 会话、提示词指导、问答 DTO 或业务历史。文本 Plan 的优化不会自动应用于图像 Plan，本次没有合并两套业务链路或更改其产品语义。

| 接口（均在 `/api/v1` 下） | 作用 |
| --- | --- |
| `GET /image-prompts/capabilities` | 可用模型、图片限制、历史持久化状态 |
| `POST /image-prompt-assets` | Multipart 主动上传、解码及元数据清理 |
| `GET /image-prompt-assets/{id}`、`DELETE` 同路径 | 私有预览、撤销资产 |
| `POST /image-prompts` | 单图描述性还原 |
| `POST /image-prompts/plans` | 新图创作 Plan，可无图 |
| `POST /image-prompts/plans/{id}/confirm` | 服务端绑定计划与实际题答生成 |
| `GET /image-prompts/operations/{id}` | 查询已提交操作，不再次调用模型 |
| `POST /image-prompts/operations/{id}/save` | 单独重试保存已生成结果 |
| `GET /image-prompts/history` | 分页查询，`current`、`size=10/20/50`、可选 `mode` |
| `GET /PATCH /DELETE /image-prompts/history/{id}` | 当前正文、乐观修订、逻辑删除 |
| `POST /image-prompts/history/{id}/re-optimize` | 基于已保存文字再次优化 |
| `GET /PUT /admin/image-prompt-models` | 管理员读取与登记能力；PUT 的 `modelId` 为查询参数，兼容包含斜杠的模型标识 |

## 配置、存储与权限

- JPEG / PNG，每张原始及规范化文件不超过 10 MiB、1500 万像素、单边 8192；平台单任务最多三张、总规范化字节最多 30 MiB。实际模型还受管理员登记的 `maxImages=1..3` 限制，未经登记不接受图片。
- 先验证实际格式和尺寸再分配完整像素；按 JPEG EXIF 校正方向，重新编码去除元数据。不会把用户提交的路径或外部图片 URL 当成读取目标。
- 临时图片默认在 `${java.io.tmpdir}/prompt-optimizer-image-assets`，可设 `app.image-prompt.asset-directory`；默认一小时失效，定时清理每分钟运行。撤销先使引用无效，再清理文件。单实例还限制每个身份十二个活动资产及目录约 512 MiB 总预算；多实例配额不是全局精确配额。
- Plan 和资产元数据默认保存在 Redis，Plan 有效期不超过一小时及其图片有效期；幂等操作和结果缓存保留二十四小时。Redis 故障拒绝继续，不回退到各实例重复调用。`app.image-prompt.store-mode=MEMORY` 仅供显式本机演示。
- 多实例需要共享临时图片目录或保持请求落到持有图片的实例；当前没有对象存储适配，不应将默认本地目录误当成多实例共享存储。
- V39 新增 `image_prompt_record`、`image_prompt_model_capability`，包含完整数据库注释。长期历史只存文字和来源元数据，不存原图、Base64 或公网图片 URL。编辑使用 `edit_revision`，所有业务读写校验服务端租户、工作区和用户；逻辑删除后查询、保存恢复、编辑及再次优化都拒绝访问。
- `app.history.enabled=false` 仅提供有界内存演示历史，服务重启不保留；正式模式使用 PostgreSQL 和 MyBatis XML。不能回改已应用的 V39。
- 管理员依据官方能力或受控验证记录显式登记视觉准入，不靠厂商或名称猜测。普通用户不能配置模型端点和密钥，管理员能力配置仍复核当前权限。

参考官方协议：[TokenHub 图片理解](https://cloud.tencent.com/document/product/1823/136956)、[MiniMax 调用指南](https://cloud.tencent.com/document/product/1823/132246)、[Kimi 调用指南](https://cloud.tencent.com/document/product/1823/132232)。模型及参数以实际服务端路由和验证记录为准。

## 当前边界

项目上下文目前为用户主动填写的文字摘要，不自动读取项目目录、源码或文本工作台的上下文。图内命令、链接和二维码不执行；来源图片和模型观察不产生新授权。

元数据清除、私有存储和明确凭据扫描不等于完整隐私识别。当前没有自动人脸、证件、所有个人信息、敏感题材的本地检测，也没有自动打码；图片发送前仍需要用户检查，模型服务的内容拒绝会明确返回。图片可能包含的文字和分析也属于私有业务数据，不能因不保存原图就视为无敏感内容。

真实视觉验证仅覆盖本机已启用的 MiniMax M3、合成单图和限定 Plan 场景；三份生成的提示词已通过独立验收工具绘制图片，未将绘图接入产品。照片、专业图表、模糊小字、多图冲突、其他模型及成图稳定性尚未完成系统验收。当前模型仍可能追问已委托的设计，下游也未完全落实严格扁平风格；不能承诺像素复刻、准确文字成图或所有创作意图稳定识别。工程实现与完整质量验收、正式发布分别记录。
