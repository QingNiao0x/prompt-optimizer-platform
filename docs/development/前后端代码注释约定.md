# 前后端代码注释约定

## 1. 为什么要定这个约定

这个项目会同时维护 Vue 前端和 Java 后端。注释的主要用途是帮助后来阅读代码的人快速理解设计思路、业务边界和容易踩坑的地方，而不是把每一行代码翻译成中文。

提交代码前至少检查两件事：

1. 只看方法名和类型，能否大致看懂这段代码负责什么；
2. 遇到不直观的处理时，注释是否说明了为什么这样做。

## 2. 必须写注释的情况

- 涉及源码隐私、API Key、权限红线和敏感信息脱敏；
- 有文件数量、大小、Token、超时或限流等边界；
- 为兼容浏览器、模型供应商或操作系统而采用特殊写法；
- 正则、递归、缓存、并发和重试逻辑不容易直接看懂；
- 代码行为与表面含义不同，例如测试使用模拟接口但仍校验请求内容；
- 为后续扩展预留了接口或暂时采用折中方案；
- Java 中对外服务、领域服务、适配器和重要 DTO 的职责与参数约束。

## 3. 不建议写的注释

下面这类注释会增加阅读负担：

```ts
// 设置加载状态为 true
isLoading.value = true;
```

代码本身已经说清楚了动作。更有用的写法是解释原因：

```ts
// 请求期间禁止重复提交，避免同一份项目上下文被并行发送多次。
isLoading.value = true;
```

同时避免：

- 每行代码前都写一句中文；
- 使用“首先、其次、综上所述”等文章式表达；
- 留下已经过期的实现说明；
- 用大段注释掩盖命名混乱或方法过长；
- 写“这里进行了某某操作”这类没有补充信息的句子。

## 4. Vue 和 TypeScript 注释写法

### 4.1 组件顶部

页面组件的数据流较复杂时，可以在关键状态或事件处理函数前说明它连接了哪些模块。普通展示组件不需要固定格式的文件头。

```ts
// 文件内容只保存在当前页面状态中；用户刷新页面后不会自动恢复，避免源码被默认持久化。
const files = ref<ContextFileInput[]>([]);
```

### 4.2 方法和组合式函数

对外导出的组合式函数、请求转换器以及包含业务规则的方法，优先使用简短的 TSDoc。参数名称已经清楚时，不必逐项重复。

```ts
/**
 * 把浏览器读取的文件整理成后端上下文格式，并跳过二进制文件和超大文件。
 * 跳过文件时返回提示信息，让用户知道本次分析并不包含完整工程。
 */
export const useProjectFiles = (): ProjectFilesState => {
  // ...
};
```

### 4.3 模板部分

Vue 模板只有在布局分区、权限控制或状态切换不明显时才写注释。简单的输入框、按钮和标题不用逐个说明。

```vue
<!-- 分析结果为空时保留引导区，避免右侧页面在请求前出现大块空白。 -->
<div v-if="!result" class="empty-result">
  <!-- ... -->
</div>
```

### 4.4 类型要求

- TypeScript 保持严格模式；
- 不使用 `any`，不确定的数据先使用 `unknown` 并做类型收窄；
- Props、Emits、接口请求和响应都定义明确类型；
- 注释不能代替类型，例如不要用注释描述一个本可用联合类型表达的取值范围。

## 5. Java 注释写法

### 5.1 类注释

Controller、Service、领域服务、Provider 适配器和上下文分析器要说明职责边界。类级 Javadoc 使用公开别名 `QingNiao`，不填写真实姓名或容易过期的创建日期；具体格式见 5.4 节。

```java
/**
 * 负责组织提示词增强流程。
 * 本服务只协调上下文分析、模板构建和模型调用，不负责保存用户源码。
 *
 * @author QingNiao
 * @since 0.1.0
 */
@Service
public class PromptOptimizationService {
    // ...
}
```

### 5.2 公共方法

公共方法和接口方法需要说明业务用途或调用契约。参数存在格式、长度、隐私或异常约束时再写 `@param`、`@return` 和 `@throws`，不要机械生成没有信息量的标签。实现类中仅委托给已写明契约的接口方法可以继承说明；实现有额外边界或副作用时应单独写明。

本项目现有后端类已统一补齐类级 Javadoc；后续新增类、公共方法和非平凡私有方法都要同步补充注释。实体类中纯 getter/setter 属于样板代码，可以不写方法注释。

```java
/**
 * 分析本次请求主动提交的项目文件，生成技术栈、依赖和目录摘要。
 * 原始文件内容只参与本次计算，分析器不会主动读取请求范围以外的本地路径。
 *
 * @param request 用户本次提交的上下文，文件数量和大小必须满足接口限制
 * @return 可发送给提示词增强流程的上下文快照
 */
public ContextSnapshot analyze(ContextAnalysisRequest request) {
    // ...
}
```

### 5.3 方法内部

方法内部注释放在规则、边界和特殊分支前面，说明为什么存在这段处理。

```java
// 先脱敏再计算缓存键，避免敏感内容出现在日志、指标标签或 Redis Key 中。
String cacheKey = cacheKeyFactory.create(redactedContext);
```

### 5.4 类级注释和作者标识

以后新增的 Java 类，类上方必须有类级 Javadoc，至少说明类的职责边界。作者标识使用公开别名即可，不要求填写法定姓名。

当前仓库统一写法：

```java
/**
 * 负责组织一次提示词增强请求，不保存用户原始源码。
 *
 * @author QingNiao
 * @since 0.1.0
 */
public class PromptOptimizationService {
    // ...
}
```

后续新增顶层类必须保留 `@author QingNiao` 与 `@since 0.1.0`，内部私有记录类不强制添加。既有类仍可能使用旧格式；修改其业务行为时同步核对注释，不必仅为统一标签而批量改动无关类。

说明：

- `QingNiao` 可以作为 GitHub 公开别名使用；如果它不是你的公开账号，也可以改为团队名或项目维护组名称。
- 在每个类中写公开别名通常不会产生知识产权问题。作者标签主要用于维护和追溯，不等于版权转让或权利声明；真正的知识产权归属仍以劳动合同、委托合同、公司制度和开源许可证为准。
- 不建议在公开仓库写入真实姓名、手机号、私人邮箱、内部路径或其他不必要的个人信息，除非你明确希望公开并得到组织允许。
- `@author` 和 `@since` 是更常见的 Javadoc 标签；`@DateTime`、`@Author`、`@ProjectName`、`@Description` 属于自定义格式，未配置 Javadoc 工具时可能产生未知标签警告。
- 既有四字段头部可在未涉及该类的任务中暂时保留；新增类使用上面的标准 Javadoc 格式，不再复制四字段写法。
- 已有类不要求为了统一格式一次性全部重写；从后续新增或实际修改的类开始执行。

## 6. 注释与代码一起维护

修改代码行为时要同步检查相邻注释。发现注释和代码不一致时，以实际业务要求为准修正两者，不能只改代码留下错误说明。

代码评审时重点看：

- 注释是否解释了真正困难的部分；
- 描述是否与当前代码一致；
- 是否泄露密钥、真实项目路径或用户源码；
- 能否通过更清楚的命名和拆分减少注释数量；
- 初次接触前端或后端的人能否沿着注释理解关键数据流。

## 7. 数据库模型与持久化实体

- 新建表时必须添加 `COMMENT ON TABLE`，并为每个字段添加 `COMMENT ON COLUMN`；表级说明业务职责、数据归属和隔离范围。
- 新增或修改字段、外键、默认值、可空性、CHECK、唯一性或删除策略时，在同一条新的 Flyway 迁移中同步更新注释。已应用迁移不得回改，以免破坏校验和。
- 外键注释写清引用表和级联规则；可空字段说明何时为空；时间、金额和计数说明单位、时区或估算口径。
- 枚举或 CHECK 字段逐一写出全部数据库合法值及含义、默认值和保留值。未受数据库 CHECK 约束的字符串不得描述为数据库枚举。
- JSON/JSONB 注释说明对象或数组结构、已知键/元素类型、默认值、空值规则及数据库是否校验结构；未固定的结构明确标为未固定。
- MyBatis Mapper XML 是持久化 SQL 的唯一位置；Mapper 接口、XML namespace 和 statement ID 必须一致，所有值使用 `#{}` 参数绑定，禁止 `${}` 和注解 SQL。
- 映射类型类级 Javadoc 说明表名、业务职责、租户/工作区范围及持久化边界；关键字段说明外键、枚举、JSON、敏感信息和逻辑删除语义。普通访问器不重复写注释。
- 已退役表只保留历史迁移说明，不得在新迁移中当作现存表引用；数据库注释跟随 Flyway 前向迁移，不回改已应用迁移。
