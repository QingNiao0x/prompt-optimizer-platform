# 自然增强要求覆盖与缺口检查

本轮按用户认可的当前自然模式继续开发，不引入职业／场景模板或恢复固定约束。默认策略为NATURAL/4；NATURAL/3作为冻结基线，与第一、二版一样按历史保存版本兼容。

## 职责与流程

1. 同一次模型调用先理解原定任务，按实际存在的目标、对象、格式、篇幅、独立条件和用户确认组织要求；不要求六个槽位都出现。完整原始提示词、授权资料与全部实际题答仍是依据。
2. `requirements`保留来源原句及适用维度，`additions`分别记录拟议补充、具体缺口与交付作用。需求充分时保留有效表达、允许零补充；模糊时补足目标作品所需内容，已委托设计由执行者完成。
3. 生成指导要求返回前核对意图、遗漏、矛盾、空模板和无意义重复，最终返回自然正文及仅供内部使用的`review`。没有新增常态裁判调用、通用评分线或质量重试。
4. `NaturalTaskUnderstanding.resolve`核对当前来源原句并由服务端覆盖来源类别。第四版还核对要求维度、原始需求及各份真实题答的来源关联、补充缺口与检查记录的安全／容量。
5. `NaturalTaskReview`用已登记下标对应最终正文的逐字锚点，要求覆盖及补充均不得缺项、越界或重复冒充另一项。自然增强在模型正文及平台组装后分别核对，不能靠平台补写原要求掩盖模型漏写。
6. Plan尚无最终正文，覆盖数组为空；每题须关联重要未知，并说明为何需要用户决定及不同答案怎样改变交付。可以零问题，不按职业、数量或自报分类自动删题，真实题答、推荐保护、所有权、TTL及注册时机沿用既有机制。

## 检查的实际边界

覆盖记录是同次生成的候选自查，不是独立语义裁判。下标、分类、来源存在和正文引用不能证明任务理解穷尽、任意改写等价、判断正确或补充有用；这些仍以同信息条件下的实际作品评估。用户实际回答“不知道”仍表示未知，不能因其被引用而视作参数已经确定。

内部覆盖引用采用单行片段；跨行要求可以对应多个片段，正文、代码围栏及来源引文仍保留原格式。离线初次发现跨行引用在完整追加权限原句去重后失效，已通过上述有限协议约定处理，并统一CRLF及Unicode换行判据，未取消组装前后保护或扩大自由正文删除范围。

只有协议／必要保护失败才沿用现有最多两次调用，鉴权、超时和网络错误仍不自动重试。每次实际尝试均计量；Plan注册、历史写入等副作用位于校验成功之后。内部理解、覆盖引用和文件引文不进入优化提示词、用户历史或日志。

## 兼容与验证

- 直接增强、Plan最终生成与再次增强仍共用自然链路；自然模式不自动添加五条固定约束。用户明确追加权限、原始具体要求、上下文过滤与敏感扫描保留。
- V1—V3冻结各自生成指导，旧记录读取不重写，再次增强按保存字符串版本分发。浏览器没有新增可自行选择内部策略版本的参数。
- 新增V19仅前向维护版本与约束归属的数据库注释，不修改表结构、旧记录或V1—V18，本轮不应用迁移。
- 前端产品源码、三栏界面、编辑／复制和历史契约不变。`chainVersion`继续为字符串，第四版的内部记录不进入wire响应。
- 本轮受影响后端最后报告去重合并120项通过；包含覆盖、来源、Provider、自然服务、历史、控制器、结果及旧动态条款。真实评测按单独冻结的[48次上限协议](../testing/evidence/natural-coverage-workflow-2026-10-20/protocol.json)执行，不能以离线检查代替作品收益。

## 实际作品评估

以原始提示词、冻结第三版和候选第四版三臂，在同一材料、有效信息、模型及参数下执行。先依据原任务检查完整源码、JSON数据与格式、篇幅等客观事项，再从用户是否可直接使用、要求是否落实、事实是否有据及是否增加加工负担审阅；记录调用、Token与耗时。需求已充分时允许并列，不强行制造赢家。失败原件、工具错误、评审错引与未定归因分别保留，不能采样到成功。
