# 提示词增强、Plan 与示例：后续优化及待办审查

日期：2026-10-11。类型：开发规划、源码复核、待办清理。源码基线：`44a5840`。

本次只修改文档，没有修改业务代码、执行模型调用或开展新的浏览器验收。工作区原有 SMTP／注册配置修改不属于本次范围。此前直接增强的局部代码修复及真实作品结果单独记在[正文目标保护与真实复验](./testing/直接增强正文目标保护与真实复验-2026-10-11.md)，不能与此次文档交付混算。

## 1. 结论与产品目标

用户反馈指向同一个质量问题：增强结果虽然更长、段落更齐全，却未稳定地帮助下游完成原定任务。解决方向是让任务理解、确认状态、示例要求与最终正文共用一致的依据，并用实际作品验证改进；继续追加通用规则或压缩字数均不足以解决根因。

保留以下产品约束：

- 平台只生成优化提示词。用户要求报告、代码或“论文方法部分的写作提示词”时，保持下游交付物及层级，不能统一改成分析方案或大片填空模板。
- 模糊需求可以有实质补全，充分需求保留有效框架。最小必要干预约束无依据改动，不限制必要帮助，也不要求普通用户开启高级模式才获得智能增强。
- 区分相关事实、已确认选择、候选建议、待定参数和实际缺失数据。不能用缺少数据阻止全部交付，也不能为了让报告显得完整而编造结果。
- Plan 用于解决真正影响结果的未知。已回答事项改成执行要求，未回答或部分回答的剩余条件仍保留；普通组织细节不再变成问卷。
- 示例开关开启已经构成用户要求。有效要求应明确相关输入与预期输出，不能退回“仅在用户要求时”；原文禁例、禁虚构和实际不兼容的格式限制继续生效。

执行依据为[优化方案](./14-提示词增强与Plan最小干预优化方案.md#root-cause-remediation)和[当前 ME 待办](./待办事项.md#enhancement-review-20261011)。此次没有把任何 ME／PF／PL 功能标记为完成，也不保证任意模型永不退步。

## 2. 核心问题复盘与根因

### 2.1 证据分层

1. **用户历史截图**证明当次可见内容与产品体验有问题，但缺少完整模型响应、组装前后文本和固定执行条件，不能单凭截图确定每句话由模型还是平台添加。
2. **当前源码**可以确认仍存在的条件句兜底、词法判定、字符串覆盖和前端状态路径。静态路径不是所有真实请求都失败的证明。
3. **已有确定反例及真实记录**证明部分修复有效，也保留了重复缺口、无依据参数、额外交付等未通过项。本次引用其限定范围，没有重新执行这些测试。

用户给出的两份报告也不能直接视作同条件 A/B：检索能力、可用资料、模型及参数未全部固定。增强前作品的专业细节更丰富是有价值的体验反馈，但其数值、引用和默认方法是否正确仍须独立核实；不能靠取消事实边界复现“更像专业报告”的外观。

### 2.2 根因、现状与修复职责

| 问题 | 当前依据及边界 | 根因与修复落点 |
| --- | --- | --- |
| 对需求做表面重排，或选错交付画像 | [TaskIntentResolver](../services/api/src/main/java/com/promptoptimizer/template/domain/TaskIntentResolver.java) 已集中部分识别，但主要基于原文和确认决定的词法规则，未直接接收相关上下文；[AmbiguityDetector](../services/api/src/main/java/com/promptoptimizer/enhancement/service/impl/AmbiguityDetector.java) 提供有限候选问题，不承担完整任务建模 | 相关上下文、交付层级、缺口和确认状态尚未形成各阶段共用的有效任务视图。沿用现有识别器，先补最小共同输入，避免在模板、检测器、Provider 分别补另一套分类规则 |
| 有结构、保真通过，却缺少可执行增益 | [Provider](../services/api/src/main/java/com/promptoptimizer/provider/infrastructure/openai/OpenAiCompatiblePromptEnhancementProvider.java) 的 `SYSTEM_PROMPT` 已有实质补全和确认融入规则；[组装器](../services/api/src/main/java/com/promptoptimizer/enhancement/service/impl/OptimizationResultAssembler.java) 有结构、规则和目标保护 | 系统并非没有调用模型或完全没有增强指令。规则存在不代表稳定落实，既有校验也不能证明补充有价值。需按任务检查输入输出、边界、执行细节及验收是否解决真实缺口，再用作品检验；不能以新增条数作为硬门槛 |

| Plan 决定重复、旧问题回流 | Provider 已传递 `confirmedDecisions`／兼容答案，并要求选择进入 TASK、格式进入 OUTPUT；[PlanningSessionServiceImpl](../services/api/src/main/java/com/promptoptimizer/enhancement/service/impl/PlanningSessionServiceImpl.java) 与现有事实／决定结构已有确认基础。结果链仍有字符串覆盖及缺项补回 | 不是简单“漏传答案”，而是缺少稳定的对象、条件与正文落实关系。复用 [ConfirmedPlanDecision](../services/api/src/main/java/com/promptoptimizer/enhancement/domain/ConfirmedPlanDecision.java) 与 [PlanningFactCard](../services/api/src/main/java/com/promptoptimizer/enhancement/domain/PlanningFactCard.java)，形成有效选择后替换当前任务中的旧选择；来源原件保留，不能无差别删掉原文问句 |
| 背景反复盘点缺口，报告变成待填材料 | Provider 已要求不在各段重列待确认清单，但模型仍可能输出，平台又有统一未决条件和交付指导；最新目标降级校验已修一部分确定反例 | 模型与组装器对“事实、行动、缺口”的表达职责仍有重叠。背景只写相关已知事实，缺口放在一个必要位置；限制真正依赖该缺口的部分。保留原框架并补可执行帮助，而不是每节重申不能计算，或把标题改成“初稿”就视为通过 |
| 示例开关和结果相反 | [TaskDeliveryProfile.exampleGuidance](../services/api/src/main/java/com/promptoptimizer/template/domain/TaskDeliveryProfile.java) 仍有“仅在用户要求且资料允许时……”科研兜底；组装器按 `includeExamples` 加入缺失段或移除示例段。前端已传递开关 | “开关、原文要求、显式禁止、格式限制”没有统一的有效示例契约。模型生成和模板兜底都须核对；仅替换这一句不能覆盖模型原文中的弱化。最终正文已在 OUTPUT 等位置落实时，不强制增加独立示例段 |
| 资料串任务与编辑丢稿 | [optimization.ts](../apps/web/src/stores/optimization.ts) 历史载入清理遗漏补充资料，后续添加存在合并旧资料路径；[OptimizationResultPanel.vue](../apps/web/src/components/prompt/OptimizationResultPanel.vue) 保存事件后退出编辑，可能早于父层校验成功 | 任务和请求生命周期没有完整绑定；编辑提交缺少成功反馈契约。先修任务隔离、迟到响应和保存成功后退出，再完善资料实际发送状态。当前是源码确认的路径，本次未做浏览器复现，也不把它夸大为已证明跨用户泄露 |

[RequirementFidelityGuard](../services/api/src/main/java/com/promptoptimizer/enhancement/service/impl/RequirementFidelityGuard.java) 中假设语境过滤可能漏收包含“假设”的禁止句，属于应补反例的局部风险。不能直接认定最终必然漏掉“不得使用假设数据”，因为还有其他保护路径。验收须故意构造违反禁止要求的响应，核对最终可复制正文；不能只测试提取器列表。

### 2.3 为什么不能继续用局部补丁叠加

- 再加一条系统提示词，无法保证平台后处理不会重新补回旧句；必须核对模型原文、组装结果及复制正文。
- 完整句子相同不等于要求落实，表达不同也不等于遗漏。先对否定、比较符、数值单位、对象／年份／机构及确认条件建立可追溯覆盖，再局部替换旧护栏。
- 降低待确认数量不能以默认未知参数换取。没有上下文的“弄个排序”不能直接认定为 Python 快排；有 Python 学习、Java 订单或 Excel 资料时，才据此补相应边界与验收。
- 固定加章节、测试、代码附录会扩大交付。论文方法写作样例需要保留四类共 20 项任务、每模式每任务三次、两名独立盲评、公平信息对照、中文方法提纲不超过 1200 字且附表另计，以及研究尚未实施等条件；可补执行说明，不能另定评分尺度或把平台评测量表塞进用户研究。

## 3. 架构与逻辑收敛方案

不重建新平台，也不新增默认的多模型裁判链。沿用模块化单体、现有四要素 API、`TaskIntent`、事实卡片、确认决定和有限修复预算，按职责逐步收敛：

```mermaid
flowchart LR
  A[原始提示词与相关安全上下文] --> B[有效任务视图]
  C[已绑定的有效 Plan 决定] --> B
  B --> D[判断实质缺口与改写力度]
  D --> E[现有 Provider 增强调用]
  E --> F[高风险要求覆盖与定向修复]
  B --> F
  F --> G[统一组装与同版本展示复制]
```

“有效任务视图”是拟实施的内部职责，并非已有新 DTO／API。先覆盖目标、交付层级、相关依据、有效选择和重要未知；高风险条目按来源、对象、属性、条件、状态建立关联，不一次开发通用语义解析系统。

### 3.1 三项核心功能

| 功能 | 必须形成的稳定行为 | 不能采用的替代办法 |
| --- | --- | --- |
| 提示词增强 | 保留目标和有效框架；对真实缺口补必要输入输出、边界、组织和验收；背景不重复盘点缺失，短充分需求可少改 | 只重排原句；默认指定技术／专业参数；把报告降级成方案；依靠通用禁令制造篇幅 |
| Plan 确认 | 已确认选项进入对应执行段，旧选择在有效任务中失效；部分回答只解决对应对象和条件；新冲突仍可提出 | 把题目／答案整块附加在末尾；把“不确定”视为同意；因某一参数已确认就认为全部计算依赖已满足 |
| 示例参考 | 原文＋开关＋限制形成统一要求；明确要求下游提供相关的输入与预期输出，可用合规且标注清楚的演示材料 | “仅在用户要求时”；泛化为只有空表；将演示值当真实结果或已选参数；把用户示例与内部 few-shot 混为一谈 |

示例开关关闭不覆盖原文明确的示例要求；开关开启也不覆盖禁虚构、禁例或不兼容的严格格式。JSON 本身不是禁止示例的理由。平台仍在编写给下游的提示词，内部 few-shot 只服务优化器，不是用户要求的最终示例交付。

### 3.2 兼容与边界

- 修改共享输入时同步核对直接增强、Plan 提问／确认后检索、OpenAI 兼容序列化、Mock、组装器及兼容构造；不能只改某一家模型提示词。
- 保留 Plan 服务端所有权、输入绑定和失效机制；新视图及请求仍需适用的租户／工作区归属验证，不宣称旧缓存已全部具备相同隔离能力。
- 保存失败保持编辑态与全部草稿。展示和复制对应同一版本；编辑不覆盖原历史，历史恢复忠实还原所选版本。持久化编辑版本继续独立设计。
- 资料以“解析／检索／本次实际发送”分别报告；完整发送不等于模型理解或采纳。预览与发送使用同一安全表示，优先参考不绕过授权和预算。
- 每替换一段原句补回逻辑，先有保护否定、对象、条件、数值的测试及对应作品证据。失败时保留未通过项并限制受影响候选的放行范围，不靠删检查或成功重跑抹平。

## 4. 按优先级实施的路线图

详细依赖与退出条件以[方案第 5.1 节](./14-提示词增强与Plan最小干预优化方案.md#remediation-priority)为唯一排期入口，沿用 ME 编号，不新增一套并行工单。

| 优先级 | 工作范围 | 交付与验收重点 |
| --- | --- | --- |
| P0 | ME-00 最小基线；前移 ME-04／ME-05 的资料隔离、失败保稿及发送覆盖 | 先冻结 6–12 个代表样例和确定操作路径；A→历史 B→新增资料不回流 A，校验失败草稿保留，发送状态可核对。无需等待完整 PF／动态展示框架 |
| P1 | ME-03 最小共享任务视图＋ME-01 边界；ME-02 Plan 融合及示例契约 | 先统一目标／交付／依据／状态再做复杂融合。示例可独立修复；确认选择只落实到适用对象，旧选择不重问，示例语义在模型与兜底一致 |
| P2 | ME-03 其余实质补全、充分性与提问价值；ME-04 紧凑内容、撤销比较及再次增强；ME-05 贯穿 | 对模糊、充分、开放任务分别验证帮助；按中英文／排版变体回归。原始要求与当前稿分开，连续增强不累积模型自创要求 |
| P3 | ME-06 冻结候选验收 | 拟开放的两个 DeepSeek 模型、直接／Plan × 示例开／关、关键组合、真实目录、正常身份端到端及全仓库检查；候选任一严重退步不得被总分掩盖 |

ME-03 的**最小基础部分**前移，不代表先完成整个智能识别产品才能修 ME-02。完整 PF 策略组合、动态协议、PL 用户模板／反馈以及浏览器插件独立排期。默认智能补全不依赖它们。

每节点都评测实际作品，P3 只负责最终完整收口。保留既定十二类至少 24 个主场景及关键组合；30–50 题是可扩充候选池，不替代覆盖要求，也不自动证明统计显著。采用同材料、同有效确认信息、同执行模型与参数，区分优化器采样和固定提示词重复执行；Plan 对照组给相同答案，评测脚本不得替平台增强正文补答案。

分别记录任务完成、硬约束违反、无依据新增、修订负担、真实用量／成本和耗时，列胜／平／负／双方失败／未评审及严重退步。专业人员核验依既有用户决定放在上线后；上线前独立基础业务双评审、跨行业／专业样例、事实及安全检查仍执行。未通过的质量或能力范围如实登记，不能借延期放行已知严重缺陷。
