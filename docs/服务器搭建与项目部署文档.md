### 8.2 恢复与完整性核对

以下恢复命令为历史 `pg_restore` 的安全整理，增加单事务；仅在已确认的空目标执行：

```bash
# 恢复全部结构和数据，不沿用源数据库的对象所有者和 ACL；出错整体回滚
docker compose exec -T postgres pg_restore \
  -U prompt_optimizer -d prompt_optimizer \
  --no-owner --no-acl --single-transaction --exit-on-error \
  /backup/prompt.dump

# 查看表清单，并检查 Flyway 历史；不执行任何建号或重设密码操作
docker compose exec -T postgres psql -X -U prompt_optimizer -d prompt_optimizer -c '\dt'
docker compose exec -T postgres psql -X -U prompt_optimizer -d prompt_optimizer \
  -c 'SELECT installed_rank, version, description, success FROM flyway_schema_history ORDER BY installed_rank;'

# 恢复后更新优化器统计信息；这是复现补充，不是历史已执行记录
docker compose exec -T postgres psql -X -U prompt_optimizer -d prompt_optimizer -c 'ANALYZE;'
```

遇到 `public already exists`、缺扩展、字符集、权限或约束冲突，停止并核对目标结构，**不要删除报错行、忽略错误继续或直接套用清库命令**。单事务恢复的说明见 [PostgreSQL 官方文档](https://www.postgresql.org/docs/16/app-pgrestore.html)。

行数检查应在冻结写入的源库与恢复后的目标库分别执行，并保留对照结果。下面仅为关键表，不代替全量资源核对：

```sql
-- 包括逻辑删除记录在内核对全量数据，不读取邮箱、手机号、密码哈希或正文
SELECT 'tenant' AS table_name, COUNT(*) AS row_count FROM tenant
UNION ALL SELECT 'user_account', COUNT(*) FROM user_account
UNION ALL SELECT 'user_identity', COUNT(*) FROM user_identity
UNION ALL SELECT 'workspace', COUNT(*) FROM workspace
UNION ALL SELECT 'workspace_member', COUNT(*) FROM workspace_member
UNION ALL SELECT 'optimization_session', COUNT(*) FROM optimization_session
UNION ALL SELECT 'optimization_record', COUNT(*) FROM optimization_record
UNION ALL SELECT 'usage_event', COUNT(*) FROM usage_event
UNION ALL SELECT 'audit_event', COUNT(*) FROM audit_event;
```

源/目标还需核对：租户和工作区关联、身份唯一约束、管理员角色和引导状态、逻辑删除时间、序列值，以及经过授权抽样的内容完整性。行数相同不是全部内容相同的证明。Redis 会话不沿用，用户在新环境重新登录。

### 8.3 区分整库恢复与 Flyway 前向迁移

- **整库恢复**恢复某次快照的结构、数据和 `flyway_schema_history`；不能另手工建一套表再重复导入。
- **恢复原历史版本**：选择与备份匹配的 JAR / 迁移文件，核对已应用迁移校验后启动。本文默认先保持 `FLYWAY_ENABLED=false`，避免未确认的自动变更。
- **部署当前源码**：本版核对时当前目录最高已有 V38。先在恢复演练库核对待执行迁移及校验和，备份目标库，人工批准迁移窗口，再由受控迁移步骤执行。不能把“旧库里有 V13”理解为“当前应用无需迁移”。
- 已应用迁移不回改，不用 `repair`、删除历史行或重新跑 V1 来掩盖校验错误。当前项目未在本文交付独立生产迁移流水线，不能编造一条未经配置的 `mvn flyway:migrate` 当作已经可用。
- 如暂时选择应用启动触发 Flyway，必须明确这是一次获批的生产结构变更；用受控进程／迁移账号执行，完成后核对结果，再恢复普通运行配置。不要为省步骤让日常业务账号一直持有超级用户权限。
- 恢复准备时的 `FLYWAY_ENABLED=false` 只是避免提前变更结构。完成演练和审批后，若采用项目内启动迁移，应明确设置 `FLYWAY_ENABLED=true`，重建已核验的新 API 并核对实际待执行集合；不能长期关着迁移却运行依赖新字段的新代码。
- 新旧应用是否兼容数据库变更需逐个发布评估。数据库已前向迁移后，回滚旧 JAR 不保证可用。

## 9. 数据库远程管理：历史直连与更安全的替代

**日志确认的现状**：用户历史选择 `5432:5432`，L6:48 证明 10-24 仍发布到 IPv4/IPv6 全接口。L4 有 4,615 次口令认证失败及异常协议探测；这些请求已到达 PostgreSQL，但记录不足以确定每个来源。**应优先收紧，而不只是保留一条“建议白名单”的备注。** 本批未提供云防火墙、SSH 隧道和 PostgreSQL TLS 的现场配置。

复现主线使用 `127.0.0.1:5432:5432`，通过 SSH 隧道管理。已有数据库变更前先核对备份、现有连接者和维护窗口；确认 Compose 项目名及命名卷保持不变，只修改 postgres 的端口映射，不重新导库。重建数据库容器有短暂中断，应安排应用停写或暂停 API。流程为：

1. 在腾讯云控制台核对 IPv4/IPv6 入口，先限制数据库来源，保留 SSH 可用连接；不要把 5432 的来源设为任意地址。
2. 保留 Compose 配置副本，将映射改为回环，`docker compose config --quiet` 通过后，在维护窗口只重建 postgres，**不改卷、不执行 down -v、不重跑恢复**。
3. 确认原库/表仍在、数据库 healthy，恢复 API 并检查业务；重新查看端口应不再出现数据库的全接口映射。
4. 建立以下隧道后从 DBeaver 验证，再移除不再需要的公网数据库入站规则。只改 Docker 映射不等于全部云端访问规则已整理完成。

```powershell
# Windows：另开终端建立隧道，保持窗口打开；替换服务器地址及 SSH 账号
ssh -N -L 127.0.0.1:5433:127.0.0.1:5432 root@<SERVER_IPV4>
```

DBeaver 连接 `127.0.0.1:5433`，数据库仍是 `prompt_optimizer`，凭据在本机私下输入。也可使用 DBeaver 内置 SSH 功能，二者选一种，不要重复套隧道。

以下是**已有部署改回环映射时的维护命令**，不是本轮已执行操作。执行前必须完成上述备份、停写与卷名核对，且已经在编辑器中只改 postgres 的端口映射：

```bash
# 固定项目入口，校验修改后的配置；失败时不停止任何容器
cd /opt/prompt-optimizer/deploy
docker compose config --quiet

# 人工确认维护窗口和停写完成后暂停 API，避免数据库重建时仍有业务写入
docker compose stop api

# 只重建数据库容器，继续使用原命名卷，不新建数据库、不执行恢复
docker compose up -d --no-deps --force-recreate postgres
docker compose ps

# 确认数据库 healthy 后查看原表清单，核对未误切空卷
docker compose exec -T postgres sh -c 'psql -X -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\dt"'

# 检查映射；目标为回环 5432，而不是 0.0.0.0 或 IPv6 全接口
docker compose port postgres 5432

# 数据、健康与连接检查通过后再恢复 API；失败时保留现场按维护回滚方案处理
docker compose start api
docker compose logs --tail=100 api
```

不要因数据库检查失败继续执行 `start api`。关闭公网数据库来源后，从受控外部环境验证不能直连，并验证 SSH 隧道可用；不要把连接被拒绝本身当成数据丢失，也不要为恢复直连放开所有来源。

如果确有理由保留历史公网直连，另行批准、核对来源限制与 PostgreSQL TLS；不能直接把下面的历史配置当推荐默认值：

```yaml
# 历史事实：曾采用该映射；它默认发布至所有主机接口，不是回环映射
ports:
  - "5432:5432"
```

连接超时先检查路由、实际公网 IP、云防火墙、主机监听、容器映射和 PostgreSQL 认证策略，不能仅凭超时断言某一层故障。不要为方便排查放通 `0.0.0.0/0:5432`。

## 11. 前端构建与发布

### 11.1 Windows 构建生产包

```powershell
# Windows：在前端目录按锁文件安装依赖，再构建；不是启动 npm run dev
Set-Location 'E:\MyProject\prompt-optimizer-platform\apps\web'
npm ci
if ($LASTEXITCODE -ne 0) { throw '依赖安装失败，停止发布。' }
npm run build
if ($LASTEXITCODE -ne 0) { throw '前端构建失败，停止发布。' }

# 打包 dist 内部内容，关键是 -C dist .，避免再包含顶层 dist 目录
$webArchive = Join-Path $env:USERPROFILE 'Desktop\web.tar.gz'
tar -czf $webArchive -C dist .
if ($LASTEXITCODE -ne 0) { throw '前端归档失败，停止上传。' }

# 查看归档层级和校验值；入口应是 ./index.html 而非 dist/index.html
tar -tzf $webArchive | Select-Object -First 12
Get-FileHash -LiteralPath $webArchive -Algorithm SHA256

# 确认新包和旧回滚包已区分后上传；与 SFTP 上传二选一
scp $webArchive 'root@<SERVER_IPV4>:/opt/prompt-optimizer/private/web.tar.gz'
```

上传新包到服务器私密目录，旧包另存，不覆盖唯一回滚副本。L1 主要采用 zip，可二选一：

```powershell
# Windows：zip 备选方式，打包目录内容，不是 dist 文件夹本身
Compress-Archive -Path '.\dist\*' -DestinationPath (Join-Path $env:USERPROFILE 'Desktop\web.zip')
```

没有 `-C dist .` 或 `dist\*` 时，**tar.gz 同样可能多套一层**，不能概括为“tar 天然无嵌套”。检查归档内容才是依据。无痕窗口也不是判断版本正确的唯一证据，应核对 `index.html` 内容与引用资源。

### 11.2 服务器发布：保留上一版，不先删除 assets

**人工确认**：确认归档由本次已验证构建产生、SHA256 匹配、仅含前端静态文件，无绝对路径、`..` 路径穿越、秘密或不可信链接。下例按可信归档说明；不把陌生来源归档直接以 root 解压。

```bash
# 服务器：确认原始包，检查入口层级和传输校验值
cd /opt/prompt-optimizer
sha256sum private/web.tar.gz
tar -tzf private/web.tar.gz | head -20

# 新包只解压一次到独立目录；若已存在同名目录会失败，不覆盖它
site_release="web-next-$(date +%Y%m%d-%H%M%S)"
mkdir -m 0755 "$site_release" && tar -xzf private/web.tar.gz -C "$site_release"

# 必须先确认 index.html 存在，避免发布 web/dist 或 web/web
test -f "$site_release/index.html"
```

上述命令必须逐条确认成功；入口检查失败时停止，不进入切换。下面在**同一个 SSH 会话**定义并调用切换函数，用显式返回阻止失败后继续。首次安装没有旧 `web`，会跳过备份。

```bash
# 切换函数只接受本项目顶层的新目录，失败时返回，不继续覆盖
publish_web() {
  cd /opt/prompt-optimizer || return 1
  case "${site_release:-}" in
    web-next-[0-9]*) ;;
    *) printf '请先完成新包检查\n'; return 1 ;;
  esac
  case "$site_release" in
    */*|*..*) printf '目录名不合法\n'; return 1 ;;
  esac
  test ! -L "$site_release" && test -f "$site_release/index.html" || return 1
  test ! -L web || { printf '现站点为符号链接，请按现有发布机制处理\n'; return 1; }

  # 保留旧哈希资源，兼容持有旧 HTML 的浏览器；不覆盖新包中的资源
  if [ -d web/assets ]; then
    mkdir -p "$site_release/assets" || return 1
    cp -an web/assets/. "$site_release/assets/" || return 1
  fi

  # 仅给公开静态目录读权限，private 目录仍保持 700
  chmod 755 /opt/prompt-optimizer || return 1
  chmod -R a+rX "$site_release" || return 1

  # 保留上一版，不删除站点；现有同名备份时停止，避免 mv 隐式嵌套
  site_backup="web-bak-$(date +%Y%m%d-%H%M%S)-$$"
  test ! -e "$site_backup" && test ! -L "$site_backup" || return 1
  if [ -e web ]; then
    mv -T -- web "$site_backup" || return 1
  fi
  if ! mv -T -- "$site_release" web; then
    printf '新目录切换失败，保留新包并尝试还原上一版\n'
    if [ ! -e web ] && [ -d "$site_backup" ]; then
      mv -T -- "$site_backup" web || return 1
    fi
    return 1
  fi

  # 确认入口，并记录可回滚的旧目录名
  ls -lh /opt/prompt-optimizer/web/index.html
  printf '上一版目录（首次发布可能不存在）：%s\n' "$site_backup"
}

# 人工确认维护窗口后调用；有失败立即停止，不继续宣布发布成功
publish_web
```

这是对历史“删除 assets 再解压”的安全修正，仍是一遍解压、目录改名，没有临时目录再全量复制。两次 `mv` 之间有短暂不可用窗口；不能宣传为原子或零停机发布。若切换失败，保留新目录并把刚生成的旧目录恢复为 `web`；只操作已核实的本次目录，不使用日期通配符批量删除。

纯静态文件替换通常不需要重启 Nginx；修改站点配置才先 `nginx -t`、再 reload。旧资源保留一段观察期后由独立清理流程处理，避免磁盘无限增长。

### 11.3 原件中的嵌套目录修复记录

历史实际出现的是 `web/web/index.html`。当时通过 `mv web web-nested`，再 `mv web-nested/web web` 提出内层站点。

这属于**指定现场的故障修复**，不是每次部署都应运行的命令。若今天遇到类似情况，先检查绝对路径和备份目标是否已存在，再只移动确认的内层；外层目录保留备查，不能无条件递归删除。压缩包和数据库备份都必须移出公开 `web/`。

## 12. 宿主机 Nginx、DNS、HTTPS 与可信代理

### 12.1 安装并编辑站点

**人工确认**：本指南使用宿主机 Nginx，API 仅绑定回环。先检查 80/443 是否已被其他服务或容器使用，不能同时启两套 Nginx。

```bash
# 服务器：检查端口并安装宿主机 Nginx
ss -lntp | grep -E ':80\b|:443\b' || true
sudo apt-get install -y nginx
sudo systemctl enable --now nginx
nginx -v

# 修改已有配置前先备份，备份不要放进 sites-enabled
if [ -f /etc/nginx/sites-available/prompt-optimizer.conf ]; then
  sudo cp --backup=numbered -p /etc/nginx/sites-available/prompt-optimizer.conf /etc/nginx/sites-available/prompt-optimizer.conf.before-edit
fi
sudo nano /etc/nginx/sites-available/prompt-optimizer.conf
```

以下是**初次 HTTP 预检配置内容**。替换域名；已经配置 HTTPS 的站点不能用它覆盖掉现有 443 配置：

```nginx
# 文件内容，不是终端命令
server {
    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;
    root /opt/prompt-optimizer/web;
    index index.html;
    charset utf-8;

    # 沿用历史上限；只是代理请求体上限，不证明应用可处理同等大小文件
    client_max_body_size 128m;
    gzip on;
    gzip_vary on;
    gzip_min_length 1024;
    gzip_types text/plain text/css application/javascript application/json image/svg+xml;

    # 缺失资源应返回 404，不能把 JS 请求回退成 HTML
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        try_files $uri =404;
    }

    # 入口文件不长期缓存
    location = /index.html {
        add_header Cache-Control "no-store";
    }

    # Vue history 路由：页面路径回退到入口
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 不带尾部斜杠，保留 /api/v1/... 前缀
    location /api/ {
        proxy_pass http://127.0.0.1:9000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        # 单层公网 Nginx 覆盖客户端伪造的转发头；加 CDN 后须重新设计可信链
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 10s;
        proxy_send_timeout 180s;
        proxy_read_timeout 180s;
    }
}
```

历史使用 `$proxy_add_x_forwarded_for`；上面的覆盖写法是单代理部署的**安全补充**。URI 是否重写取决于 `proxy_pass` 有无 URI 部分，说明见 [Nginx 官方文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass)。

```bash
# 启用项目配置，先确认同名链接不存在或确实指向本项目
sudo ln -s /etc/nginx/sites-available/prompt-optimizer.conf /etc/nginx/sites-enabled/prompt-optimizer.conf

# 人工确认默认链接确为系统默认站点后，将其移出启用目录以便恢复
if [ -L /etc/nginx/sites-enabled/default ]; then
  sudo mv -T -- /etc/nginx/sites-enabled/default "/etc/nginx/default.disabled.$(date +%Y%m%d-%H%M%S)"
fi

# 检查启用项、语法，再重载；测试失败不能继续 reload
ls -l /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# 本机验证必须同时看内容，避免把默认欢迎页的 200 当应用成功
curl -sS -H 'Host: example.com' http://127.0.0.1/ | grep -o '<title>[^<]*</title>'
curl -sS -H 'Host: example.com' http://127.0.0.1/workbench | grep -o '<title>[^<]*</title>'
curl -sS -H 'Host: example.com' http://127.0.0.1/api/v1/auth/capabilities
```

上述检查期望项目标题和 JSON，而不是 `Welcome to nginx!`、错误页或拦截页。`/workbench` 的 HTML 回退成功不等于该受保护页面已经通过登录授权。

### 12.2 DNS 与端口

域名解析平台添加 A 记录：`@`、`www` 指向实际服务器 IPv4。先核实备案和接入状态，不能把域名实名误当 ICP 备案通过。若不使用 `www`，应同时从 DNS、Nginx 和证书申请中移除，而不是给未解析的域名申请证书。

```bash
# 查询 DNS；DNS 返回正确 IP 仍不等于外网链路或应用可用
dig +short example.com
dig +short www.example.com

# 查看本机监听与防火墙，不先扩大放行范围
ss -lntp | grep -E ':80\b|:443\b|:5432\b|:6379\b|:9000\b' || true
sudo ufw status verbose
```

| 端口 | 主线要求 |
| --- | --- |
| SSH 22 | 限制运维来源并保留可用会话，修改规则前防止锁出服务器 |
| HTTP 80 / HTTPS 443 | 满足公开上线条件后开放网站入口；80 还可能用于 ACME 验证及跳转 |
| PostgreSQL 5432 | 主线仅回环；历史直连例外须明确来源 `/32`、TLS 与维护窗口 |
| Redis 6379 | 不发布公网端口 |
| API 9000 | 仅服务器回环映射供 Nginx 使用 |
| SMTP 465 | 出站目标端口，不新增服务器入站规则 |

仅在 UFW 已启用、入口开放已获确认时运行：

```bash
# 允许已确认公开的网页端口，不顺带开放数据库、Redis 或 API
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
```

腾讯云控制台防火墙也须配置相应规则。不要以“本机 curl 成功”代替外网验证，也不要在 SSH 22 已进入认证阶段时继续盲目放开其他端口。

### 12.3 证书与续期

历史使用 Certbot Nginx 插件。域名解析、域名访问限制、80 验证链路和申请次数均需先核实；已有证书先检查，不重复申请：

```bash
# 新机尚无工具时按本机发行版安装；不要混用多个 Certbot 安装渠道
sudo apt-get install -y certbot python3-certbot-nginx

# 查看已有证书元数据，不读取或打印私钥；已有有效证书时不重复签发
sudo certbot certificates

# 人工确认域名控制权、DNS 和申请窗口后签发，按提示完成 HTTPS 跳转
sudo certbot --nginx -d example.com -d www.example.com

# 签发后检查配置及真实域名 TLS，验收不使用 -k
sudo nginx -t
curl --connect-timeout 5 --max-time 20 -sS -o /dev/null -w '%{http_code} %{content_type}\n' https://example.com/

# 检查定时器并演练续期，不能只看到证书就宣布自动续期完成
systemctl list-timers --all | grep certbot || true
sudo certbot renew --dry-run
```

命令基于原件的 APT 路线整理；发行版不同或已有 snap/pip 安装时跳过安装，按 [Certbot 官方说明](https://certbot.eff.org/instructions?ws=nginx&os=pip)核对渠道，勿混装。不要将历史证书到期时间当作当前证书期限。

本机定向检查 HTTPS 时，应使用正确域名/SNI 并保留证书校验：

```bash
# 保留域名和 SNI，只将连接地址定向到本机，区分 TLS 配置与外网链路
curl --resolve example.com:443:127.0.0.1 --connect-timeout 5 --max-time 20 \
  -sS -o /dev/null -w '%{http_code}\n' https://example.com/
```

L1:458–459 留有检查定时器及 `certbot renew --dry-run` 的命令，但没有该次输出；L3:129–216 的 29 次 `Finished certbot.service` 更新了旧版“定时服务完全无证据”的判断，但不能证明实际续签或 dry-run 通过。检查证书到期时间、任务结果和续期验证链路仍不可省略。

原件曾使用 `curl -k`、IP 直连和手动跳过证书告警作为诊断；它们**不能证明证书可信，也不是面向用户的正式访问方式**。

### 12.4 Cookie 与真实客户端 IP

HTTPS 就绪后在实际 `private/api.env` 核对：

```dotenv
# 会话 Cookie 仅经 HTTPS 发送；SameSite 保持同源需要的 Lax
AUTH_COOKIE_SECURE=true
AUTH_COOKIE_SAME_SITE=Lax
AUTH_CORS_ALLOWED_ORIGIN=

# 历史采用 Tomcat 原生转发头处理；必须同时限定可信代理边界
SERVER_FORWARD_HEADERS_STRATEGY=NATIVE
```

**可信代理人工确认**：API 仅回环发布，公网边缘 Nginx 覆盖转发头。容器看到的直接连接可能是 Docker 网关地址而不是 127.0.0.1；上线前按实际网络核对并收紧 Tomcat 的可信内部代理范围，验证合法客户端地址可恢复、伪造转发头不可越过 IP 限流。原件没有足够证据证明这项安全验证已完成。新增 CDN、多代理或公网 API 入口时必须重新评估，不凭一个 `NATIVE` 宣布完成。

原件“未设 Secure 会让 HTTPS 浏览器不保存 Cookie”的说法不准确：`Secure=false` 不阻止 HTTPS 保存 Cookie，但失去仅 HTTPS 发送的保护。不要为兼容裸 IP/HTTP 测试而降低生产 Cookie 保护。

当前安全实现中，Session Cookie 为 HttpOnly；`XSRF-TOKEN` 为前端双提交 CSRF 而刻意允许脚本读取。不能要求两个 Cookie 都为 HttpOnly，也不能通过关闭 CSRF 修复 403。

```bash
# 服务器：检查真实域名首页及 SPA 子路由状态
curl --connect-timeout 5 --max-time 20 -sS -o /dev/null -w '首页 %{http_code}\n' https://example.com/
curl --connect-timeout 5 --max-time 20 -sS -o /dev/null -w '工作台路由 %{http_code}\n' https://example.com/workbench
```

```bash

# 备份脚本：只导出和检查数据库，不修改业务数据，不自动清理旧备份

# 由数据库容器取本身的连接用户和数据库名，不打印密码

docker compose exec -T postgres pg_restore --list < "$backup_partial" >/dev/null
mv -- "$backup_partial" "$backup_final"
printf '数据库备份已生成并通过归档目录检查\n'
```


## 15. 失败操作、过时说法与风险修正

### 15.1 分层诊断命令

以下归并原件多次出现的诊断动作；只读检查先行，不凭一个现象重配安全组、Nginx 或 DNS。域名需替换为实际目标，日志分享前脱敏。

```bash
# 服务器：查看 Nginx 运行状态和语法，不直接重写站点
sudo systemctl status nginx --no-pager
sudo nginx -t
ls -l /etc/nginx/sites-enabled/

# 查看服务日志，区分配置错误、启动失败和外部链路错误
sudo journalctl -u nginx -n 30 --no-pager
sudo tail -n 20 /var/log/nginx/error.log

# 检查监听和主机过滤规则，不新增放行规则
ss -lntp | grep -E ':80\b|:443\b|:5432\b|:9000\b' || true
sudo ufw status verbose
sudo iptables -L INPUT -n --line-numbers

# 查看 HTTP 响应头，判断跳转指向本域 HTTPS 还是接入商拦截页
curl --connect-timeout 5 --max-time 20 -sS -I http://example.com/

# 带真实域名 SNI 检查 TLS；与第 12.3 节正常 curl 的主机名校验结合判读
timeout 15 openssl s_client -connect example.com:443 -servername example.com -verify_return_error -verify_hostname example.com </dev/null
```

Windows 侧可辅助定位网络；这不是原件中遗漏的工具参数恢复，而是复现补充：

```powershell
# Windows：核对实际 DNS 和 TCP 443；TCP 成功不代表 TLS、HTTP 或应用通过
Resolve-DnsName 'example.com'
Test-NetConnection 'example.com' -Port 443

# 记录真实 HTTP 状态，不输出会话 Cookie 或完整请求体
curl.exe --connect-timeout 5 --max-time 20 -sS -o NUL -w '%{http_code}\n' 'https://example.com/'
```

`openssl` 自身输出的证书链验证、`curl` 的域名校验、Nginx 本机响应和外部设备访问要分别看；不要用其中一项替代其余检查。

### 15.2 已纠正的历史步骤

| 原记录中的情况 / 指令 | 问题 | 本文处理 |
| --- | --- | --- |
| `FROM` / `RUN` 贴进 SSH | Bash 不理解 Dockerfile 指令 | 第 5 节分开文件内容与构建命令 |
| 本机 `docker compose ... up -d` | 业务库实际是原生 PostgreSQL，另启 Redis 又占 6379 | 使用已核实的 DBeaver 连接和原生客户端，不停旧库、不另建空库 |
| `service postgres is not running` | 在错误的容器实例上导出 | 先确认真正数据来源，而不是继续修一个无数据容器 |
| 在 `private` 执行 `docker compose` 找不到配置 | 当前目录不对 | 固定 `deploy`；不能由此判定 Docker 没安装 |
| `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` | 对已有库会删除整套 schema 内业务对象；历史只用于最初空目标 | **仅作为危险历史文本保留，不进入主线执行块**；失败恢复改用确认过的干净目标 |
| 直接改 `POSTGRES_PASSWORD` 期待旧库密码改变 | 初始化变量不等于轮换 | 受控数据库密码轮换后同步客户端配置 |
| `install -o 10001` 报 invalid user | 本次目录授权未成功；不能跳过 stat 继续 | 数字 chown + 700，并验证容器 UID |
| `chmod 777 /tmp` | 可能清掉系统共享临时目录的 sticky bit，不是下载日志的必要条件 | 第 15.3 节先核实，确认后只恢复该目录自身为 1777；不递归操作 |

### 15.3 本批历史中特别需要核对的 /tmp 与 SSH

#### /tmp：0777 不等于正确的 1777

L1:643、L2:633 的 `chmod 777 /tmp` 是命令留痕，不是当前权限实测。系统共享临时目录通常需要 **1777**：普通用户可以创建临时文件，但 sticky bit 限制删除/改名他人文件。0777 不会自动让内部 0600 文件变得可读，但会失去这层目录保护。[GNU 权限说明](https://www.gnu.org/s/coreutils/manual/html_node/Mode-Structure.html)

```bash
# 只检查 /tmp 自身的类型、所有者与权限；不列出他人的临时文件
ls -ld /tmp
stat -c '%a %u:%g %F %n' /tmp
```

若确认是标准 root 所有的真实目录、当前确为 0777，并已确认修复，可执行下面的**非递归**调整；它不是“现在把所有临时文件改权限”：

```bash
# 人工确认后恢复 /tmp 自身 sticky bit；遇符号链接或非 root 所有则停止
if [ -d /tmp ] && [ ! -L /tmp ] && [ "$(stat -c '%u' /tmp)" = 0 ]; then
  sudo chmod 1777 /tmp
  stat -c '%a %u:%g %F %n' /tmp
else
  printf '目录类型或所有权异常，停止调整并人工核对\n'
fi
```

下载日志应使用同一 SSH/SFTP 账号或受控导出副本；无需更改整个 /tmp 的权限，也不要将私密日志目录改成 777。原始记录保留在受限目录，公开教程不附带原件。

#### SSH：不为了部署开启更多口令入口

L1:9–14 有开启 PasswordAuthentication 和重启 SSH 的历史命令，不包含最终有效配置。先只读核对：

```bash
# 检查 SSH 配置语法，不重启服务
sudo sshd -t

# 查看基础有效配置；如有 Match 条件，还需按实际运维来源进一步核对
sudo sshd -T | awk '$1 == "passwordauthentication" || $1 == "pubkeyauthentication" || $1 == "permitrootlogin" { print }'
```

不要把历史 `sed` 开启口令登录纳入新机必做流程。后续收紧应先配置并用第二个会话验证密钥登录，再保留当前会话进行受控变更，避免锁出；本轮不改 SSH 认证方式、不生成或索取私钥。
