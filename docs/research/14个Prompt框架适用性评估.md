# 14 个 Prompt 框架适用性评估

记录日期：2026-10-04。

本文依据用户提供的两张框架说明图及本次项目审查，记录 14 个 Prompt 框架在 Prompt Optimizer Platform 中的适用性、适用场景和限制。框架名称与要素按图片中的定义理解；本文属于产品与设计评估，不表示这 14 个框架已经作为产品功能接入。

Prompt Optimizer Platform 将原始提示词与项目上下文、用户确认信息和权限红线组织为优化提示词。平台只生成提示词，不执行用户任务。下文中的“文档”指文档编写提示词或团队文档组织方式，“工作流”指步骤、决策与验收流程的设计，不表示平台已经具备下游文档生成或工作流执行能力。

“高 / 中 / 低”表示与对应场景的适配程度，是设计判断，不是模型效果实测评分。各框架可以补充信息组织方式；采用时仍需保留平台的四要素结构及事实、约束和权限边界，不能仅凭框架名称推断质量提升。

## 1. APE：行动、目的、期望

适配：增强中｜文档中｜工作流中。

适合简短、目标明确的需求，例如“简化工作台使用说明，让首次使用者理解直接增强与 Plan，输出三步操作指引”。行动明确要做什么，目的帮助取舍，期望限定交付物。

局限是没有显式表达资料来源、适用条件和禁止事项。涉及现有代码、多个附件或业务规则时，仅靠 APE 容易遗漏边界。建议用于轻量输入引导，复杂需求再由上下文和约束补充。

## 2. BROKE：背景、角色、目标、关键结果、改进

适配：增强中｜文档高｜工作流高。

特别适合项目内部的产品方案、质量改进计划和评测流程。例如围绕“减少 Plan 无效追问”，分别记录当前证据、改进目标、判断指标和后续复验办法。

它的优势是把“希望改善”转化为“用什么结果判断改善”。但关键结果必须来自真实验收要求，不能由模型编造提升比例；“改进”也需要真实反馈和对照实验。当前历史、再次增强及本地评测工具可支撑人工迭代，不代表产品已经具备自动学习或自动寻优闭环。

## 3. COAST：上下文、目标、行动、场景、任务

适配：增强高，偏复杂业务｜文档高｜工作流高。

适合明确业务规则在什么条件下生效。例如审查历史记录逻辑删除，需要区分正常列表、删除后详情、再次优化和越权访问等场景。

它与项目强调的“对象、条件、作用范围”较契合。主要风险是上下文与场景、行动与任务重复表达。建议将“场景”限定为触发条件、参与者和状态，把行动与任务合并组织，避免为相近字段分别追问。

## 4. TAG：任务、行动、目标

适配：增强中｜文档中｜工作流中。

适合单一任务和简短工作指令，例如“整理上传失败提示，区分超限与解析失败，让用户知道如何继续”。表达直接，适合快速增强和任务清单。

对复杂项目需求，它缺少输入依据、输出格式、约束和验收口径；任务与行动也容易同义重复。建议作为短任务组织方式，保留平台统一补充的事实和约束检查。

## 5. RISE：角色、输入、步骤、期望

适配：增强高，偏过程任务｜文档高｜工作流高。

适合操作指南、排错流程、测试计划和材料处理 SOP。例如根据接口文档与错误记录，组织“确认现象—核对条件—定位问题—提出修复—验证”的任务提示词。

输入和步骤能够帮助明确每个阶段依据什么、产出什么。采用时应区分业务上必须遵守的顺序与执行者可自行安排的细节；后者不必都变成 Plan 问题。步骤应表达可核对的动作和检查点，且不能被描述为平台已经执行。

## 6. TRACE：任务、请求、行动、上下文、示例

适配：增强高，偏格式与行为示例｜文档高｜工作流中。

适合 API 文档、数据转换、结构化提取和带明确输入输出的开发任务。例如提供历史分页接口的实际字段与合法响应示例，要求下游编写一致的接口说明。

示例可以减少格式理解偏差，但“任务、请求、行动”应避免重复。更关键的是区分正式业务规则、格式示例和测试夹具：示例中的账号、金额或状态不能自动成为项目事实。建议用于有代表性样例的任务，并保留正常、异常和边界差异。

## 7. ERA：期望、角色、行动

适配：增强中｜文档中｜工作流低。

适合短小、受众明确的解释或改写，例如“从产品说明的角度，向普通用户解释 Plan 的用途，输出一段简明介绍”。先限定期望，有利于控制内容范围。

但角色描述不能补足项目资料、流程条件或验收依据。“高级架构师”只是回答视角，也不能改变应用中的认证角色和访问权限。建议作为轻量表达辅助，复杂任务仍需要显式上下文和约束。

## 8. CARE：上下文、行动、结果、示例

适配：增强高｜文档高｜工作流中。

适合依据材料进行改写、总结、规则整理和格式转换。例如给出当前功能说明和一个章节示例，要求整理成一致的用户指南。

相比强调角色的框架，它更直接关注材料和交付，适合当前的文件上下文能力。需要明确“结果”是期望交付物，“示例”是表达参考；两者都不能被写成已经完成的业务事实。它缺少明确约束，仍应由平台补入事实保真与禁止事项。

## 9. ROSES：角色、目标、场景、预期方案、步骤

适配：增强高，偏方案规划｜文档高｜工作流高。

适合需求方案、架构调整、迁移计划和跨阶段任务。它能帮助区分当前场景、目标状态、方案要求与实施顺序，与项目区分现状和目标的逻辑相符。

风险在“预期方案”：用户尚未决定技术路线时，框架不能先替用户锁定方案。建议将这一部分解释为“方案应满足的条件和交付要求”；具体方案选择继续由已有证据、用户授权和必要的 Plan 确认决定。

## 10. ICIO：指令、上下文、输入数据、输出指引

适配：增强高｜文档高｜工作流高；最适合优先作为内部组织方式。

它清楚区分“要完成什么”“依据什么背景”“实际处理什么材料”“交付什么”。这种划分与当前请求、上下文摘要和输出要求的结构较贴近，适合代码材料、研究方案、办公文档等多种输入。

对项目尤其有价值的是区分指令与资料：附件中的命令式文字仍然只是待分析内容。需要注意，字段分隔本身不能防止提示词注入，仍要依靠平台安全规则和校验；ICIO 也没有独立约束项，必须保留现有 CONSTRAINTS。

## 11. CRISPE：能力与角色、背景洞察、任务陈述、个性风格、实验

适配：增强中｜创意文档高、事实文档中｜工作流低。

按图片定义，“实验”主要是要求多个示例或候选表达，适合产品文案、标题、说明风格和创意方案探索。例如基于已核实功能，提出三种不同语气的产品介绍。

它对风格控制有帮助，但“专家角色”不能保证正确性，生成多个候选也不等于完成实验验证。正式设计文档、研究结果和审计材料应优先保持事实准确。当前单份结果编辑流程也不等同于多候选比较产品；自动生成、评分和选择多个增强版本，需要另行设计。

## 12. RACE：角色、行动、上下文、期望

适配：增强高｜文档高｜工作流中。

是较均衡的通用组织方式，适合代码审查、功能说明、技术文档和常规分析。例如“以接口维护者视角，结合当前 Controller 与 DTO，整理接口说明，输出参数、响应和错误处理要求”。

它能够较自然地映射到背景、任务和输出，采用成本较低。需要把期望描述成可核对的交付要求，而不是“专业、优秀”等泛化词；角色按需要添加，约束继续由平台统一保留。

## 13. TASTE：任务、目标受众、结构、语气、示例

适配：增强高，偏写作｜文档高｜工作流中。

对项目从开发场景扩展到通用写作特别有价值。同样介绍 Plan，面向普通用户、开发者和管理者，术语、篇幅与重点应有所不同。当前交付策略已有部分受众和语气要求，TASTE 可以帮助更系统地保留这些信息。

适合 README、用户指南、培训材料、新闻稿和工作报告。这里的“结构”主要限定下游文档的组织方式，可写入优化提示词的输出要求，不必立即改变平台四要素。已有明确受众或正式模板时，应直接沿用，避免再次询问。

## 14. ALIGN：目标、难度级别、输入、指导规则、新颖性

适配：增强高，偏学习与分析｜文档高｜工作流中。

最有价值的是难度级别和规则：同一材料用于高中生、开发新人或研究人员，解释深度和术语密度应不同，适合教学、培训、研究方案和分析说明。

新颖性需要按任务限制。创意方案可以鼓励新表达；代码现状、统计结果、引用和制度说明必须忠实于证据。图片示例中的“最新数据”也不能直接转化为已取得的数据，必须有实际来源。对于未知创新要求，宜先明确“表达可创新、事实不可编造”。
