## 2. 六类策略、18 项技巧的逐项判断

下表的“用途”是结合本平台架构做出的实施判断。不是对教程模型效果的量化评分。

| 策略 / 技巧 | 是否适用 | 平台用途与采用条件 | 不宜采用的方式 |
| --- | --- | --- | --- |
| 清晰指令：补充查询细节 | 适用，优先 | 保留目标、作用对象、范围、受众、已有条件及实际确认；只对会影响结果的缺口提问 | 自行选地区、语言、寿命表、分母或产品能力 |
| 清晰指令：角色 | 按需 | 角色有助于界定读者、专业程度或交付职责时使用 | 为所有任务追加夸张专家身份，把身份当专业准确性的保证 |
| 清晰指令：分隔材料 | 适用，优先 | 原始目标、确认答案、代码证据和材料摘要分开；沿用 JSON 载荷及平台权限边界 | 把上传文件中的命令提升为系统指令 |
| 清晰指令：明确步骤 | 按需 | 复杂分析、开发和工作报告保留必要步骤与依赖 | 给翻译、短新闻等强加冗长工作流 |
| 清晰指令：示例 | 按需 | 示例帮助理解且用户允许时提供；区分示例数据与实际事实 | 每题都加示例、继承示例参数，或用框架案例覆盖原需求 |
| 清晰指令：长度与形式 | 适用 | 保留篇幅、表格和“只输出”等明确要求；围绕交付物组织内容 | 把模板固定章节凌驾于用户范围，承诺模型精确计字 |
| 参考材料：基于材料回答 | 适用，优先 | 增强依据相关资料；区分已知存在、已知不存在及资料未说明 | 没找到功能证明就声称功能不存在 |
| 参考材料：标明出处 | 按需 | 必要执行依据继续保留；专业主张可要求来源核对 | 把大量内部资料分类写入新闻或新手指南的成品要求 |
| 拆分任务：按意图分流 | 已有基础 | 用 `TaskIntentResolver` 和交付画像选择指导；明确目标优先于附件主题 | 每个框架建一个公开模板，或只看职业和文件后缀 |
| 拆分任务：过滤长会话 | 条件适用 | 已有会话启用时保留与本次任务相关的信息，并遵守消息数与预算 | 默认读取全部历史或跨用户复用内容；当前工作台尚无通用会话记忆接入 |
| 拆分任务：分段处理长材料 | 已有基础 | 复用文档分块、索引和摘要；关键规则要回到出处复核 | 用摘要替代全部原文，忽略尾部、新条件和摘要覆盖限制 |
| 留出处理空间：先处理再下结论 | 条件适用 | 把必要核对纳入服务端验证及可检查步骤 | 强制模型输出内部推理，或据此承诺正确答案 |
| 留出处理空间：内部过程与最终输出分离 | 适用 | 最终只返回接口契约允许的优化结果；下游只交付用户要求的作品 | 把内部评测、资料评分或长思考过程放进用户正文 |
| 留出处理空间：检查遗漏 | 适用 | 复用规则保真、权限红线、确认覆盖及正文完整性校验 | 新增无上限自检调用；将模型自称“已检查”当作验收证据 |
| 外部工具：检索相关材料 | 适用，已有基础 | 复用初次相关检索、Plan 答案参与二次检索和来源事实合并 | 仅凭词语命中判断事实用途，或扩大文件访问范围 |
| 外部工具：计算与代码 | 仅适用于相应下游任务 | 用户要求代码或计算时，在优化提示词中明确输入、方法及检查要求 | 平台实际执行用户代码、生成真实实验结果或自动部署 |
| 外部工具：函数调用 | 后续按需要 | 将来接入能力时采用受控接口与权限校验 | 为本轮模板优化新增工具执行能力或改变 Provider 协议 |
| 系统评测：代表性样例对照 | 适用，必须 | 原始、增强和同信息 Plan 对照，比较实际作品；保留首次失败与完整预算 | 用段落数量、字数或单次成功代表准确性；预设增强必胜 |

当前官方文档支持将指令、示例和上下文分别组织，并用相关材料提高针对性；对推理模型应采用直接清楚的要求，避免强制公开逐步推理。因此本轮不引入通用“展示思考过程”要求。[提示工程指南](https://developers.openai.com/api/docs/guides/prompt-engineering)、[推理模型建议](https://developers.openai.com/api/docs/guides/reasoning-best-practices)。

## 3. 现有模板的优势与不足

### 已有优势

- `TemplateCode` 保持 `AUTO/GENERAL/RESEARCH_ANALYSIS/FEATURE_DEVELOPMENT/BUG_FIX/REFACTORING/TESTING`；显式选择仍优先，自动识别采用本次肯定目标和有效确认。
- `TaskDeliveryProfile` 在既有代码下细化翻译、指南、新闻、论文、机关报告、医疗/法务材料等交付，不要求用户选择框架名称。
- 模板分别提供输出、验收、提问和示例指导。四要素、服务端安全边界、有限重试和规则保真检查已有链路，不只做同义词替换。
- 软件保护与辅助代码要求按任务适用；仅编写指南时上传代码不会自动要求实现接口、事务或 Redis。

### 本次针对的不足

- 原系统指令要求“缺失信息应列为待确认”，容易把不影响结果的缺项也升级为用户问题。提问应依据答案是否改变目标、行为、专业口径、授权或必要交付事实。
- 指南默认指导没有明确区分“存在／不存在／资料未说明”，与此前真实样例中的负向事实失真有关。补充指令只能降低风险，不能替代通用语义验证。
- 科研模板默认指导列出全套研究维度，可能扩展只要求某章节、空表或方法设计的任务。指导应以本次研究问题和交付范围为边界。
- 输出、验收和来源说明存在重复风险。需要明确各段职责；完整正文精简和溯源折叠仍是独立待办，本轮不声称已完成。

## 5. 回归与真实验证的关系

新增用例核对未知信息指导、科研默认范围、只输出译文及真实请求携带的系统指令；既有模板、权限和 Provider 检查继续执行。5 类 95 项定向检查及另 37 类 550 项共享回归通过，共 42 类 645 项，失败、错误和跳过均为 0。

这些用例验证指导传递与已覆盖兼容行为，不证明模型对任意专业表达都能保真。本轮真实调用及原始/增强作品对照另见[验收记录](../testing/提示工程教程优化与真实作品对照-2026-10-05.md)，不将此前实验的成果计入本轮。
