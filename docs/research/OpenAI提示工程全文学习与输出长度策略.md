## 2. 全文经验在本平台的采用边界

以下是结合项目做出的实施判断，技术实现状态以代码和验收记录为准：

| 范围 | 本平台的采用方式 | 要保留的边界 |
| --- | --- | --- |
| 指令和细节 | 沿用目标、对象、读者、范围及明确限制；真正影响结果的缺口才进入Plan | 信息充分时少改；不自行选择地区、专业参数或产品能力 |
| 角色、步骤、示例 | 按交付物决定需要哪些指导 | 专家身份不等于准确；短翻译不强加工作流，示例不变成真实数据 |
| 长度和形式 | 明确作用于哪个交付物，必要时提供组织建议 | 段落数不能替代字数硬要求，Token预算不能当作字数 |
| 参考资料和出处 | 先判断相关性与资料用途，再把结论回连原文 | 测试样例、草稿与现状分开；未说明不等于不存在 |
| 意图、会话、长材料 | 以本次目标分流；复用有授权的检索和分块 | 摘要可能遗漏，中尾部规则要核对；不扩大文件或身份范围 |
| 核对和内部过程 | 检查规则、遗漏与最终交付，保留必要解释 | 不强制公开内部推理，不用无限自检调用代替验证 |
| 检索、计算和工具 | 检索服务于相关资料；准确计数可以由评测工具执行 | 平台只生成提示词，不执行用户代码、交易、临床决定或生产部署 |
| 系统评测 | 同材料、同答案条件比较实际作品，保留失败 | 开放题不要求逐字等于答案卡；AI评分须核验，不能预设增强必胜 |

## 3. 当前代码已吸收什么，尚缺什么

`services/api/src/main/java/com/promptoptimizer/provider/domain/PromptOptimizationGuidance.java`：

- `ENHANCEMENT` 已规定信息充分时少改、各段分别承担背景/任务/输出/约束职责、合并同对象同条件的重复表述，并使“只输出”等明确限制优先。
- `PLANNING` 已规定只问影响目标、行为、专业口径、授权或交付事实的决定。标题组织和普通排版原则上由执行者处理。
- 上一轮未根据长度补充段落数／要点数。本轮后续为明确新闻正文范围补了可调整的组织建议（见第8节），没有新增独立篇幅规划模型，也不声称模型可精确计字。

`services/api/src/main/java/com/promptoptimizer/provider/infrastructure/openai/OpenAiCompatiblePromptEnhancementProvider.java`：

- 增强System Prompt引用`ENHANCEMENT`，Plan引用`PLANNING`；输出仍为现有JSON契约。BACKGROUND、TASK、OUTPUT、CONSTRAINTS这四个**提示词段落**不等于下游作品必须只有四段。
- 结构化修复核对JSON、段落字段、问题/提醒的类型和数量，应用服务继续校验保真与权限。最多三次尝试；修复指令替换旧修复消息，保留原需求和有效答案。
- 修复时输出预算有上限，不能用放大预算保证正文达到任意长度。该适配器生成的是优化提示词，未执行下游新闻、论文等作品，因而不会统计这些作品的字数、段数或要点数。
- 优化提示词完整保留了“600–800字”，不代表接收它的另一个模型已经遵守；需检查真实作品。本轮新闻稿增强组的篇幅不足是实际失败，不能以教程经验取消这个验收项。

## 4. 段落或要点指导是否值得采用

可以作为输出组织的辅助，但不保证准确性、完整性或字数。对“简短说明”这类软要求，给出少量要点可能减少漂移；对严格格式、译文、表格、法律文书或指定章节的论文，通用段数可能反而破坏交付。

建议采用顺序：

1. 保留原始需求与有效确认中明确的长度单位、范围、作用对象、段落或要点数。
2. 判断限制是硬要求还是组织建议。用户写“恰好3段”就保持3段；只写“简短”时可以提出简洁组织建议，不能冒充用户指定了固定数量。
3. 无格式冲突时，再按交付物提出可选结构，例如概览、事实、行动信息。目标是覆盖内容，不能为了凑要点增加事实或删掉未决条件。
4. 清楚区分主文、标题、附表、代码、引用与附件的长度范围。用户未说明的计数口径不静默升级成硬规则；评测可以同时记录不同口径并标记不确定。
5. 输出时自行校对；真正要求精确篇幅的下游工作，应由执行环境计数并在有限范围内修订。平台不会因此获得执行用户任务的权限。

例如用户已要求“600–800字新闻稿，标题另列”，可将组织建议写在优化提示词的OUTPUT中：

```text
交付标题和600–800字正文，标题另列。正文可按发布信息、主要价值、
适用对象、能力边界、反馈方式组织成若干短段；段落组织是建议，
正文篇幅和必需事实仍按原要求验收。输出前核对长度，避免填充空话。
```

这是上一轮的拟采用示例。后续采用范围和真实失败见第8节；此前冻结输入未回改。如果建议5–7段，它只能是组织建议且不与用户格式冲突；不能假定每个新闻任务都适用同一段数。

## 5. 与约束补全及Plan的关系

| 情形 | 处理原则 |
| --- | --- |
| 原文“只输出译文” | 保留纯译文交付；不增加提纲、要点、长度报告或解释 |
| 原文“固定3段” | 保留3段，默认模板不得改为5–7段 |
| 主文限字、附表另计 | 仅主文按限制验收，附表不得偷偷纳入 |
| 用户明确提供0、false、取消等业务规则 | 篇幅压缩仍保留原规则及条件，不靠删规则控制长度 |
| 用户尚未选择寿命表、分母、评分锚点 | 保留未决条件；不能用短句或固定段数隐藏专业缺口 |
| 固定字数与固定段数同时出现 | 同时保留；出现实质冲突才澄清，不把普通写作细节变成Plan问卷 |
| 输出Token不足或`finish_reason=length` | 按截断/失败记录；段数提示不能代替路由和预算校准 |

建议组织指导位于OUTPUT或交付画像；明确字数位于对应交付说明与必要验收中。沿用现有`RequirementFidelityGuard`及强制安全边界，避免多个模板重复追加互相冲突的格式。本轮不改公开接口、模型目录、上传索引或前端四要素展示。

## 6. 下一步独立验收

采用A/B/C三组：A保留当前优化策略；B增加软性的段落/要点组织；C在同样组织下补有限计数校对。三组使用相同原始需求、资料、实际Plan答案、执行模型与预算；未收集答案的组单独比较。

- 样例覆盖新闻、指南、机关报告、论文主文与附表、教学、翻译、纯JSON以及冲突格式；同时有中长需求、完整需求和真正未决条件。
- 每组固定重复次数，记录字数范围命中、段落/要点命中、关键事实遗漏、规则反转、冗余、正文截断、延迟和真实Token。字数与计数口径先冻结，不因某组失败修改标准。
- 数量可以客观计数；事实和可执行性独立核对。模型自报字数或“检查通过”不算证据，段数正确也不代表业务正确。
- 本轮没有完成上述长度策略的独立A/B/C实验；现有真实跨行业对照见[最终候选报告](../testing/最终候选缺陷修复与跨行业闭环验收-2026-10-05.md)。

## 8. 本轮后续采用与验证（2026-10-05）

`ENHANCEMENT`与新闻交付画像现已区分优化提示词和下游作品篇幅：保留字数单位、上下限、固定结构及标题／附表作用范围；组织内容后核对正文，不拿标题补字、不虚构材料。`NewsLengthContract`仅对明确新闻正文的单一有效整数范围提供软性规划，并由结果组装器写入OUTPUT和可复制正文。600–800的例子给约750及约7个短段起草建议，段数可调整，不新增硬验收；原文固定3段时不追加默认段数。其他任务、纯JSON、非法或冲突范围不推断。

已真实执行两个DeepSeek优化模型×中／长新闻×原始／直接／Plan三组×两个下游模型，最终24份作品全部完整返回。实际计数仍有399汉字／449非空白字符的不足，以及817／898的超长；部分正文遗漏MVP阶段。故“模型更容易按段组织”不能推导为“加入段数就满足篇幅”。最终结果未证明增强稳定优于原文，完整比较及中间48份首次结果见[本轮报告](../testing/DeepSeek开放表达归并与篇幅修复-2026-10-05.md)。

目前尚未完成第6节要求的独立A/B/C、多轮和人工验收。不因模型返回stop、自报字数、段落数或自动关键词命中宣布业务通过。当前平台只生成提示词，不能替下游执行器验证其尚未生成的正文；后续应继续同信息配对、实际计数和必要事实保留检查。TokenHub篇幅预算／截断按用户要求暂缓，本轮只调用DeepSeek。
