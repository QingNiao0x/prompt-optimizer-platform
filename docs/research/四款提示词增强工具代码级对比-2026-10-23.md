## 2. 先区分四种容易混淆的能力

1. **优化用户提示词 / 系统提示词**：区分最终指令的用途或消息角色。它与本项目“自然 / 结构化表达”不是同一维度。
2. **生成步骤化提示词**：把执行步骤写进提示词，未必会向用户提问。
3. **多轮编辑**：用户说“缩短这一段”等意见，模型继续修改正文；不等于问题有来源、答案有归属、确认有边界的Plan。
4. **可复用模板**：有意留下变量供不同任务填写。对模板产品是能力，对一次性自然需求强制添加变量则可能是交付退步。

本项目的“优化提示词”是交给下游执行者的请求，“项目上下文”是事实集合，“上下文摘要”是经过选择与预算处理的本次可见表示。相似提示词、格式模板、对话历史均不能自动替代项目事实。术语依据：[CONTEXT.md](../../CONTEXT.md)。

## 3. JIULANG9/PromptOptimizer：本机模板式改写

### 3.1 架构与完整路径

Flutter界面、Riverpod状态、Drift/SQLite模板及历史、Hive设置、Dio模型请求构成本机应用。没有与我们的Spring Boot API对应的独立增强后端。

```text
输入原始提示词，选择用户/系统用途、模型和模板
→ HomePage._onOptimize
→ OptimizationNotifier.optimize
→ OptimizePromptUseCase.execute
→ TemplateEntity.buildMessages 替换 {{originalPrompt}}
→ OpenAiApiService.streamChatCompletion
→ SSE文本累加
→ 展示、编辑、复制、本地历史
```

用例从仓库取模型配置和模板，模板中的system/user消息插入原文后直接请求模型；正常增强为一次逻辑调用。服务请求包含model、messages和stream，没有单独的任务理解或质量审阅阶段。模型响应读取delta.content，没有要求生成来源表、覆盖矩阵等内部业务JSON。[用例编排](https://github.com/JIULANG9/PromptOptimizer/blob/750c866e21e8a4c745c64f8b915da4d3612dbf67/lib/features/optimization/domain/usecases/optimize_prompt_usecase.dart#L29)、[消息构建](https://github.com/JIULANG9/PromptOptimizer/blob/750c866e21e8a4c745c64f8b915da4d3612dbf67/lib/features/template/domain/entities/template_entity.dart#L22)、[模型请求与SSE](https://github.com/JIULANG9/PromptOptimizer/blob/750c866e21e8a4c745c64f8b915da4d3612dbf67/lib/features/optimization/data/openai_api_service.dart#L17)。

### 3.2 增强机制与功能边界

效果主要由用户选中的元提示词决定。基础优化强调清晰、简洁和保留原意；专业优化要求具体参数、量化标准和步骤；系统优化则要求角色、技能、规则、工作流等栏目。空库初始化六条记录，其中四条标记为内置。没有根据职业自动选模板的确定性路由。[默认模板](https://github.com/JIULANG9/PromptOptimizer/blob/750c866e21e8a4c745c64f8b915da4d3612dbf67/lib/database/seed/default_templates.dart#L15)。

所查主链未实现问答Plan、自动多轮优化、项目文件检索或原始与增强的实际作品对比。模板可以包含多条消息，原始文本可以带材料，但这不等于具有持续会话或上下文分析服务。复制后打开其他AI应用，也不等于自动执行和评测。[优化状态与历史](https://github.com/JIULANG9/PromptOptimizer/blob/750c866e21e8a4c745c64f8b915da4d3612dbf67/lib/features/optimization/presentation/providers/optimization_provider.dart#L104)、[复制后跳转](https://github.com/JIULANG9/PromptOptimizer/blob/750c866e21e8a4c745c64f8b915da4d3612dbf67/lib/features/ai_app_launcher/domain/usecases/launch_ai_app_usecase.dart#L17)。

### 3.3 可借鉴与限制

- 可借鉴：生成用例职责窄，配置、模板、正文、历史分开；用户得到的是完整可复制正文。
- 不宜照搬：默认增加量化参数、大量角色栏目，均可能把自然需求过度具体化。其短链没有提供完整事实与权限保护，不能以“更简单”推定“更可靠”。
- 证据限制：测试包含占位smoke和通用输入框光标检查，没有可支持跨任务增强收益的作品评测。README致敬linshenkx，两者也不是两份独立质量实证。[测试目录](https://github.com/JIULANG9/PromptOptimizer/tree/750c866e21e8a4c745c64f8b915da4d3612dbf67/test)、[README](https://github.com/JIULANG9/PromptOptimizer/blob/750c866e21e8a4c745c64f8b915da4d3612dbf67/README.md)。
- 部署差异：用户密钥存于本机，AES密钥来自应用常量派生，不适合作为本项目服务端密钥与多租户隔离的替代。[加密实现](https://github.com/JIULANG9/PromptOptimizer/blob/750c866e21e8a4c745c64f8b915da4d3612dbf67/lib/core/crypto/aes_crypto_service.dart#L13)。

## 4. linshenkx/prompt-optimizer：可编辑、可测试的优化工作台

### 4.1 架构与一次优化

pnpm monorepo将TypeScript核心服务放在`packages/core`，Vue/Pinia/Naive UI交互放在`packages/ui`，Web、Electron、扩展和MCP为不同宿主。Web主要在浏览器实例化core并调用模型，Electron通过IPC接主进程服务，MCP也复用core；不能一概描述成传统独立HTTP后端。[初始化与多端分发](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/ui/src/composables/system/useAppInitializer.ts#L130)、[MCP核心服务](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/mcp-server/src/adapters/core-services.ts#L51)。

```text
选system/user、优化模型和模板，输入原文
→ usePromptOptimizer.handleOptimizePrompt
→ PromptService.optimizePromptStream
→ resolveOptimizationMessages
→ TemplateManager + TemplateProcessor
→ LLMService + Provider Adapter
→ 流式正文/独立reasoning
→ HistoryManager版本链
```

核心生成通常一次逻辑模型调用，响应只检查非空。模板缺省按用途类型选第一项或回退，没有固定职业分类器。输出即模型正文，不附带本项目的taskUnderstanding/coverage协议。[PromptService](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/core/src/services/prompt/service.ts#L133)、[默认模板选择](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/core/src/services/prompt/service.ts#L994)、[UI调用与历史](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/ui/src/composables/prompt/usePromptOptimizer.ts#L110)。

“一次逻辑调用”不等于永远只有一次HTTP请求：OpenAI适配器设置了流式与非流式SDK重试。比较成本应按实际请求统计。[适配器](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/core/src/services/llm/adapters/openai-adapter.ts#L865)。

### 4.2 上下文与模板的实现

字符串模板作为system，原文作为user；消息模板通过Mustache渲染，支持变量、条件、循环和JSON字符串封装。advancedContext可以带对话messages、变量和工具描述，多消息模式可只优化选中的一条。优化时保留已有变量，测试执行时再填值，这一分离比“没传值就要求补齐”更适合复用资产。[模板处理器](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/core/src/services/template/processor.ts#L81)、[执行时变量展开](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/core/src/services/template/processor.ts#L198)。

但它的对话上下文不等同于我们的文件索引、受保护路径过滤和预算化上下文摘要。模板本身也存在取舍：user基础模板要求保留原意，system通用模板则铺开角色与规则；上下文模板在没有上下文或工具时引导保守假设、替代方式或占位，这仍可能误判下游实际资源。[user基础模板](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/core/src/services/template/default-templates/user-optimize/user-prompt-basic.ts#L38)、[上下文模板](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/core/src/services/template/default-templates/user-optimize/context/context-user-prompt-basic.ts#L11)。

`user-prompt-planning`是生成步骤化提示词的模板，**不是提问—用户回答—服务端绑定—最终生成的Plan链**。[planning模板](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/core/src/services/template/default-templates/user-optimize/user-prompt-planning.ts#L36)。

### 4.3 迭代、执行测试和模型评审分开

| 能力 | 实际逻辑 | 对本项目的意义 |
| --- | --- | --- |
| 定向迭代 | 用户输入改进意见，调用iterate，再存新版本 | 比对整份结果反复盲目增强更容易控制修改范围 |
| 原始/增强双执行 | 两份提示词分别交给所选测试模型，展示实际输出 | 直接让用户看到任务交付是否改善 |
| 独立评审 | 评估prompt、result或compare；复杂compare有多组成对判断及综合 | 评审不强塞进每次默认生成 |
| 智能重写 | 用户触发，依据评估建议形成迭代意见；可skip | 充分结果可以保持不动 |

调用依据：[定向迭代](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/ui/src/composables/prompt/usePromptOptimizer.ts#L356)、[真实双执行](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/ui/src/composables/prompt/usePromptTester.ts#L58)、[评估服务](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/core/src/services/evaluation/service.ts#L275)、[重写入口与skip](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/ui/src/composables/prompt/useEvaluationHandler.ts#L550)。

两项重要限制：内置迭代模板实际只带`lastOptimizedPrompt`和`iterateInput`，保存原始历史不等于每轮都重新校对原始要求；自动多轮SPO仍在设计阶段，不能把文档里的状态机当已上线引擎。[实际迭代字段](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/packages/core/src/services/template/default-templates/iterate/iterate.ts#L58)、[SPO实现状态](https://github.com/linshenkx/prompt-optimizer/blob/a201f47d2b17d6cf6a9347f336691b00c98720a1/docs/architecture/spo-thin-loop-ui-and-stop-rules.md#L19)。

**本项目最值得优先借鉴这一项目的服务分工与实际作品对比；现有源码与样例不足以证明其单次增强普遍胜过我们的31。**

## 5. Prompt Ark：可研究产品流程，暂不能审计后端

### 5.1 核实到的公开范围

用户给出的URL是个人主页锚点。该主页仓库固定树只有README；网站页脚GitHub入口也回到同一个人主页。公开账号另有两个fork，README分别介绍通用SaaS模板和其他计算器，没有建立它们就是Prompt Ark生产源码的证据。检索到的其他作者同名PromptArk也不能替代本项目。[主页说明](https://github.com/comparelists/comparelists/blob/1fb95ef1739b18c90135a38194a644a4e9bacde6/README.md)、[公开仓库入口](https://github.com/comparelists?tab=repositories)。

### 5.2 页面可见的增强组织方式

### 5.3 能借鉴什么，不能推断什么

- 可借鉴：快速路径与主动澄清路径分开，优化后可以试用结果。
- 不宜照搬：固定提问数量、默认补全全部角色/受众/语气/格式，可能继续增加用户不需要的条件。
- 未核实：后端技术栈、模型路由、重试、是否有独立编排器、Basic/Advanced具体差异、完整提示词、事实校验与开放许可。
- 网站关于格式可靠性和效果提升的数字属于页面主张，未发现相应可复核实验，**本报告不将其计为质量证据**。

## 6. prompts.chat：单次增强、多轮编辑与模板资产平台

### 6.1 三条机制

当前源码是Next.js/React/TypeScript应用，Prisma/PostgreSQL持久化，Auth.js认证，服务端OpenAI兼容模型调用；另有独立SDK与MCP接口。它已经超出早期静态提示词清单的范围。[依赖与入口](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/package.json#L35)、[数据模型](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/prisma/schema.prisma#L93)。

| 机制 | 输入与处理 | 输出 |
| --- | --- | --- |
| `improvePrompt()` | 已有原文、输出用途/格式，可选相似提示词，再作一次模型改写 | 原文、改写正文、参考来源及模型信息 |
| AI Builder | 当前编辑表单全文、会话、标签/分类，通过模型工具循环修改表单 | 文字反馈与更新后的编辑状态 |
| SDK builder | 调用者明确填写角色、任务、变量等，程序确定性组装 | 文本、messages、JSON或YAML；本身不是模型优化 |

### 6.2 单次增强路径

```text
PromptEnhancer输入原文，选用途与格式
→ POST /api/improve-prompt
→ 认证 + Zod输入校验
→ improvePrompt
→ 可选相似公共prompt检索
→ YAML元提示词插值
→ 一次chat completion
→ trim、非空检查
→ 显示、复制、本地历史
```

接口不让模型填写本项目式来源/覆盖协议，服务端不再追加固定约束。JSON/YAML主要靠指导文本要求，返回后未进行对应schema解析。配置文件写的模型名也不必然实际生效：YAML声明的模型与TypeScript所用`OPENAI_IMPROVE_MODEL`或默认值不同，应以调用代码为准。[API](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/src/app/api/improve-prompt/route.ts#L8)、[实际生成与模型选择](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/src/lib/ai/improve-prompt.ts#L141)。

相似检索在aiSearch启用时才运行：生成查询embedding，读最多100条符合可见性条件的prompt，在应用层算相似度，取阈值以上前三条，每条截取500字符作参考；检索失败可无参考继续。检索对象是“别人怎样写提示词”，不是用户的业务事实。[检索实现](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/src/lib/ai/improve-prompt.ts#L67)。

这条链也不是低成本的当然证明：当前代码连text模式都插入约39k字符完整类型定义。指令还要求文本采用Act as角色格式，鼓励变量与背景补充，偏向可复用模板建设。[元提示词](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/src/lib/ai/improve-prompt.prompt.yml#L12)、[类型定义](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/src/data/type-definitions.ts#L7)。

### 6.3 多轮Builder与交互

前端每轮发送聊天文本和当前完整表单。后端将其与系统指令组合，最多进行10轮模型工具调用，使用`search_prompts`、`set_content`、`set_title`等工具。SSE回传状态，前端将状态写入编辑表单，用户最后提交保存。[后端循环](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/src/app/api/prompt-builder/chat/route.ts#L149)、[前端SSE与状态续接](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/src/components/prompts/prompt-builder.tsx#L146)、[表单应用结果](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/src/components/prompts/prompt-form.tsx#L538)。

它没有独立语义Plan状态机：需要澄清时普通聊天提问，下轮带回答继续。MCP的elicitation则用于填写模板已有变量，也不是判断哪个未知会改变交付。[Builder指导](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/src/app/api/prompt-builder/chat/prompt-builder-agent.prompt.yml#L12)、[MCP变量填充](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/src/pages/api/mcp.ts#L375)。

值得借鉴的细节是修改时注入当前全文、只改用户指定部分。需要警惕的细节是：新建强制先搜示例，文本强制角色，每份prompt鼓励至少1–2变量；检索无命中时还可能回退最新公共prompt。这些规则适合某些资产创作，直接搬到一次性自然需求可能扩大模板化。[编辑/新建策略](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/src/app/api/prompt-builder/chat/prompt-builder-agent.prompt.yml#L21)、[检索回退与工具赋值](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/src/lib/ai/prompt-builder-tools.ts#L253)。

社区版本比较和作者审批属于提示词资产协作；不能把它描述成每次AI增强都会经过语义验收。SDK的`quality.check()`偏向长度、关键词与结构规则，也未接入单次增强作为下游质量门。[版本比较](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/src/components/prompts/version-compare-modal.tsx#L143)、[SDK质量规则](https://github.com/f/prompts.chat/blob/dbb20df3b58aec4c8886bc967eb4861b0528e472/packages/prompts.chat/src/quality/index.ts#L67)。

## 8. 与本项目问题的直接关系

### 8.1 目前无需重写整个架构

本项目的模块化单体、Provider接口、上下文服务、Plan绑定和历史能力已经支持替换正文策略。当前自然入口与旧结构链独立：`DocumentOptimizationController`将COMPACT分给`NaturalEnhancementService`。自然31先判断成果范围，明确成果在Provider中分发到冻结4，所以上一轮34候选不会自动影响日常默认。[README当前边界](../../README.md#enhancement-plan-direction)、[自然/结构路由](../../services/api/src/main/java/com/promptoptimizer/enhancement/controller/DocumentOptimizationController.java)、[自然Provider](../../services/api/src/main/java/com/promptoptimizer/provider/infrastructure/openai/OpenAiCompatibleNaturalPromptProvider.java)。

`MockPromptEnhancementProvider`、`ConstraintCompleterImpl`、`EffectiveTaskViewFactory`和旧`AmbiguityDetector`并不是当前自然31真实生成的直接前置链，不能因其名称像“增强引擎”就把外部模板迁移进去。[自然服务](../../services/api/src/main/java/com/promptoptimizer/enhancement/service/impl/NaturalEnhancementService.java)、[自然输入边界](../../services/api/src/main/java/com/promptoptimizer/provider/domain/NaturalPromptInput.java)。

### 8.2 外部对照揭示的四个改进方向

| 本项目问题 | 外部可借鉴机制 | 本项目具体落点 |
| --- | --- | --- |
| 生成时同时填写多张内部检查表 | JIULANG/linshenkx正文生成职责集中，评估另设服务 | 在现有阶段协议基础上对照减少模型负担，保留服务端身份、完整来源、实际题答与硬约束保护 |
| 未附资料被写成现实未确定 | linshenkx优化与执行时变量处理分开 | 复用NaturalPromptInput、ContextSnapshot和现有范围记录，区别原始要求与执行阶段资源；没有依据不创建现实未知 |
| 用户只能重复点增强 | 定向迭代、完整当前正文、版本记录 | 明确区分首次生成和用户反馈修改；持续携带原始要求、完整实际题答及本轮修改意见 |
| 研发评测很多，用户仍看不到收益 | linshenkx实际双执行和执行快照 | 复用现有评测能力，提供可审查的同信息作品差异及必要修改量，而非只评分提示词外观 |

这里有三个不能机械照搬的边界：第一，服务端无法单凭程序自动证明所有自由文本语义正确，来源/覆盖记录如何减负需要单独验证；第二，运行参数尚未填写只有在用户本来要可复用模板时才应保留变量，不能给普通需求新增填空；第三，保存原始历史不等于生成时已使用原始要求。

### 8.3 上下文预算与资料状态

本项目已有`fileCoverage`、`extractionStatus`、`contextLimited`等信息。按照上下文设计，`contextLimited=true`表示本次只选入部分片段，不代表原文不完整，更不代表用户没有资料。相似prompt检索也不能提供用户的真实地区、数据或项目状态。应利用已有元数据解释可见范围，而非默认增加“尚未确定”“请先补齐”。[上下文预算与过滤](../06-上下文分析设计.md)、[ContextSnapshot](../../services/api/src/main/java/com/promptoptimizer/context/domain/ContextSnapshot.java)。

## 9. 建议的实施顺序与验收

以下为本轮调研建议，未实施，也不是新一批真实调用计划。

**第一步：只验证默认正文的任务重点。**利用当前自然链和阶段协议现有实现，准备一条职责明确的正文候选：保留原定动作与成果，用具体处理内容、材料用途、必要动作和预期发现完成有用补充。证据和局限服务这些内容，充分需求允许原文不变。复用已经证实的失败原件，避免重复把旧问题当新发现；旧4保持冻结，新候选单独比较。

**第二步：把原始要求与执行阶段信息分开传递。**在`NaturalPromptInput`、`NaturalTaskScope`和现有任务理解中复用当前对象，先明确哪些是用户已经说明的事实/约束，哪些是下游需完成的检索、阅读或方法选择。避免新增职业分类器、完整“未知清单”或更多必填槽位。用户明确不知道、明确没有、明确要求先确认时继续保留。

**第三步：收敛模型协议，保留确定性保护。**参考短生成链，但不能直接删除现有来源和题答保护。以已经实现的阶段协议候选为起点，隔离验证“正文+必要语义证据”是否足够，服务端维护来源编号、阶段、版本等机械元数据。分别评估协议可靠性和正文质量；不再让每项工程修复承担全域作品提升的证明义务。[既有阶段协议结果](../testing/自然增强阶段协议解耦与分层验收-2026-10-22.md)。

**第四步：增加基于用户反馈的局部修改能力。**参考定向迭代与全文编辑，保留原始提示词作为稳定基准，明确本轮要改什么，避免上一结果逐轮吞掉原要求。展示变更、恢复及复制历史一致性比再增加一批风格模板更直接。此项需要单独产品范围确认，不能因调研而自动开发。

**第五步：由实际作品决定采用。**沿用同模型、同参数、同资料、同工具能力的原始/31/候选对照；重点检查意图和事实错误、有效补充、可直接使用程度、必要修改量。充分需求持平允许通过保真；协议成功率、延迟、Token另记。公开项目的star、模板数量、格式评分、单次演示均不替代这些证据。[本项目分层验收规范](../testing/自然增强分层验收与独立对照规范.md)。

不建议先复制多轮Agent循环、默认公共提示词RAG、固定职业模板、固定提问数量或强制角色/变量。这些会增加行为变量，却没有现成证据证明能解决本项目当前的过度补全。
