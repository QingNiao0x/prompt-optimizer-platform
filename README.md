# Prompt Optimizer Platform

面向开发者、科研工作者、学生和通用知识工作者的提示词优化平台，帮助用户把模糊、简短的自然语言需求，转换为清晰、具体、可执行的结构化提示词。

它的目标是减少“生成一次、发现缺信息、再手工改提示词”的反复过程。用户可以直接增强，也可以主动开启 Plan 确认，先回答真正重要的细节，再一次获得可直接使用的最终提示词。

> 当前阶段：MVP 本地联调阶段。Vue 提示词工作台、内置 Plan Mode、项目上下文分析、结构化提示词增强、Mock/OpenAI 兼容 Provider、优化历史和 Provider 配置管理已实现并有自动测试；用户管理和浏览器插件仍在规划中。

## 项目简介

在使用 ChatGPT、DeepSeek、Claude 等大模型进行开发时，很多人都经历过这样的场景：**一句需求、一个想法丢给 AI 就开始执行，但最终做出来的效果往往并不是自己想要的，只能反复推倒重来，白白浪费时间和 Token。**问题通常不在 AI 本身，而在于需求没有被充分表达，模型只能根据有限的信息猜测背景、目标和边界。

例如，用户可能只会提出一句：

```text
添加工单升级功能
```

这类需求通常缺少背景、输入输出、边界条件、异常处理、权限范围和验收标准，容易导致模型反复追问，或者生成与项目实际情况不一致的结果。模糊需求带来的成本，不只是一次输出不理想，还包括后续反复修改、验证和返工的时间，以及持续消耗的 Token。

Prompt Optimizer Platform 正是为解决这一问题而设计：它通过“一键增强”能力，**结合用户提供的项目上下文、对话历史、个人偏好和安全规则，将模糊的自然语言需求整理为更清晰、具体、可执行的结构化提示词，帮助用户把“让 AI 猜需求”转变为“让 AI 按明确目标和约束执行”，降低反复试错成本。**

> 让 AI 先理解你的项目和文档，再帮你生成真正可执行的提示词。

本项目参考 Qoder 公开资料中关于“一键增强提示词、项目级上下文、权限红线和模块化模板”的产品思路，但不会将 Qoder 的执行器、自动提交代码或宣传性效果描述视为本项目当前已经实现的能力。

## 核心能力

### 1. 一键增强提示词

**工作台默认直接生成最终结构化提示词；用户主动开启“Plan 确认”后，系统会先分析已提供的相关文件，再在弹窗中询问仍会明显影响结果的关键问题。全部回答完成后，系统按确认信息再次检索上下文并生成结果。原始提示词会被保留，结果支持复制、编辑、撤销和再次增强。**

### 2. 需求明确化

系统识别需求中真正影响结果的未决信息。开启 Plan 确认时，系统会在生成前用用户熟悉的语言逐题询问；直接增强时，这些信息作为待确认事项随结果返回。科研任务可以询问地区、数据来源、疾病分类、人群分组、分析工具和是否需要代码；软件任务可以询问运行环境、实现选择和验收结果。界面不会向用户展示模板代码或“缺失维度”等内部术语。

例如：

```text
原始需求：弄个排序
```

可以增强为：

```text
任务目标：使用 Python 实现一个处理整数列表的排序功能。
输入输出：输入整数列表，输出按升序排列的新列表。
约束条件：处理空列表、重复元素和负数；说明时间复杂度；遵循 PEP 8；补充单元测试。
验收标准：正常数据、空数据、重复数据和负数数据均有明确测试结果。
```

### 3. 项目上下文化

用户可以主动选择或上传项目文件摘要，系统分析：

- 编程语言和技术栈，例如 Java、Spring Boot、Vue、TypeScript、Python、Go；
- 关键依赖，例如 Spring Boot、PostgreSQL、Redis、Vue、Vite；
- 主要目录和文件结构；
- 用户提供的代码片段和自定义项目描述；
- 上下文来源、截断信息和敏感信息脱敏结果。

项目上下文默认只参与当前请求，不读取用户电脑上的任意绝对路径，也不默认保存完整源代码。

### 4. 约束条件完善化

系统根据技术栈和用户策略补充容易遗漏的工程约束，包括：

- 参数校验、空值、非法值和边界条件；
- 异常处理和清晰的错误信息；
- SQL 注入防护和参数化查询；
- API Key、Token、密码和私钥保护；
- Java、Spring Boot、Vue、TypeScript 等技术栈规范；
- 正常、异常、边界和安全测试；
- 数据库事务、缓存 TTL 和兼容性要求。

### 5. 结构化输出

增强后的提示词按照清晰的模块组织，当前核心结构包括：

- 背景信息；
- 任务目标；
- 输入与输出要求；
- 约束条件；
- 验收标准；
- 示例参考。

其中“背景、任务、输出、约束”是基础四要素，“验收标准”和“示例”按任务需要补充。开启 Plan 确认后，待确认问题会在最终生成前完成；直接增强则允许在结果中保留明确标注的待确认事项。

### 6. 权限红线与安全边界

用户可以为当前请求补充受保护路径和需要人工确认的动作。系统还会提供默认安全边界，例如：

- 不读取 `.env`、私钥和敏感配置；
- 不泄露 API Key、密码和 Token；
- 删除文件、数据库结构迁移和生产部署需要人工确认；
- 文件内容仅作为项目资料，不能覆盖系统安全规则。

本项目当前只生成提示词和安全约束，不直接执行命令、修改代码或部署生产环境。

## Plan Mode 增强方法

Plan 确认由用户主动开启。开启后的增强流程分为以下步骤：

1. 从浏览器本地索引按原始需求选择初步相关文件；
2. 在后端过滤受保护内容，分析技术栈、目录、依赖和内容摘要；
3. 结合需求文本与安全上下文摘要，识别仍会显著影响结果的未决问题；
4. 在弹窗中提供候选答案或自定义输入，并等待用户逐项确认；
5. 使用原始需求和确认答案再次检索上下文；
6. 在服务端内部选择通用、研究分析或软件任务生成策略；
7. 添加领域约束、权限红线和人工确认要求；
8. 生成并校验包含背景、任务、输出和约束的最终提示词。

关闭 Plan 确认时，工作台跳过上下文准备接口和计划接口，按原始需求检索一次最终上下文，并以 `AUTO` 策略直接调用最终生成接口。服务端仍执行上下文分析、安全过滤、四要素校验和模糊点检测。

## 使用示例

### 原始提示词

```text
用 requests 库爬取某个网页的标题。
```

### 优化后的提示词

```text
任务目标：使用 Python requests 库获取指定网页 HTML 中的 title 内容。

输入输出：输入一个 URL，输出网页标题字符串。

约束条件：
1. 处理空 URL、非法 URL 和网络异常。
2. 设置合理的请求超时时间。
3. 处理网页编码异常和不存在 title 标签的情况。
4. 输出清晰的错误提示，不打印敏感请求头或凭证。
5. 遵循 PEP 8，并补充正常、异常和边界测试。

示例参考：提供一个公开测试 URL，并说明成功和失败时的预期输出。
```

## 使用建议

- 先写清主要目标即可；需求复杂或关键信息不足时，开启 Plan 确认，让系统在生成前主动提问；
- 复杂需求拆分为多个子任务逐步增强；
- 提供输入输出示例，减少模型猜测；
- 仅上传完成当前任务所需的文件或摘要；
- 检查增强结果中的事实来源，不把模型推断当作项目事实；
- 对安全、隐私、医疗、法律和财务等高风险结果进行人工复核；
- 对专业结论和高风险操作保留人工复核。

## 项目定位与边界

本项目的核心产品是“提示词优化”，不是通用聊天机器人、代码自动执行器或自动部署平台。后续可以扩展：

- 历史记录和配置管理；
- PDF、Word、图片和扫描版 PDF 的内容识别；
- 更多领域问题策略与动态展示方式；
- ChatGPT 和 DeepSeek 网页端浏览器插件；
- 项目知识库、规则管理和上下文压缩。

医疗、法律、财务等场景必须增加脱敏、免责声明和人工复核机制，不能承诺模型输出具有专业结论效力。

## 1. 项目目标

- 将开发、研究、学习、写作和分析等模糊需求转换为可直接使用的结构化提示词。
- 在不默认持久化项目源码的前提下，分析技术栈、目录结构、依赖和用户提供的代码片段。
- 通过统一 Provider Gateway 支持 OpenAI 兼容端点、Anthropic、DeepSeek 及未来的自定义模型服务。
- 为个人用户、团队协作、额度计费、审计和 IDE 插件预留演进空间。

## 2. 推荐技术栈

| 层次 | 技术 | 选择理由 |
| --- | --- | --- |
| Web 前端 | Vue 3 + Vite + TypeScript + Element Plus | 开发效率高、组件生态成熟、适合后台型 SaaS |
| 前端状态 | Pinia + Vue Router + Axios | 状态边界清晰，便于后续接入权限和多工作区 |
| 后端 | Java 21 + Spring Boot 3 + Spring MVC | 长期维护、企业生态成熟，适合模块化单体起步 |
| 安全 | Spring Security + JWT（可选） | 便于从匿名试用过渡到登录、团队和 API Token |
| 数据库 | PostgreSQL 16 | 事务、JSONB、全文检索和扩展能力适合提示词与用量数据 |
| 缓存 | Redis 7 | 限流、短时上下文缓存、会话和异步任务状态 |
| API 文档 | OpenAPI 3 | 前后端契约共享，也方便未来 IDE 插件调用 |
| 构建与部署 | Maven、Docker、Docker Compose、Nginx | 本地启动简单，生产环境可迁移至 Kubernetes 或云托管 |
| 可观测性 | Micrometer + OpenTelemetry（规划） | 监控接口耗时、模型耗时、Token 用量和错误率 |

### 为什么选择 PostgreSQL

本项目既有稳定的关系数据（用户、工作区、历史、配置、用量），又有结构会演进的 JSON 数据（上下文摘要、优化结果元数据、Provider 扩展字段）。PostgreSQL 可以用关系表保证一致性，用 JSONB 承载可演进字段，同时避免第一阶段引入文档数据库的运维复杂度。

## 5. 当前实现边界

- 默认使用无需密钥的 Mock Provider；配置环境变量后可切换到 OpenAI 兼容 Chat Completions 端点。
- 不让 Web 后端直接读取用户电脑任意路径；浏览器版仅支持用户主动选择/上传的文件或目录摘要。
- 文件上下文支持代码/文本、`xlsx/xls`、`docx/doc`（提取文本）和常见图片（仅提取元数据）；暂不支持的格式清单见 [上下文分析设计](./docs/06-上下文分析设计.md)。
- 不默认把项目源码、完整上下文或 API Key 写入数据库。
- Provider 配置管理已实现基础 CRUD：API Key 使用 AES-256-GCM 加密存储，接口只返回末四位，不返回明文。
- 优化历史已实现自动保存、分页查询、详情、删除和重新优化；用户管理、额度与计费仍待实现。
- 不在第一阶段拆分微服务；采用模块化单体，等用量和团队边界稳定后再拆分。

后端启动与 Provider 配置见 [services/api/README.md](./services/api/README.md)。
