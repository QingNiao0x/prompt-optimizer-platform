# Prompt Optimizer Platform

面向开发者、学生、视觉与文案创作者、办公人员和科研工作者的 AI 文本与图像提示词工具平台，提供三项核心功能：**提示词增强**、**图像转提示词**和独立的**文章祛 AI 味**工作台。

**把想法与参考图整理成清晰的提示词，把已有文章润色成适合读者的表达。** 提示词增强结合用户主动提供的项目上下文，支持自然正文、结构化表达和可选 Plan 确认；图像工作台支持参考图还原与 Plan 辅助创作；文章工作台直接交付润色正文。

> 当前阶段：MVP 本地联调与内部试用。三项核心功能均已有独立工作台和历史入口，复用平台身份与模型目录。提示词增强、图像理解与 Plan 创作、三档文体润色及正文差异对比已有工程实现；正式上线仍需完成拟开放模型的真实业务验收、双人评审及部署验收。团队管理、额度计费和浏览器插件等仍属后续范围。

## 项目简介

在使用 ChatGPT、DeepSeek、Claude 等大模型进行开发、写作或分析时，一句需求和相关材料未必能直接换来满意结果。影响因素包括需求表达、上下文选择、增强策略和执行模型能力，不能把问题都归因于用户没有说清楚。平台应承担理解与整理的工作，并通过实际输出检验增强是否有帮助。

Prompt Optimizer Platform 围绕三类任务提供对应入口：

| 功能与页面入口 | 主动提交的材料 | 实际交付 |
| --- | --- | --- |
| 提示词增强（`/workbench`） | 原始提示词，以及按需提供的代码、文档或项目背景 | 保留原任务意图的优化提示词，可选择自然正文或结构化表达、按需开启 Plan |
| 图像转提示词（`/image-to-prompt`） | 一张参考图用于还原；或文字构想搭配可选参考图用于 Plan 创作 | 描述参考图或指导新图创作的提示词，供用户复制给绘图工具 |
| 文章祛 AI 味（`/text-polish`） | 已有正文，以及文体、读者、保留文字等要求 | 可与原文对照、编辑和复制的润色正文 |

提示词增强把需求整理这一步放在执行之前：结合**原始提示词、用户主动提供的项目上下文、本次 Plan 确认答案和平台安全规则**，组织目标、输出要求、约束与待确认信息。你不必先掌握一套复杂的提示词写法，也可以从一句自然语言开始。

常用路径是：**写下想法 → 按需添加材料 → 直接增强或 Plan 确认 → 审阅、编辑并复制优化提示词**。图像工作台另有自己的视觉分析与创作问答，不自动读取文本工作台的文件、源码或 Plan 会话。

提示词增强模块交付优化提示词，并保持你原本想完成的任务：要写报告，就增强“写报告”的要求；要做方案，才围绕方案组织提示词。资料不足不应把任务改成补材料问卷或通用大片填空模板。该流程后续的写文章、分析数据或修改代码，由你选择的模型或工具执行；本平台不会自动执行命令、提交代码、发送邮件或部署系统。

图像转提示词支持文本／图片输入：关闭 Plan 时从单张参考图提取主体、构图、光色、风格与可辨认文字；开启 Plan 时围绕新图构想确认关键决定，参考图可选，最终仍交付提示词，不在产品内生成图片。见[图像转提示词使用说明](./docs/development/图像转提示词实现与使用说明.md)。

独立的“文章祛 AI 味”工作台接收已有正文，提供**正式清晰、自然流畅、轻松交流**三档文体，支持正文差异对比、编辑复制和私有历史保存。默认自然流畅，切档不调用模型；管理员在统一模型管理中单独设置润色模块的可用模型和默认项。它不接入提示词增强或任何 Plan 流程，也不提供 AI 检测分数或检测通过率承诺。见[文章润色使用说明](./docs/development/文章祛AI味实现与使用说明.md)。

## 适合哪些使用场景

按材料与交付目标选择工作台：文字需求在提示词增强中整理，图片描述与新图构想进入图像工作台，已有文章的表达调整进入独立润色工作台。具体效果仍需结合材料和所选模型核对。

| 用户与场景 | 可以从这样的需求开始 | 使用与核对重点 |
| --- | --- | --- |
| 开发者：功能、排错、重构与测试 | “给现有工单增加升级处理功能” | 现有实现、修改范围、状态与权限规则、异常分支及验证方式 |
| 学生与教师：学习和资料整理 | “根据这些课程资料制定复习计划” | 当前水平、知识范围、可用时间、练习方式和引用来源 |
| 文案创作者：文章、邮件与演讲稿 | “把这份活动资料改成公众号预告” | 目标受众、发布渠道、语气、篇幅及必须保留的事实 |
| 办公与运营人员：纪要、报告和方案 | “把会议记录整理成行动清单” | 议题、已确认决议、负责人、期限和仍待核实的信息 |
| 科研与分析人员：研究方案和分析需求 | “根据数据字典整理统计分析要求” | 研究对象、数据来源、指标口径、方法条件和交付形式 |
| 视觉创作者：参考图还原 | “根据这张参考图，整理供绘图工具使用的提示词” | 关闭图像 Plan，描述实际可见的主体、关系、构图、风格和不确定内容，不承诺像素复刻 |
| 设计与运营人员：Plan 辅助创作 | “为读书会设计一张海报，参考这张图的配色” | 开启图像 Plan，填写构想，按需指定参考图的主体／风格／布局用途，确认后生成新图提示词 |
| 已有文章：表达润色 | “将这篇说明调整为自然流畅，保留原有事实与指定原句” | 在文章工作台选择三档文体之一，核对正文差异，编辑或保存为私有历史；不进行 Plan 问答 |

开发、学习、写作、办公和科研的文字需求共享提示词增强工作台，尚未按职业分别提供专用编辑器；图像与文章润色各有独立工作台。三项功能均未完成所有专业领域的质量验收。输入研究方案不代表已经取得研究结果，上传数据字典也不代表已经提供实际数据；生成内容仍需保留这些区别。

## 核心能力

前六项介绍提示词增强的能力，后两项分别介绍图像工作台和独立文章润色工具。三者复用平台基础设施，业务输入、生成链路和历史分别管理。

### 1. 一键增强提示词

输入原始提示词，按需添加文件或背景说明，点击增强即可开始。工作台默认直接生成结果；开启“Plan 确认”后，先补充会影响结果的决定，再生成优化提示词。

工作台保留原始提示词，结果支持编辑、复制和再次增强。“再次增强”使用当前结果作为新的输入，并遵循当前 Plan 开关；“复制并打开”目标平台后，仍由用户自行粘贴和发送。

### 2. 需求明确化

将“帮我处理一下”进一步组织为“处理哪些材料、要交付什么、哪些规则必须遵守”。系统结合本次需求和可用上下文识别未决信息；开启 Plan 时用自然语言提问，直接增强时则允许在结果中保留待确认事项。

例如，演讲稿任务需要说明受众、场合和时长，研究任务需要核对对象、数据来源和分析口径，软件任务需要明确行为规则和影响范围。没有依据的事实不能变成既定信息；用户委托的方法设计可以给出拟议方案和适用条件，真正影响结果且只有用户能定的选择仍需确认。

### 3. 项目上下文化

把你提供的代码、项目说明、草稿、报告或表格作为本次需求的依据，减少重复描述背景。代码项目可以识别技术栈、依赖和目录结构；普通材料可以提取文本，并围绕当前任务检索相关片段。

- **代码项目**：浏览器对主动选择的目录建立本地索引，生成前检索有限的相关代码块。
- **文档材料**：支持 PDF 文字层及 Word、Excel、PowerPoint 文本提取；JPEG／PNG、扫描或混合 PDF 可在逐页预览、遮挡并明确同意后，通过已接入的视觉大模型识别，无需独立 OCR 服务器。大型文档采用分片上传和临时索引。
- **覆盖情况**：解析失败、截断或覆盖不足会通过分析报告和警告展示；文件被选中不等于全部内容已进入模型。

浏览器只处理用户主动选择的文件，不读取任意本机路径。使用真实模型时，参与本次生成的内容会经后端发送给模型供应商；本地索引不等于全程离线。临时索引和历史保存范围见下方“当前实现边界”。

上下文视觉识别复用模型管理的视觉能力登记，选择页与调用费用单独确认；未识别或失败页会明确提示，成功结果由 Plan 和最终增强复用，不重复识图。识别后脱敏无法阻止原图隐私首次被供应商看到；禁止外发的资料应选择“仅本地提取”。见[图片与 PDF 上下文识别使用说明](./docs/development/图片与PDF上下文识别使用说明.md)。

### 4. 约束条件完善化

依据本次任务补充约束重点：软件任务关注参数、异常、兼容性和测试；研究分析关注数据来源、统计口径、方法条件与不确定性；通用任务关注交付范围、事实依据和明确的格式要求。

原始需求中的条件、否定、数值与已确认答案会参与结果校验和补全。自然模式同次生成核对适用要求、实际缺口和正文覆盖，Plan记录提问影响，但不能保证识别所有领域的语义错误；事实、数字、引用和专业方法仍需用户复核。自然模式不自动追加平台固定条款，结构化链路保留原有条款策略，用户明确追加权限与服务端安全过滤继续保留。

### 5. 结构化输出

**两种模式使用不同生成策略。** 默认直接增强使用独立自然链路，理解原任务并按必要缺口补充内容，框架只作组织诊断；开启“结构化提示词”后，使用原生成器按五类标准模块组织，有独立内容才呈现，不为填满模块生成通用文字。工作台无需手动选择模板。

| 输出内容 | 当前 MVP 行为 |
| --- | --- |
| 背景、任务、输出、约束 | 自然模式直接输出完整正文，不生成四个假段落；结构化模式显式呈现背景、任务、输出要求、约束条件。 |
| 验收标准 | 结构化模式保留明确要求或有独立检查价值的验收，不再用模板默认文字凑第五模块；自然模式仅补任务适用且可检查的要求。具体质量与冗余继续验证。 |
| 示例要求 | 示例参考开关已退役；按原始提示词、实际题答中的举例要求、禁令与格式处理。 |
| 待确认事项 | 有实际未决信息时出现；执行前必须确认的条件也会进入可复制正文。 |

紧凑／分节的显示、复制、编辑及历史元数据已接通。新自然正文支持版本控制保存、失败保稿及同记录编辑撤销；当前NATURAL/31先区分任务动作与成果要求：准备任务保留原请求，明确成果复用冻结第四版生成；全部来源、实际题答与正文覆盖保护保持。旧版本指导冻结兼容。[2026-10-20的43次真实评测](./docs/testing/自然增强要求覆盖与实际作品复验-2026-10-20.md)记录相同信息下的实际作品：充分需求三类并列可用，报告篇幅仍有不足，成本增加，尚未证明跨任务稳定收益。实现及兼容范围见[独立自然增强与 Plan 链路](./docs/development/独立自然增强与Plan链路.md)。

### 6. 权限红线与安全边界

提示词增强对提交的上下文过滤默认受保护路径，并对可识别的敏感内容执行检测或脱敏。自然模式不自动追加固定条款，用户已明确的保密与权限要求仍保留；结构化链路按任务保留凭据保护、受保护文件范围及人工确认等既有条款策略。可复制正文和服务端安全过滤分别处理，不因自然正文取消固定块而关闭输入保护。

上传内容仅作为资料，不能覆盖平台安全规则。API 支持追加受保护路径和确认动作，不能关闭平台默认红线；当前工作台使用默认规则。这里的权限红线用于生成任务边界，实际执行权限仍由下游工具和用户控制。

### 7. 图像转提示词与 Plan 辅助创作

独立图像工作台提供两条路径：

- **参考图还原**：关闭 Plan，选择一张 JPEG／PNG 图片，从实际可见内容生成描述性提示词，不额外引导改变主体或场景。
- **新图创作**：开启 Plan，先写文字构想，可以不附图；也可附上最多三张图片，分别指定整体灵感、主体、风格或布局用途。确认重要未知后生成新图提示词，指定画面文案按原文保留；要求充分时可以零问并确认生成。

用户可以选择提示词语言，补充下游绘图工具，以及新图所需的项目背景摘要；不自动读取本机项目或复用文本增强的上下文。结果支持查看视觉分析、编辑、复制和私有历史；基于已有文字再次优化使用已保存正文与分析摘要，不重新读取原图。

图片只有在用户检查隐私、勾选同意并主动提交后，才上传至后端并按所选路由发送给模型供应商。服务端校验实际格式、尺寸和像素预算，校正 JPEG 方向并重新编码清除元数据；规范化后的临时图片约一小时失效，不进入长期历史。带图调用必须使用管理员已登记视觉能力的可用模型，Mock 仅为演示。无需独立 OCR 服务，但不保证小字识别、像素复刻或下游成图效果，也不在产品内执行绘图。详细限制见[实现与使用说明](./docs/development/图像转提示词实现与使用说明.md)。

### 8. 文章祛 AI 味：独立正文润色

`/text-polish` 接收已有正文并直接交付润色结果，**不生成供下游使用的润色提示词，不接入提示词增强或图像模块的 Plan**。

| 文体 | 适用表达 |
| --- | --- |
| 正式清晰 | 报告、商务邮件和正式说明 |
| 自然流畅（默认） | 一般文章和日常沟通 |
| 轻松交流 | 社交内容和面向大众的介绍 |

切换文体只更新设置，用户点击润色才调用模型。支持指定原样保留的文字、改写幅度、读者与补充要求；结果可对照原文查看增删差异，编辑保存、复制、基于原文重新生成或以已保存当前稿继续润色。私有历史保留原始输入、生成快照、当前编辑稿、文体及来源修订；查询和修改受用户、租户、工作区范围限制，删除采用逻辑删除。关闭历史持久化的演示模式只在服务内存中保留记录。

模型来自统一平台目录，但文章模块有独立准入列表与默认模型，由管理员在“模型管理 → 文章润色模型”配置；用户只能选择已开放的模型，端点和密钥留在服务端。正文及必要设置会发送给所选模型，不是本地离线润色。当前输入最多 12000 字符；差异提示和保留文字检查辅助人工核对，不承诺语义完全不变或通过 AI 检测。使用方式与模型配置见[实现与使用说明](./docs/development/文章祛AI味实现与使用说明.md)。

## Plan Mode 增强方法

本节描述提示词增强的 Plan；图像创作有独立的 Plan 输入与问答协议，文章润色不使用 Plan。

Plan 默认关闭，首次开启会显示说明，选择保存在当前浏览器中。它适合需要先明确范围、方法或交付要求的任务。

![提示词增强流程：默认直接增强；开启 Plan 后按需提问、确认答案，再生成优化提示词](./docs/images/plan-mode-flow.png)

1. **先看材料**：有文件时，先检索相关片段并准备经过安全处理的上下文摘要和证据；没有文件时，也可直接依据原始提示词和补充说明开始。
2. **识别关键问题**：结合已知信息生成最多 8 个确认问题，支持单选、多选和自由输入。已提供的事实用于减少重复追问；没有需要提问的内容时，直接进入最终生成。
3. **主动确认答案**：推荐项不会自动成为你的选择。可以选择候选项，在允许时填写自定义回答，也可以回看并修改已填答案；自定义回答会替换已选项。所有题目填写有效答案后，点击“生成最终提示词”。
4. **按答案再次检索**：使用原始需求和确认答案重新选择相关上下文，服务端核对答案与本次计划、需求及上下文的对应关系，再生成和校验结果。
5. **审阅并使用**：原始提示词保留，最终生成自动保存优化记录；用户检查事实和未决条件后，可以编辑、复制或再次增强。计划提问阶段不生成优化记录，页面编辑也不会覆盖原历史记录。

“暂不确定”仍属于未决信息，二次检索发现的新冲突也可能继续显示在结果中，并写入正文的执行前确认要求；完成问答不代表所有条件都已确定。计划过期时会重新生成问题，并提示核对可恢复的答案草稿后再次确认。

关闭 Plan 时，按原始需求检索一次最终上下文，直接调用生成接口；服务端仍执行上下文分析、安全过滤、结构校验和模糊点检测。详细契约见[内置 Plan Mode](./docs/12-内置Plan-Mode交互与接口.md)。

## 使用示例

以下为人工编写的结构化示意，展示增强时应明确的内容；实际输出会随材料、确认答案、模式和模型变化。自然模式输出自然正文，不自动追加固定条款。

### 开发场景：从一句需求到可核对的任务说明

原始提示词：

```text
用 requests 库爬取某个网页的标题。
```

优化提示词示意：

```text
背景：使用 Python requests 获取用户指定网页的标题，目标 URL 由用户提供。

任务：编写网页标题提取函数，说明调用方式及所需依赖。

输出：提供代码、调用示例和错误处理说明，成功时返回标题字符串。

约束：
1. 处理空 URL、非法 URL 和网络异常。
2. 设置合理的请求超时时间。
3. 处理网页编码异常和不存在 title 标签的情况。
4. 输出清晰的错误提示，不打印敏感请求头或凭证。
5. 遵循 PEP 8，并补充正常、异常和边界测试。

验收标准：覆盖正常网页、缺少标题、非法 URL 和网络异常，不泄露凭据。
```

### 写作场景：把素材、受众和表达要求放在一起

原始提示词：

```text
根据上传的活动资料，写一篇面向初学者的公众号预告，300 字左右，语气亲切。
```

优化提示词示意：

```text
背景：依据用户上传的活动资料，为初学者准备公众号活动预告。

任务：提炼活动主题、适合人群和参与方式，保持亲切、容易理解的表达。

输出：约 300 字的预告正文，清楚说明读者可以了解什么、如何参与。

约束：仅使用资料中能够核实的事实；不编造讲师经历、效果承诺、时间或费用。
如果报名方式等执行所需信息缺失，将其列为发布前须确认的条件。

验收标准：受众、篇幅和语气符合要求；关键事实可回到材料中核对。
```

这两种提示词增强场景得到的都是交给下游模型的任务说明，本平台不在此执行代码或直接交付文章。已有正文需要润色时，请使用独立文章工作台，它交付的是润色正文。

## 使用建议

- 先写目标，再补充用途、受众和期望交付形式；复杂需求拆成可以独立描述的任务。
- 对会改变结果的重要决定使用 Plan；已有明确要求时可以直接增强。
- 图像还原与新图创作按目标选择模式；附图前检查隐私，生成后将提示词复制给自己的绘图工具。
- 已有文章选择独立润色工具，先确定文体和需要保留的文字，再通过正文差异核对事实与语义。
- 按需上传相关材料或提供输出示例，发送前检查内容范围并移除凭据及不必要的个人信息。
- 生成后核对事实、数字、引用和待确认事项，再复制给下游模型；重要约束应保留在正文中。
- 研究、学习和专业材料保留来源与人工复核要求，不用生成内容冒充已完成的实验、真实数据或权威结论。

## 项目定位与边界

平台当前提供三个工作台：上下文感知的提示词增强、文字／图片输入的图像转提示词、已有文章的独立润色。前两项交付提示词，文章工具交付润色正文；图像 Plan 与文本 Plan 分别管理，文章不加入任一 Plan。项目上下文处理、私有历史和基础认证已有实现；自动执行代码、浏览器或桌面操作、自动发送消息、产品内绘图及生产部署不属于当前产品能力。

后续方向包括更细的领域策略、按需展示与分段复制、扫描版 PDF OCR、更多视觉／润色模型与场景的质量验证、浏览器/IDE 插件，以及团队协作和额度计费，具体以[待办事项](./docs/待办事项.md)为准。图像语义分析已在独立图像工作台实现，不代表文本附件链路已支持识图或扫描 PDF OCR。

医疗、法律、财务等高风险领域的专用能力仍需独立设计与评测；平台不承诺优化提示词或下游模型结果具备专业结论效力。跨行业效果、节省 Token 或减少返工的幅度，需要真实使用证据，不能从结构校验或 Mock 测试推导。

## 1. 项目目标

- 将开发、研究、学习、写作和分析等需求整理为保留原意的优化提示词，支持自然正文与结构化表达。
- 从参考图片提取描述性提示词，或通过文字构想与可选参考图辅助规划新图提示词。
- 为已有文章提供独立润色工作台，支持三档文体、正文差异核对与私有历史。
- 在不默认持久化项目源码的前提下，分析技术栈、目录结构、依赖和用户提供的代码片段。
- 通过统一 Provider 接口接入 Mock 与 OpenAI 兼容模型服务，并为更多供应商适配预留空间。
- 在个人账户、优化历史和基础审计之上，逐步扩展团队协作、额度计费和插件能力。

## 2. 推荐技术栈

| 层次 | 技术 | 选择理由 |
| --- | --- | --- |
| Web 前端 | Vue 3 + Vite + TypeScript + Element Plus | 开发效率高、组件生态成熟、适合后台型 SaaS |
| 前端状态 | Pinia + Vue Router + Axios | 状态边界清晰，便于后续接入权限和多工作区 |
| 后端 | Java 21 + Spring Boot 3 + Spring MVC | 长期维护、企业生态成熟，适合模块化单体起步 |
| 安全 | Spring Security + JWT（可选） | 便于从匿名试用过渡到登录、团队和 API Token |
| 数据库 | PostgreSQL 16 | 事务、JSONB、全文检索和扩展能力适合提示词与用量数据 |
| 缓存 | Redis 7 | 限流、短时上下文缓存、会话和异步任务状态 |
| API 文档 | OpenAPI 3 | 前后端契约共享，也方便未来 IDE 插件调用 |
| 构建与部署 | Maven、Docker、Docker Compose、Nginx | 本地启动简单，生产环境可迁移至 Kubernetes 或云托管 |
| 可观测性 | Micrometer + OpenTelemetry（规划） | 监控接口耗时、模型耗时、Token 用量和错误率 |

### 为什么选择 PostgreSQL

本项目既有稳定的关系数据（用户、工作区、历史、配置、用量），又有结构会演进的 JSON 数据（上下文摘要、优化结果元数据、Provider 扩展字段）。PostgreSQL 可以用关系表保证一致性，用 JSONB 承载可演进字段，同时避免第一阶段引入文档数据库的运维复杂度。

## 5. 当前实现边界

截至 2026-10-25，三项功能均有工程实现。以下区分功能行为、数据与模型边界，以及限定验证范围；工程完成不代表全部模型效果或正式发布验收通过。

- **提示词增强**：`/workbench` 处理原始提示词与主动提供的项目上下文，支持自然／结构化表达及可选 Plan；交付优化提示词，不执行用户任务。JPEG／PNG 与 PDF 可经独立预览和外发确认调用视觉模型提取资料，识别指导与图像创作工作台分别维护。
- **图像转提示词**：`/image-to-prompt` 关闭 Plan 时要求一张参考图；开启时要求文字构想，可附零至三张参考图。JPEG／PNG 单张不超过 10 MiB、1500 万像素、单边 8192 像素；还受模型已登记的图片数量限制。选图不自动上传，用户确认隐私后主动提交，服务端按实际格式解码、校正方向并清理元数据。规范化后的临时图片约一小时失效，长期历史保存提示词、输入设置、视觉分析、实际题答与来源元数据，不保存原图或 Base64；这些文字仍可能含图片中的敏感信息。没有自动人脸／证件打码或完整隐私识别保证，用户仍须在上传前检查。模型与文本增强共用目录，带图须显式开放视觉能力；不调用绘图模型生成图片。
- **文章祛 AI 味**：`/text-polish` 直接润色已有正文，支持三档文体、正文差异、编辑复制及私有历史，不接入提示词增强或图像 Plan。输入最多 12000 字符，未实现长文分块或个人风格学习；普通模式在 PostgreSQL 保存原始输入与润色版本，关闭持久化的演示模式记录随服务重启丢失。统一模型目录下另有模块准入与默认项，全局停用／删除和路由可用性优先；不额外部署本地 GPU，不提供 AI 检测分数、检测通过率或“真人度”保证。
